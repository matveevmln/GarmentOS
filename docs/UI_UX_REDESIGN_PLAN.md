# UI/UX Redesign GarmentOS — аудит и план

> Запрошено владельцем проекта 2026-08-23: перед Pilot v1 провести полноценный UX/UI redesign — превратить работающую систему в визуально цельный современный продукт уровня SaaS, одинаково удобный с телефона, ноутбука и большого десктопа. **Это не разработка функциональности**: бизнес-логика, API, схема БД, Snapshot партии, жизненный цикл заказа, генерация спецификаций, RBAC и аудит не меняются.
>
> **Влияние на Freeze.** Решение снимает часть Freeze, зафиксированного 2026-08-04 (`CLAUDE.md`, правило 10) — только в части интерфейса. Запрет на изменение схемы БД, жизненного цикла партии и бизнес-процессов остаётся в силе без изменений. Это решение владельца проекта, зафиксировано здесь как основание.

## 2. Проблемы, найденные аудитом

### 🔴 P0 — блокируют ощущение «современный продукт»

**P0-1. Весь интерфейс зажат в колонку 760px.**
`styles.css:305` — `.app-main { max-width: 760px; margin: 0 auto; }`. На мониторе 1920px рабочая область занимает 40% ширины, по бокам пустота. Это мобильный макет, растянутый на десктоп — прямая противоположность требованию «полноценный рабочий интерфейс, максимальная плотность данных».

**P0-2. Sidebar отсутствует как класс.**
Навигация — горизонтальная лента пилюль поверх контента (desktop) и нижний таб-бар (mobile). При 9 пунктах лента уже требует горизонтального скролла. Нет ни рабочего пространства, ни контекстной панели деталей — того, что задано в требованиях для десктопа.

**P0-3. Планшетный режим не существует.**
Во всём проекте: 4 медиа-запроса в CSS (`640px`, `600px`, два `hover:hover`) и ~22 использования `sm:` в JSX. Префиксы `md:`, `lg:`, `xl:` — **не встречаются ни разу**. Фактически два режима вместо трёх; всё между 641px и ∞ выглядит одинаково.

**P0-4. Две параллельные системы стилей.**
`styles.css` (782 строки легаси-классов) сосуществует с Tailwind design-system. Легаси-переменные (`--bg`, `--surface`, `--ink`, `--muted`) — алиасы токенов, то есть одно значение под двумя именами. `AppLayout` и `LoginPage` целиком на легаси, остальные страницы — на Tailwind. Любое изменение вида требует правки в двух местах.

### 🟡 P1 — заметно вредят ощущению качества

**P1-1. Баг тёмной темы в мобильной навигации.**
`styles.css:321` — `background: rgba(255, 255, 255, 0.92)` захардкожен. В тёмной теме нижний таб-бар остаётся белым. Это ровно тот класс бага, который уже дважды находили и чинили (см. комментарии в `tokens.css:287`), — здесь он остался.

**P1-2. Паспорт партии: порядок блоков не совпадает с приоритетом вопросов.**
Сейчас: Заголовок → Экономика → Производство → пустые заглушки (Материалы/ОТК/Логистика) → Документы → Размеры → История. Три пустые заглушки стоят **выше** реального содержимого (документов и размеров) — пользователь пролистывает пустоту, чтобы дойти до данных.

**P1-3. Все карточки всегда раскрыты.**
На `BatchPassportPage` 7+ секций рендерятся развёрнутыми одновременно. Нет ни accordion, ни progressive disclosure — на мобильном это очень длинная лента скролла. Компонента `Accordion` в системе нет.

**P1-4. Формы создания встроены прямо в страницы списков.**
`ProductionOrdersPage` — 360 строк, из них большая часть — инлайн-форма создания заказа внутри той же страницы, что и список. То же в `PurchaseOrdersPage` (254 строки). `Drawer` и `Dialog` в системе есть, но для этого не используются.

**P1-5. Нет sticky primary action.**
Ключевые действия («Скачать спецификацию», «Создать заказ») уезжают вверх при скролле. На мобильном это означает скролл вверх ради каждого действия.

### 🟢 P2 — техдолг и мелочи

**P2-1. Мёртвый код.** Классы `card-pad`, `entity-form`, `cta`, `pending-list`, `inline-action` — объявлены в `styles.css`, **0 использований**. Файл `components/DataTable.tsx` (40 строк) не импортируется ниоткуда.

**P2-2. Компонентов из целевого списка не существует**: `AppShell`, `Sidebar`, `MobileNavigation`, `TopBar`, `PageHeader`, `SectionHeader`, `MetricCard` (есть `KpiCard` — близко), `Table`, `MobileListCard`, `LoadingState` (есть `Skeleton`), `BottomSheet` (есть `Drawer` на `vaul` — база для него), `Accordion`, `Tabs` (есть `FilterTabs` — другое), `FormField`, `FilterBar`, `Timeline`, `Stepper`, `DocumentRow`.

**P2-3. Playwright не установлен** в `apps/web` (нет ни зависимости, ни конфига). Визуальная проверка, которую требует задание, сейчас технически невозможна.

## 3. Новая Design System

### 3.1. Что НЕ трогаем

Палитра, радиусы, тени, тёмная тема, easing-кривые — **остаются как есть**. Они уже выстроены и утверждены. Меняем только то, чего не хватает.

### 3.2. Типографика — привести к именованным ролям

Шкала есть, но роли не заданы, и компоненты пишут произвольные значения (`text-[0.82rem]`, `text-[1.85rem]`, `text-[0.78rem]` встречаются в разных файлах). Закрепляем 7 ролей поверх существующих токенов:

| Роль | Размер | Начертание | Где |
|---|---|---|---|
| `display` | 1.75rem / 2.25rem (desktop) | 800 | Крупная цифра в KPI, сумма партии |
| `page-title` | 1.4rem / 1.75rem | 750 | `<h1>` страницы |
| `section-title` | 1.05rem | 700 | Заголовок карточки |
| `body` | 0.95rem | 400/600 | Основной текст |
| `body-sm` | 0.85rem | 400 | Вторичный текст |
| `caption` | 0.72rem | 700, uppercase, tracking | Подписи полей, метки |
| `numeric` | наследует | `tabular-nums` | Все деньги, количества, номера |

### 3.3. Spacing — единая шкала

Сейчас отступы задаются произвольно (`gap-2.5`, `gap-3`, `gap-5`, `py-2.5`, `px-4`). Закрепляем 6 ступеней и используем только их: `4 / 8 / 12 / 16 / 24 / 32px` (Tailwind `1 / 2 / 3 / 4 / 6 / 8`).

### 3.4. Цвет как состояние, не украшение

Правило, которое станет проверяемым: **акцентный цвет (`primary`) — только для основного действия и активного пункта навигации.** Всё остальное — нейтральные поверхности. Семантические цвета (`success`/`warning`/`destructive`/`info`) — только для статусов и сумм, никогда для декора.

## 4. Responsive-стратегия

Единая система, один код. Три режима через Tailwind-брейкпоинты:

| Режим | Ширина | Навигация | Контент |
|---|---|---|---|
| **Mobile** | 360–767 | Нижний таб-бар (5 главных пунктов) + «Ещё» → BottomSheet | 1 колонка, карточки вместо таблиц, sticky primary action, детали через accordion/BottomSheet |
| **Tablet** | 768–1199 (`md:`) | Sidebar-rail: только иконки, 64px, раскрывается по кнопке | 1–2 колонки, компактные карточки |
| **Desktop** | 1200+ (`lg:`/`xl:`) | Полный sidebar 240px, закреплён | Workspace без ограничения 760px; таблицы там, где они уместны; опциональная правая панель деталей |

**Ключевое изменение**: `max-width: 760px` снимается; вместо него `max-width` задаётся по типу страницы (список — во всю ширину рабочей области, форма/текст — ограничение по читаемости ~72 символа).

**Touch targets**: минимум 44×44px для всех интерактивных элементов на mobile — сейчас в нижнем таб-баре `padding: 4px 10px` при иконке 21px, то есть ~29px по высоте.

## 6. Паспорт партии — новая структура

Порядок блоков строго по приоритету вопросов владельца бренда:

| # | Блок | Mobile | Desktop |
|---|---|---|---|
| 1 | **Шапка**: модель, номер, цех, количество, статус | всегда развёрнут | всегда развёрнут |
| 2 | **Что требует внимания**: просрочка, неоплаченный этап, отсутствующий документ | только если есть | только если есть |
| 3 | **Деньги**: сумма партии, себестоимость, цена спецификации, разница, условия оплаты | 2 крупные цифры + «подробнее» | полная карточка |
| 4 | **Где партия сейчас**: `Stepper` по статусу | горизонтальный компактный | полный с датами |
| 5 | Документы | accordion | правая колонка |
| 6 | Размеры и цвета | accordion | правая колонка |
| 7 | История | accordion | правая колонка |
| 8 | Материалы / ОТК / Логистика | **уходят вниз**, свёрнуты | внизу |

Первый экран на мобильном отвечает ровно на 4 вопроса: что за партия / сколько денег / что происходит / что делать.

**Пустые заглушки (Материалы/ОТК/Логистика) перемещаются вниз и сворачиваются** — данных под них нет и не будет до реализации соответствующих модулей; они не должны занимать место выше реального содержимого.

## 8. Что НЕ меняется

**Категорически не трогаем:**
- Бизнес-логику любого рода
- Схему БД и миграции
- Snapshot партии (`production_orders.cost_snapshot`)
- Жизненный цикл заказа (draft → placed → in_progress → ready_for_pickup → received)
- Генерацию спецификаций и шаблон PDF
- RBAC и permissions
- Audit trail
- Telegram-интеграцию
- Любые эндпоинты API

**Не добавляем:**
- Новые бизнес-модули
- Вымышленные данные: KPI, проценты готовности, прогнозы, остатки, аналитику. Нет данных → честный `EmptyState`.

**Единственное исключение по зависимостям**: Playwright как `devDependency` в `apps/web` — инструмент проверки, требуемый самим заданием, в рантайм не попадает.

**Если в ходе работы выяснится, что визуальное улучшение требует изменения API или бизнес-логики — работа останавливается, и я объясняю почему, вместо того чтобы менять втихую.**
