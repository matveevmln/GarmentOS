## 0. Зачем — реальная потребность, а не гипотетическая функция

При проектировании `Contract Manufacturing` (Итерация 3, Фаза 0) `production_batches` были **сознательно исключены** из MVP: один заказ пошива моделировался как единая сущность (`production_orders` + `production_order_variants`), без отдельного отслеживания партий поставки — с явной пометкой «Future, если появится потребность» (`DATABASE_SCHEMA.md`, строка 270).

Эта потребность теперь названа владельцем проекта конкретно, на реальном сценарии аутсорс-производства: **цех присылает партию не всегда полностью и не всегда без брака, и последующая допоставка компенсирует именно этот брак — не является новым заказом**. Пример:

- Заказано 1000 изделий, оплачено 1000 по договору.
- Цех отгружает партию, фулфилмент принимает 900 — 100 признано браком.
- Через 1-2 недели цех присылает 100 изделий довшива.
- **Это не новый заказ и не новая партия к оплате** — это компенсация брака первой партии. Без отдельного механизма бухгалтер рискует либо оплатить эти 100 изделий второй раз, либо не заметить, что заказ по факту всё ещё не закрыт, потому что 100 изделий так и не были компенсированы.

Сегодня в системе для этого нет ни структуры данных, ни use case — `production_order_variants` фиксирует только план (заказанное количество по SKU), фактически принятое — read-model поверх `stock_movements` (`DATABASE_SCHEMA.md`, раздел 8), без понятия партии, брака или компенсации вообще.

## 1. Что это НЕ («не просто учёт брака»)

Владелец проекта явно расширил рамку дважды: сначала — «это не функция, а отдельный business-модуль», затем — «это не только защита от двойной оплаты, а весь жизненный цикл партии»: заказ → спецификация → крой → пошив → ОТК цеха → отправка → приёмка фулфилментом → брак → устранение (не только компенсация, раздел 6) → повторная отправка → закрытие партии → финансовая сверка.

```mermaid
flowchart LR
    A[Производственный заказ + спецификация] --> B[Партия создана]
    B --> C[Крой / Пошив]
    C --> D[ОТК цеха]
    D --> E[Отправка]
    E --> F[Приёмка фулфилментом]
    F --> G{Брак?}
    G -->|Нет| H[Партия закрыта]
    G -->|Да| R[Устранение:\nдошив / перешив /\nскидка / списание]
    R -->|дошив| I[Компенсационная партия]
    I --> F
    R -->|перешив/скидка/списание| H
    H --> J[Финансовая сверка]
```

Один `production_order` может породить **несколько** `production_batch` — исходную и одну или более компенсационных, связанных цепочкой (раздел 3). Брак одной партии может быть закрыт **несколькими способами одновременно** (раздел 6), не только дошивом.

## 2. Bounded context: `packages/domain/production-batch`

Новый доменный пакет — тот же шаблон `domain/application/infrastructure/index.ts`, что и во всех остальных 12. Владеет новыми таблицами (миграция потребуется):

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `production_batches` | `id`, `company_id`, `production_order_id` (FK), `batch_number` (последовательный в рамках заказа), `status` (`created/cutting/sewing/qc/shipped/received/closed`), `quantity_ordered`, `quantity_shipped NULL`, `quantity_accepted NULL`, `quantity_defective NULL`, `compensates_batch_id NULL` (FK на другую `production_batches` — раздел 3), `closed_at NULL` | Аггрегатный корень модуля — одна физическая поставка от цеха, не весь заказ целиком |
| `batch_defects` | `id`, `batch_id` (FK), `category` (свободный текст, раздел 5), `detection_stage` (свободный текст, раздел 5), `quantity`, `note NULL`, `recorded_by NULL`, `recorded_at` | Факт брака: сколько, что за брак, где выявлен |
| `batch_defect_resolutions` | `id`, `batch_defect_id` (FK), `resolution_type` (`compensation/rework/discount/write_off`), `quantity`, `compensation_batch_id NULL` (FK на `production_batches`, только при `resolution_type='compensation'`), `financial_impact_note NULL`, `recorded_at` | Как именно устранён брак — раздел 6. Одна запись `batch_defects` может иметь **несколько** resolutions (например, 100 брака: 50 дошито + 20 перешито + 30 списано) |

**Не дублирует** `production_orders`/`production_order_variants` (`contract-manufacturing`) — партия ссылается на заказ через FK, не копирует его данные. **Не дублирует** `stock_movements` — физическое движение остатков (приёмка на склад) по-прежнему пишется туда же (`type=receipt`, `reference_type='production_batch'` вместо сегодняшнего `'production_order'` — единственное изменение существующей схемы, обратная совместимость сохраняется, т.к. `reference_type`/`reference_id` уже полиморфны).

### 2.1. Use case'ы

| Use case | Что делает |
|---|---|
| `createBatch` | Создаёт партию по заказу — первая партия создаётся автоматически при подтверждении `production_order` (или явно пользователем/AI), последующие — только как компенсация (`compensatesBatchId` обязателен для 2-й и далее партии одного заказа, если не указано иное) |
| `recordShipment` | Цех сообщает об отправке (Telegram, `docs/AI_PRODUCTION_ASSISTANT_ARCHITECTURE.md`, сценарий 4, или ручной ввод) — фиксирует `quantity_shipped` |
| `recordAcceptance` | Фулфилмент подтверждает приёмку — `quantity_accepted`, пишет `stock_movements` (receipt) |
| `recordDefect` | Фиксирует `batch_defects` (категория + место выявления + количество, раздел 5) — `quantity_defective` партии = сумма записей брака |
| `resolveDefect` | Фиксирует `batch_defect_resolutions` — один или несколько способов устранения конкретной записи брака (раздел 6); **не позволяет** сумме количества resolutions по одному дефекту превысить количество самого дефекта |
| `createCompensationBatch` | Создаёт новую партию с `compensatesBatchId`, вызывается из `resolveDefect` при `resolution_type='compensation'` — предзаполняет количество из соответствующей resolution, **не позволяет** превысить объём непокрытого брака (инвариант, раздел 3) |
| `closeBatch` | Закрывает партию, когда весь `quantity_defective` покрыт resolutions (компенсацией и/или перешивом/скидкой/списанием) и `quantity_accepted + скомпенсировано == quantity_ordered` — иначе явная ошибка «партия не может быть закрыта, остаток N единиц не покрыт» |
| `reconcileBatchPayment` **(техническое имя — «Production Reconciliation», раздел 4)** | Проверяет, не создаётся ли платёж/счёт на количество, уже оплаченное в компенсируемой партии — раздел 4 |

## 3. Инвариант: цепочка компенсации

Ключевой доменный инвариант, ради которого создаётся весь модуль:

> **Компенсационная партия не может компенсировать больше брака, чем зафиксировано и ещё не покрыто (через уже существующие resolutions) в исходной партии.**

`compensatesBatchId` образует цепочку (партия №19 компенсирует №18, №20 могла бы компенсировать остаток №18 или брак №19 — обе валидны, поле указывает ровно одну родительскую партию). Через историю цепочки в любой момент можно восстановить: «почему заказ №25 закрылся на 3 недели позже, чем планировалось» (владелец проекта, «История компенсаций») — это уже read-model над `production_batches`/`compensates_batch_id`, не отдельная таблица.

## 4. Баланс партии и предотвращение повторной оплаты

**Баланс партии** — read-model, не отдельная таблица (тот же принцип, что маржа в Finance, `DATABASE_SCHEMA.md`, раздел 0b): `ordered / paid / produced / shipped / accepted / defective / compensated / remaining`.

**Баланс взаиморасчётов с цехом** — то же самое, агрегированное по всем партиям всех заказов этого цеха: сколько оплачено, сколько реально принято, сколько ещё должен цех (в виде дошива), сколько должны мы (если приняли больше оплаченного — переплата в другую сторону).

**Механизм предотвращения повторной оплаты (`reconcileBatchPayment`, техническое название процесса — Production Reconciliation)**: когда создаётся `cost_entries`/`invoices` строка типа «оплата пошива» (`Finance`, `docs/DATABASE_SCHEMA.md`, раздел 0b) со ссылкой на партию, use case проверяет `compensates_batch_id` — если партия компенсационная, ожидаемая сумма оплаты за пошив по умолчанию равна нулю (эти изделия уже оплачены в исходной партии), и попытка провести полную оплату **вызывает явное предупреждение** с точной формулировкой не хуже примера владельца проекта: *«Эти N изделий уже были оплачены в партии №X — повторная оплата не требуется»*.

**Открытый вопрос владельцу проекта (бизнес-правило, не архитектура — `CLAUDE.md`, раздел 6.8):** должно ли предупреждение **блокировать** проведение оплаты (жёсткий инвариант) или только **предупреждать**, оставляя решение бухгалтеру (например, компенсационная партия иногда всё же несёт частичные расходы — материал на замену, логистика)? Это решение кодирует бизнес-правило и не реализуется в коде до явного подтверждения.

## 5. Причины и место выявления брака

**Категория брака** (`batch_defects.category`) — свободный текст, не жёсткий enum (тот же принцип, что `documents.doc_type`: у каждой компании свой словарь, не диктуется системой), но модуль поставляется с **рекомендуемым стандартным набором** (заполняется по умолчанию в UI как подсказка, не ограничение): раскрой, пошив, ткань, фурнитура, загрязнение, неправильный размер, неправильная маркировка, повреждение при перевозке, брак выявлен фулфилментом, другое.

**Место выявления** (`batch_defects.detection_stage`) — тоже свободный текст с рекомендуемым набором, соответствующим реальному пути товара: цех (внутренний ОТК) → отправка/логистика → фулфилмент (приёмка) → маркетплейс/склад → возврат покупателя. Хранится **отдельно** от категории причины, потому что это разные измерения одного факта: «что не так» и «кто/где это заметил» — второе прямо определяет, чья это ответственность (брак кроя, найденный цехом до отправки, — не то же самое по последствиям, что тот же брак, обнаруженный только после жалобы покупателя на маркетплейсе).

Оба поля вместе дают аналитическую матрицу «категория × этап» (раздел 8) — не просто накопленный процент, а понимание, на каком этапе цепочки чаще всего теряется качество.

## 6. Способы устранения брака (не только компенсация)

`batch_defect_resolutions.resolution_type`:

| Тип | Что означает | Финансовое следствие |
|---|---|---|
| `compensation` | Цех дошивает недостающее количество бесплатно — создаёт `compensation_batch` (раздел 3) | Оплата пошива за эти единицы уже произведена в исходной партии — повторно не начисляется (раздел 4) |
| `rework` | Изделие исправляется (перешив) без создания новой партии поставки | Обычно бесплатно со стороны цеха (тот же принцип, что compensation) либо частично оплачивается — решается `financial_impact_note` + связанным `cost_entries`, если стоимость реально возникла |
| `discount` | Бренд соглашается принять товар с дефектом со скидкой, не возвращая его цеху | Уменьшение суммы, причитающейся цеху за эту партию, — конкретный use case скидки в `finance` не проектируется этим документом, только связь `financial_impact_note` |
| `write_off` | Товар списывается полностью (брак невозможно исправить или продать) | Влияет на себестоимость партии (раздел 8) — списанные единицы не попадают в остаток склада, `stock_movements` типа `adjustment` |

Одна запись брака может быть закрыта **несколькими resolutions одновременно** (пример владельца проекта: 100 единиц брака → 50 дошито + 20 перешито + 30 списано) — `batch_defect_resolutions` это многие-к-одному к `batch_defects`, сумма количеств resolutions не может превышать количество исходного дефекта (инвариант `resolveDefect`).

## 7. Медиа и переписка по партии — переиспользование существующей инфраструктуры

**Фото/видео/документы брака** — не новая подсистема. `batch_defects`/`production_batches` — обычные сущности для `document_links` (`entityType='batch_defect'`/`'production_batch'`), фото и видео — обычные `documents` (`DOCUMENT_ENGINE_ARCHITECTURE.md`, принцип 18 «полная связанность документов»). Ничего специфичного для брака проектировать не нужно — механизм уже спроектирован для любой сущности.

**История переписки по партии** (пример владельца проекта: цех «отправили» → мы «нашли 47 брака» + фото → цех «дошьём») — это Entity Timeline, уже спроектированный в `INBOX_ARCHITECTURE.md`, раздел 7.3, как read-model поверх `inbox_items`/`document_links` по `(entityType, entityId)`. Требуется одно дополнение: `inbox_items`, порождённые перепиской о конкретной партии (через Telegram-сценарий 4 `AI_PRODUCTION_ASSISTANT_ARCHITECTURE.md`), должны получать `entityType='production_batch'`/`entityId` — то же самое уже происходит для `production_order` (Итерация 7). Отдельного хранилища переписки этот модуль не создаёт.

## 8. Аналитика и KPI цеха — read-models, не новые таблицы

Тот же принцип, что маржа/себестоимость (`DATABASE_SCHEMA.md`, раздел 0b: «вычисляемая метрика... принадлежит модулю Reporting/BI, не доменной таблице»). Поверх `production_batches`/`batch_defects`/`batch_defect_resolutions`:

- **Процент брака по цеху** — текущая партия против среднего за последние N партий этого цеха (пример владельца проекта: «14% против обычных 3.2%» — сам по себе повод для предупреждения пользователю, не только пассивная цифра в отчёте).
- **Процент брака по модели / по ткани / по поставщику ткани** — связь `batch_defects` → `production_order` → `product`/`bom_items` → `material`/`supplier` (уже существующие связи, новых FK не требуется).
- **Матрица «категория брака × место выявления»** (раздел 5) — где именно в цепочке чаще всего теряется качество.
- **Среднее время дошива** — от `closed_at`/создания резолюции компенсируемой партии до `closed_at` компенсационной.
- **KPI-карточка цеха** (пример владельца проекта, витрина на карточке цеха): средний срок пошива, средний % брака, среднее время дошива, количество компенсаций за период, количество просроченных обязательств (раздел 9), средняя цена пошива.
- **Производственная память** на карточке модели («средний срок пошива за 18 партий — 7.3 дня, средний брак — 2.8%, лучший цех — Ак-Сарай») — витрина тех же read-model'ей, не новая инфраструктура.

Ничего из этого раздела не блокирует реализацию разделов 2-6 — аналитика строится поверх уже накопленных данных, реализуется по мере необходимости (`PRINCIPLES.md`, принцип 3), не одновременно с первой итерацией модуля.

## 9. Обязательства цеха

Read-model, не новая сущность с собственным жизненным циклом: **открытое обязательство** — это `batch_defects`, у которых `quantity` ещё не полностью покрыто суммой `batch_defect_resolutions.quantity`. «Просрочено» — если у соответствующей resolution (или у самой записи брака) указан ожидаемый срок устранения (`promised_by`, новое поле на `batch_defect_resolutions` для типа `compensation`/`rework`), и этот срок прошёл, а `compensation_batch` не создан/не закрыт.

Пример владельца проекта — на карточке цеха отображается: «Цех должен дошить 87 изделий, срок до 12 августа, статус: ожидается» — и подсвечивается, если срок нарушен. Это прямое чтение read-model'я «открытые обязательства», не отдельно хранимое состояние — обязательство закрывается автоматически, когда соответствующий `compensation_batch` закрыт (`closeBatch`, раздел 2.1), не отдельным действием пользователя.

## 10. История изменений партии — переиспользование `audit_log`

Не новый механизм. `packages/domain/audit` (Итерация 6) уже применяется ко всем критичным операциям других модулей (`AuditService.record(companyId, userId, source, {entityType, entityId, action, beforeJson, afterJson})`) — изменения `production_batches` (плановое количество, срок, цена пошива, цех, добавление resolution) записываются туда же, `entityType='production_batch'`. Пример владельца проекта («заказ был 1000 → изменили 1200 → перенесли срок → изменили цену → изменили цех → добавили компенсацию») — это последовательность строк `audit_log` с `before_json`/`after_json`, читаемая как таймлайн на карточке партии. Никакой отдельной таблицы «история изменений» не создаётся.

### 15. Спецификация как обязательная точка входа партии

Сейчас `apps/web` не имеет формы, физически называющейся «Спецификация» — есть «Заказ пошива» (`ProductionOrdersPage`), из которого спецификация генерируется как следствие. Предлагается:

- Переименовать пользовательский путь (не обязательно код): экран создания заказа пошива подаётся в интерфейсе как «Новая спецификация партии» — это и есть форма-мастер, поля 1:1 совпадают с уже существующими (модель, цех, цена пошива, срок, разбивка по SKU) плюс уже существующие поля цеха (условия оплаты, способ доставки, подписанты).
- **Технологическая карта модели** — не новая сущность: это уже существующий approved BOM (`boms`/`bom_items`), но с явным требованием (дисциплина заполнения, проверяется на уровне use case, не миграцией): approved BOM модели, из которой шьётся партия, должен содержать материалы **всех** категорий, которые реально расходуются — ткань (`fabric`), фурнитура (`trim`), упаковка (`packaging`), нитки/декор (`accessory`). Технически это уже так работает в демо-данных (раздел про Moda Love) — просто нужно закрепить как обязательное правило, а не как факультативную практику.
- Предпросмотр расчёта материалов (`checkMaterialAvailability`) должен стать отдельным переиспользуемым use case `previewMaterialRequirement(productId, bomId, totalQuantity)`, вызываемым и из AI-оркестрации (уже есть), и из формы Web UI **при каждом изменении количества** в ещё не подтверждённом черновике — то есть то самое «поменял количество — всё пересчиталось», без отдельного технического решения, только вызов уже существующей логики в новом месте.

### 16. Расчёт потребности в закупке (MRP-lite)

Новый use case в `procurement`, не новая таблица: `computeProcurementSuggestion(companyId, productId, bomId, totalQuantity)` →
для каждого `bomItem`: `требуется = totalQuantity × quantityPerUnit × (1 + wastePercent/100)`, `доступно = сумма material_stock_items.quantityOnHand по всем складам компании`, `к докупке = max(0, требуется − доступно)`. Для материалов, требующих докупки — предложение поставщика и цены **не выдумывается**, а берётся из истории (`purchase_order_items`, группировка по `material_id` + `supplier_id`, последняя по дате цена — тот же принцип, что уже описан для истории закупочных цен, `DATABASE_SCHEMA.md` раздел 0b), если материал раньше не закупался — явно сообщается «нет истории закупок, выберите поставщика вручную», не подбирается наугад.

Экран: «Что нужно купить под эту партию» — список материал/количество/рекомендуемый поставщик/цена/сумма, с кнопкой «Создать закупки» (создаёт черновики `purchase_orders`, сгруппированные по поставщику, из уже существующего `createPurchaseOrderDraft`).

### 17. Способ закупки: официально / наличными

Новое поле `purchase_orders.payment_channel` (enum: `official`/`cash`, nullable — не обязательно для уже существующих закупок). Чисто учётный признак — не меняет ни один существующий use case, только добавляется в форму создания закупки и в карточку. **Открытый вопрос владельцу** (раздел 25, п.3): нужна ли этому признаку своя логика (например, наличные закупки не попадают в НДС-отчётность) или это только пометка для собственного учёта на этом этапе.

### 18. Предоплата цеху и график оплаты партии

Новая, небольшая структура поверх уже существующих `invoices` (`finance`), не новый модуль:

- Новое поле `invoices.payment_stage` (enum: `prepayment`/`final`/`full`, по умолчанию `full` для обратной совместимости со всеми существующими счетами).
- Новый use case `createProductionPaymentSchedule(productionOrderId, prepaymentPercent)` — вызывается автоматически при подтверждении заказа пошива (`confirmProductionOrder`), создаёт **два** черновика `invoices` с `productionOrderId`: `prepayment` на `agreedUnitPrice × plannedQuantity × prepaymentPercent%` и `final` на остаток, `final` создаётся сразу, но логически «неактуален» до закрытия партии.
- `closeBatch` (раздел 2.1, уже спроектирован) при закрытии партии автоматически переводит `final`-счёт в `issued`, если он ещё в `draft` — «осталось оплатить 30%» появляется сам, без напоминания вручную, ровно как просил владелец проекта в пункте 13.
- **Открытый вопрос владельцу** (раздел 25, п.1): 70/30 — единое правило для всех цехов или настраиваемый процент в карточке цеха (`workshops.prepayment_percent`, по умолчанию 70)? Предлагаю второе — реалистичнее (разные цеха реально договариваются на разные условия), но это бизнес-правило, не архитектурное решение.

### 19. Результаты кроя по партии

Новая таблица `batch_cutting_results` (дочерняя `production_batches`, тот же паттерн, что `production_order_variants`): `id`, `batch_id` (FK), `product_variant_id` (FK), `quantity_cut`, `recorded_by`, `recorded_at`. Заполняется один раз при переходе партии в статус `cutting → sewing` (форма «Введите факт кроя по размерам» — 1:1 пример владельца проекта: S 150 / M 280 / L 320 / XL 250), хранится **отдельно** от планового количества (`production_order_variants.quantity`) и от фактически принятого фулфилментом (`production_batches.quantity_accepted`) — три разных числа на трёх разных этапах жизни партии, каждое имеет смысл (план → реальный крой → реально принято).

### 20. Статус партии: добавить «Упаковка», добавить процент выполнения

Уточнение enum `production_batches.status` (раздел 2 этого документа): `created → cutting → sewing → packing → shipped → received → closed` (было: без `packing`). Плюс новое необязательное поле `production_batches.progress_percent` (0-100, обновляется цехом вручную или через будущую Telegram-интеграцию, раздел 11) — витрина «в работе, 65%» на карточке партии, ничего не блокирует и не пересчитывается автоматически (честная ручная отметка, не наукообразная оценка).

### 21. Фулфилмент-центр как партнёр, а не просто склад

Новая сущность `fulfillment_centers` — по образцу `workshops`/`suppliers` (карточка, контакты, договор, документы через `document_links`), а не безликий склад: `id`, `company_id`, `name`, `contact_info`, `contract_number`/`contract_date`, `status` (`partnerStatusEnum`, переиспользуется). `warehouses.type` получает новое значение `'fulfillment'` (по аналогии с уже существующим `'workshop'`) + новое поле `warehouses.fulfillment_center_id` (FK, обязателен при `type='fulfillment'`, запрещён иначе — точно тот же инвариант `assertWorkshopIdConsistency`, что уже есть для цехов, раздел 2 `DATABASE_SCHEMA.md`).

### 22. Логистика Red Express — точечное расширение `shipments`

Модель уже подходит почти полностью: `shipments.carrierId` уже сегодня может указывать на поставщика с `type='logistics'` (Red Express заводится как обычный поставщик), `trackingNumber`/`status` уже есть. Не хватает одного: `invoices.shipment_id` (новый nullable FK, четвёртая ссылка рядом с уже существующими `order_id`/`purchase_order_id`/`production_order_id`) — чтобы счёт за перевозку жил в той же модели `invoices`, что и остальные счета (статус/оплата/просрочка — бесплатно, без нового модуля).

### 23. Кросс-граничный документооборот (бухгалтер КР → бухгалтер РФ)

Не новая архитектура — это ровно тот сценарий, ради которого уже спроектирован (но не реализован) `docs/WORKFLOW_ENGINE_ARCHITECTURE.md` («узкоспециализированный механизм многошагового согласования документов», не общий BPMN-движок). Пример владельца проекта («бухгалтер Кыргызстана готовит документы, бухгалтер РФ их проверяет») — конкретное подтверждение, что этот модуль нужен реально, не гипотетически. Предлагаю: первый реальный workflow этого движка — «Документы отгрузки партии» (`entityType='production_batch'`, шаг 1: подготовка бухгалтером КР, шаг 2: проверка бухгалтером РФ), не абстрактный конструктор произвольных workflow с нуля.

### 24. Полная связанность — что должны показывать карточки сущностей

Это не пробел в данных (все нужные связи — FK и `document_links`/`audit_log`, уже существующие или добавленные разделами выше) — это объём экранов `apps/web`, которого сейчас физически нет ни для одной сущности. Каждая карточка ниже — Entity Timeline поверх уже существующих связей (`INBOX_ARCHITECTURE.md`, раздел 7.3), не новая инфраструктура:

| Карточка | Что должна показывать |
|---|---|
| Модель | Все партии (всех заказов), все BOM/версии, весь брак по этой модели, все продажи, вся себестоимость, документы, «производственная память» (раздел 8 этого документа) |
| Материал | Все закупки, история цены по поставщикам, все партии/BOM, где расходовался (через `material_stock_movements.reference_type='production_batch'`) |
| Поставщик | Все закупки, вся история цен, все документы (`document_links`), партии, где использовалась его ткань (через материал → BOM → партию) |
| Цех | Все заказы/партии, весь брак, все обязательства (раздел 9), KPI (раздел 8), договор и документы |
| Партия | Вся жизнь: спецификация → крой → пошив → упаковка → отправка → приёмка → брак → устранение → оплата (предоплата/остаток) → логистика (Red Express) → документы — единая лента, не набор вкладок с разными данными |

Это отдельный, самостоятельный кусок работы для `apps/web` (после того как данные для этого появятся) — не блокирует раздел 2-13, реализуется по мере готовности разделов 15-23.

## 25. Открытые бизнес-правила — решает владелец проекта, не архитектура

1. **Предоплата 70/30** (раздел 18) — единое правило для всех цехов или процент настраивается в карточке каждого цеха?
2. **Повторная оплата компенсационной партии** (раздел 4, уже был открытым вопросом до этого дополнения) — блокировать проведение оплаты жёстко или только предупреждать?
3. **Официально/наличными** (раздел 17) — нужна ли этому признаку какая-то дальнейшая логика (отчётность, НДС) или это только пометка в интерфейсе на этом этапе?
4. **Фулфилмент-центр** (раздел 21) — сейчас закладываю поддержку нескольких (тот же принцип, что и цехов/поставщиков), но по факту у компании он один (Москва) — подтвердите, что не нужно с самого начала проектировать более сложные правила распределения между несколькими фулфилмент-центрами.
5. **Workflow-согласование документов** (раздел 23) — первый реальный workflow это «документы отгрузки партии, КР → РФ» — верно ли, что это ровно два шага (подготовка → проверка), или в реальности шагов больше (например, ещё и подпись/утверждение самим владельцем)?

## 26. Snapshot партии — реализовано (2026-08-03)

В отличие от разделов 1-24 (архитектура, ждёт утверждения), этот раздел документирует **уже реализованный и протестированный** механизм — прямое следствие требования владельца проекта: *«Если система каждый раз будет пересчитывать старые партии по новым ценам, то произойдёт катастрофа»*.

### 26.1 Принцип

Карточка модели (`products`, будущий `PRODUCT_MODEL_ARCHITECTURE.md`) хранит только **нормативы**: BOM, нормы расхода, стандартную стоимость пошива. Она никогда не хранит фактическую себестоимость конкретной партии — та зависит от цен материалов на момент размещения заказа, а цены меняются.

При **подтверждении** заказа пошива (`draft → placed`, ключевой бизнес-момент — деньги ещё не потрачены, но обязательство перед цехом уже фиксируется) система:

1. Считает себестоимость по **текущим** закупочным ценам (`CostingService.computeSpecificationPricing` — уже существовал для экрана «Расчёт стоимости спецификации», теперь переиспользован).
2. Забирает из карточки цеха условия оплаты, реквизиты договора, подписантов — те, что действуют **сейчас**.
3. Замораживает всё это одним JSON-объектом (`production_orders.cost_snapshot`, миграция `0017`) — `ProductionOrderCostSnapshot` (`packages/shared-types`).

После этого момента снимок **не пересчитывается никогда** — ни при повторной генерации спецификации через месяц, ни если цех сменит условия оплаты, ни если цена ткани у поставщика вырастет, ни если BOM модели изменится. Спецификация (и в будущем — любой документ по этой партии) читает данные из снимка, не из живых карточек модели/цеха/материалов.

### 26.2 Основание генерации (реализована часть раздела 5 из промпта владельца проекта)

Подтверждение проверяет **до** перевода статуса (не после — иначе при отказе заказ навсегда остаётся «подтверждён», но без снимка):

- у цеха указан номер договора (`WORKSHOP_CONTRACT_NUMBER_MISSING`, иначе спецификация физически не может называться «...к договору № ___»);
- у модели есть утверждённый BOM (уже проверялось при создании черновика заказа, `assertBomIsApproved`; `CostingService` проверяет повторно при расчёте себестоимости).

Не реализовано (сознательно, не входило в эту итерацию): проверка «выбраны ли поставщики», «указаны ли нормы расхода» отдельно от approved BOM — сейчас approved BOM уже подразумевает наличие норм расхода на каждый материал (иначе BOM не прошёл бы валидацию при утверждении).

### 26.3 Обратная совместимость

Заказы, подтверждённые до появления этого механизма, имеют `cost_snapshot = null`. Для них `generateAndSendSpecification` использует прежнее поведение — считает вживую из карточки цеха/компании на момент генерации. Это единственное место, где старое поведение сохраняется намеренно, а не баг.

### 26.4 Именование: «Партия»

Отдельной сущности `ProductionBatch` для этого механизма не создано — `production_orders` уже полностью соответствует бизнес-понятию «партия» (заказ на пошив конкретного объёма у конкретного цеха), задел под дробление одного заказа на несколько партий поставки остаётся в разделах 1-13 (не пересекается с этим разделом). Термин «партия»/«Паспорт партии» — как предложил владелец проекта — используется в интерфейсе и разговоре с пользователем; в коде/схеме остаётся `productionOrder` (не переименовано — глоссарий `CLAUDE.md` уже фиксирует этот термин, массовое переименование ради синонима не оправдано).

### 26.5 Что дальше (не реализовано в этой итерации)

- **UI «Паспорт партии»** — экран с себестоимостью, суммой партии, чек-листом закупок (что есть на складе/чего не хватает/уже заказано — MRP-lite, раздел 16), графиком оплат (70/30), в будущем — маржой по каналам продаж. Backend для первого блока (себестоимость) уже есть: `GET /production-orders/:id` возвращает `costSnapshot` целиком.
- **MRP-lite чек-лист закупок** — раздел 16 этого документа, спроектирован, не реализован.
- **Document Engine — техническая архитектура генерации** (где генерируется PDF, очередь, Railway): не отдельный вопрос для этого документа — см. `docs/DOCUMENT_ENGINE_ARCHITECTURE.md`, раздел добавлен туда же (26.6 там же, ниже сводка решения).

### 26.6 Document Engine — технические решения (сводка; полный текст в `DOCUMENT_ENGINE_ARCHITECTURE.md`)

Владелец проекта явно попросил самостоятельно спроектировать техническую архитектуру генерации (где, чем, очередь, хранение), а не просто добавить UI. Решения — с обоснованием:

- **Где генерируется PDF**: в том же процессе NestJS API (`apps/api`), синхронно по HTTP-запросу — не отдельный сервис/микросервис. `pdf-lib` не требует headless-браузера (в отличие от Puppeteer/Playwright), генерация одной спецификации — десятки миллисекунд, не секунды. Отдельный сервис добавил бы сетевой хоп, отдельный деплой на Railway, отдельную точку отказа — ради задачи, которая не упирается в производительность на масштабе одного бренда-селлера (не 500 партий/день, а единицы в день).
- **Очередь задач**: не нужна на этом масштабе. Если/когда генерация документов станет узким местом (десятки одновременных запросов) — добавить BullMQ поверх уже используемого Redis (`docs/TECH_STACK.md`), не раньше.
- **Хранение PDF**: уже реализовано и cloud-agnostic — S3-совместимое хранилище через `document.module.ts`, с fallback на локальный диск, если `S3_ENDPOINT` не задан (используется в разработке). Соответствует «Start Lean, Scale Smart» (`docs/INFRASTRUCTURE.md`) — тот же код работает на Railway (Railway Volume или внешний S3-совместимый провайдер) без изменений.
- **Версионность**: уже реализована — `documents.supersedesDocumentId`/`isCurrentVersion` (Immutable Original, `docs/PRINCIPLES.md`, принцип 19). Новая генерация спецификации не перезаписывает старую — создаёт новую строку, старая остаётся доступной навсегда.
- **Универсальность на будущее (договоры/счета/акты/УПД)**: структура уже разделена на `SpecificationTemplateDefinition` (структура документа) и `SpecificationDocumentData` (значения) — `packages/domain/document`. Сегодня это работает только для одного типа документа (`renderSpecification`); превращение в полностью универсальный движок для произвольных типов документов — отдельная задача, **не сделана в этой итерации** (сознательно, чтобы не плодить абстракцию под несуществующие пока типы документов — `docs/PRINCIPLES.md`, принцип 3, эволюционная архитектура). Когда появится второй реальный тип документа (например, акт приёмки партии), обобщение будет вынесено на основе двух настоящих примеров, а не одного воображаемого.

Код по разделам 14-24 **не пишется до ответа на эти вопросы и до общего подтверждения этого дополнения** — то же правило, что и для разделов 1-13 этого документа (см. статус в начале файла).
