# ADR 0001 — Синхронная оркестровка внутри монолита сейчас, доменные события — путь на будущее, не задача сейчас

**Статус**: принято владельцем проекта, 2026-08-02.

## Контекст

`docs/ARCHITECTURE.md` (п.3, п.4.1) описывал сквозной сценарий продажи как событийный: `Sales` резервирует остаток → `Warehouse` публикует событие `StockReserved` → на него подписаны `HonestSign` и `Finance`. Это было явно помечено как открытый риск ещё на Фазе 0 (`docs/ARCHITECTURE_SELF_REVIEW.md`, пп. 2.2-2.3: «должно быть решено до реализации Sales/Warehouse... это пробел, который нужно закрыть ADR перед реализацией Sales»).

Архитектурная ревизия 2026-08-02 (`docs/ARCHITECTURE_REVIEW.md`, находка 2.1) обнаружила, что этот риск так и не был закрыт: `SalesService` реализован, но не вызывает ни `WarehouseService`, ни `HonestSignService`, ни `FinanceService`; в кодовой базе нет ни одного `EventEmitter`/доменного события/подписчика вообще. При этом ровно та же по сути задача — «операция одного модуля должна вызвать другой» — уже дважды решена в системе прямым синхронным вызовом через DI (`ProcurementService`/`ContractManufacturingService` → `WarehouseService`, внутри одной БД-транзакции), без какой-либо шины.

Первая версия ревизии предлагала явно отказаться от идеи событийной шины. Владелец проекта скорректировал это предложение: не отказываться от событийной архитектуры как направления, а явно развести «что реализуем сейчас» и «что остаётся путём на будущее».

## Рассмотренные варианты

1. **Реализовать полноценную event bus сейчас** (in-process `EventEmitter`, доменные события, подписчики в каждом заинтересованном модуле). Отклонено: для одной БД, одного процесса, двух пользователей это чистое усложнение без выгоды — усложняет отладку сквозного сценария (принцип 11, наблюдаемость), не даёт ничего взамен на этом масштабе.
2. **Прямой синхронный вызов через DI внутри одной транзакции, без оглядки на будущее** (буквально удалить упоминание событий из документации). Отклонено владельцем проекта — теряет прослеживаемость решения: через год кто-то читающий код может не понять, что переход на события — обдуманный, отложенный, а не забытый путь.
3. **Прямой синхронный вызов сейчас, спроектированный так, чтобы стать публикацией события позже без переписывания бизнес-логики** — принято.

## Решение

Для MVP и первых месяцев эксплуатации **не реализуем событийную шину**. Сквозные сценарии, требующие вызова другого модуля (продажа → резерв остатка → гашение кода маркировки → финансовая проводка), выполняются **синхронно, внутри одной БД-транзакции**, через прямой вызов application service вызываемого модуля — тот же паттерн, что уже работает и покрыт e2e-тестами для `Procurement → Warehouse` и `Contract Manufacturing → Warehouse`.

Обязательное условие: доменный слой каждого вызывающего модуля не должен жёстко полагаться на то, что вызов синхронный. Практически это означает:
- Оркестровка живёт в **application-слое** (`apps/api/src/*/​*.service.ts`), не в доменной бизнес-логике (`packages/domain/*`) — домен модуля-владельца ничего не знает о том, кто и как его вызывает (уже так спроектировано, `docs/ARCHITECTURE.md` п.2, Dependency Inversion).
- Вызывающий сервис работает через **интерфейс** вызываемого модуля (его application service/DI-токен), не через его репозиторий/таблицы напрямую — уже обязательное правило (`docs/PRINCIPLES.md`, принцип 2).
- Результат вызова обрабатывается так, будто он мог быть асинхронным (нет предположений вида «вызов гарантированно завершился до следующей строки без обработки ошибки») — обычная транзакционная дисциплина, не специальный механизм.

При выполнении этих условий переход от:
```
Sales → Warehouse → HonestSign → Finance   (последовательные вызовы, одна транзакция)
```
к:
```
Sales → Domain Event → Warehouse → Domain Event → Finance   (публикация события, in-process bus или очередь)
```
— это замена *реализации вызова* (Infrastructure-слой), а не переписывание бизнес-правил внутри `Sales`/`Warehouse`/`HonestSign`/`Finance`. Условие перехода — не календарная дата, а сигнал: конкретный модуль стал узким местом, или потребовалось несколько независимых подписчиков на одно событие, или модуль выделяется в отдельный сервис (`docs/ARCHITECTURE.md`, п.10 «Путь к масштабированию» — тот же принцип, применённый предметно к этому случаю).

## Последствия

- `docs/ARCHITECTURE.md`, п.3 и п.4.1 — обновить: диаграмма сценария продажи описывает прямой вызов (как уже реализовано для закупок/заказов пошива), не гипотетическое событие `StockReserved`, которого не существует в коде. Формулировка «домен готов к будущей замене на события» — сохраняется как явное архитектурное требование к оркестрации, не удаляется.
- `docs/ARCHITECTURE_SELF_REVIEW.md`, пп. 2.2-2.3 — отметить закрытыми этим ADR.
- Реализация `Sales`-оркестровки (когда экран продаж/маркетплейса дойдёт до `apps/web`) следует этому ADR с первого дня — не откладывать оркестровку до появления события «стало сложно», а сразу писать вызывающий код так, будто интерфейс вызываемого сервиса может однажды стать асинхронным.
- Не пересматривается без нового ADR (`CLAUDE.md`, раздел 6, пункт 3).
