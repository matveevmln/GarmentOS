# ADR 0002 — Заказ на пошив: общая шапка над партиями по моделям

**Статус**: принято для реализации T01, 2026-09-24. Основание: `docs/GOS-PARTY-V1.md`, `docs/GOS-PARTY-V1-SCREEN-CONTRACT.md` (A02/A03/B01), `docs/GOS-PARTY-V1-REVIEW.md` (R01/R02/R05/R07), `docs/GOS-PARTY-V1-AUDIT.md` (раздел 13/18), `docs/GOS-PARTY-V1-TRANSITION-REVIEW.md`, `docs/GOS-PARTY-V1-EXECUTION.md`, `docs/tasks/T01.md`.

## Контекст

Владелец заказывает пошив у цеха одним заказом, который может содержать несколько моделей одновременно («+ Добавить модель в заказ»). В текущей схеме `production_orders` — это партия ровно одной модели у одного цеха; общей сущности «заказ» с несколькими моделями нет. Аудит T00 (раздел 13) уже исследовал варианты и рекомендовал добавить одну новую таблицу-шапку, не трогая существующую партию. Эта работа была документацией; T01 — первая кодовая реализация.

Дополнительно `docs/GOS-PARTY-V1-TRANSITION-REVIEW.md` поставил перед этим ADR восемь конкретных вопросов (черновик/размещение, идемпотентность, backfill старых данных, откат, legacy-совместимость shipments и т.д.). Ниже — решения по каждому применимому к T01 пункту; пункты про shipments/компенсации вне T01 (относятся к T05a-c).

## Рассмотренные варианты

1. **Несколько независимых `production_orders` одним нажатием, без общей сущности.** Отклонено ранее в аудите (раздел 13.6): нет общего штаба, нет постоянной связи партий друг с другом, «Заказ» существует только как временное состояние экрана, исчезающее после перезагрузки — противоречит A02/B01 напрямую.
2. **Перенести `product_id` из `production_orders` в новую таблицу позиций, партия становится многомодельной сама по себе.** Отклонено: затрагивает раскрой, приёмку, ОТК, брак, стоимость, паспорт партии — несоразмерный объём изменений для T01, риск регрессии во всём, что уже работает.
3. **Использовать `specifications` как шапку.** Отклонено: это коммерческий документ с собственным жизненным циклом (утверждение, версия PDF), контракт (E02) требует, чтобы спецификация ссылалась на заказ, а не была им; на T01 спецификаций может не быть вовсе.
4. **Новая таблица `sewing_orders` — шапка над существующими `production_orders`-партиями, без изменения их формы.** Принято.

## Решение

### Схема (миграция M1, аддитивная)

```
sewing_order_status: enum('draft', 'placed', 'cancelled')

sewing_orders
  id                  uuid PK
  company_id          uuid NOT NULL REFERENCES companies(id)
  workshop_id         uuid NULL REFERENCES workshops(id)          -- пусто только в draft
  number              integer NULL                                 -- выдаётся при place
  status              sewing_order_status NOT NULL DEFAULT 'draft'
  draft_payload       jsonb NULL                                   -- снимок формы A02
  version             integer NOT NULL DEFAULT 1                    -- защита от гонки автосейва
  client_request_id   text NULL                                    -- идемпотентность place
  created_by          uuid NULL REFERENCES users(id)
  created_at, updated_at

  UNIQUE (company_id, number) WHERE number IS NOT NULL
  UNIQUE (company_id, client_request_id) WHERE client_request_id IS NOT NULL

production_orders.sewing_order_id  uuid NULL REFERENCES sewing_orders(id)
  INDEX (sewing_order_id)
  UNIQUE (sewing_order_id, product_id) WHERE sewing_order_id IS NOT NULL  -- одна партия на модель в заказе

companies.next_sewing_order_number integer NOT NULL DEFAULT 1  -- атомарный счётчик, тот же паттерн, что next_production_order_number
```

`draft_payload` хранит форму целиком (цех, повторяемые блоки моделей: `productId`, режим распределения, введённые цвета/количества/проценты или ручные ячейки) — не localStorage, переживает смену устройства и вкладки. Черновик допускает неполные данные (нет цеха, нет ни одной модели, нулевые количества) — это ровно то, зачем нужен отдельный jsonb-снимок, а не запись сразу в `production_orders` (там `workshop_id`/`bom_id`/`agreed_unit_price` — NOT NULL).

Связь `production_orders.sewing_order_id` постоянная: API «перенести партию в другой заказ» не создаётся. `product_id` не может повториться в рамках одного `sewing_order_id` — то есть заказ не может содержать модель дважды скрытно (A02: «один и тот же SKU не дублировать скрытно» относится к SKU внутри модели; на уровне заказа это правило — про модель целиком).

### Атомарное размещение — что именно происходит при одном нажатии «Создать заказ»

Это прямой ответ на TRANSITION-REVIEW, пункт 1 («одно пользовательское действие не должно требовать серии подтверждений»). Новый use case `placeSewingOrder` выполняется в одной `db.transaction` (тот же паттерн, что `IdentityService.bootstrapCompany`, `packages/domain/identity`):

1. `SELECT ... FOR UPDATE` шапки по `(companyId, sewingOrderId)`.
2. Если шапка уже `placed` **и** `client_request_id` совпадает с переданным — вернуть её текущее состояние без повторной записи (идемпотентный повтор). Если `placed`, а ключ другой — конфликт 409 (иной ключ не создаёт вторую группу партий). Если шапка не найдена — 404. Если уже `cancelled` — конфликт 409.
3. Проверка: цех принадлежит компании; хотя бы одна модель; для каждой модели — сама модель и все её `productVariantId`, участвующие в матрице, принадлежат компании (переиспользуется существующая проверка `CatalogService.findProductVariantById`, тот же принцип, что уже применён в SEC-P1 для склада).
4. Для каждой модели: если пришли проценты — сервер **сам** пересчитывает ячейки через новую чистую функцию `distributeQuantityByPercent` (не доверяет присланным итогам, см. ниже), если пришли ручные ячейки — использует их как есть, но суммы всё равно проверяются `assertVariantsMatchPlannedQuantity`. Затем — существующий `createProductionOrderDraft` с репозиториями на `tx` и `bomApproval.ensureApprovedBomForProduct` на `tx` (материалы не требуются — если у модели ещё нет утверждённого BOM, заводится пустой, как и в существующих ручных путях). Партия получает `sewing_order_id` и **сразу переводится в `placed`** тем же вызовом `updateStatus`, что использует `confirmProductionOrder`, но на репозитории, созданном на `tx`, — то есть create+confirm происходят как один шаг транзакции, не два отдельных пользовательских действия. `costSnapshot` в T01 не фиксируется (это отдельное действие «Подтвердить партию» существующего экрана паспорта, которое собирает актуальные цены материалов — не относится к первому размещению без материалов).
5. Атомарно резервируется номер заказа (`companies.next_sewing_order_number`, тот же UPDATE...RETURNING паттерн, что `reserveNextSpecificationNumber`/`reserveNextProductionOrderNumber`), шапка получает `status='placed'`, сохранённый `draft_payload` не удаляется (история того, что ввёл пользователь).
6. Любая ошибка на любом шаге — откат целиком; частичного заказа (например, одна партия создана, вторая нет) быть не может.

Партии сразу видны в паспорте партии (`/production-orders/:id`, статус `placed`) и сразу проходят guard следующего шага (раскрой и т.д.) — не «черновик, который надо ещё раз подтвердить». Прецедент такого поведения уже есть в кодовой базе: `createProductionOrderFromSpecification` создаёт партию сразу в `placed` одним вызовом, минуя отдельное подтверждение, именно потому что вызывающая композитная операция сама гарантирует согласованность данных.

### Черновик и автосохранение

`PATCH /sewing-orders/:id` принимает `draft_payload` и ожидаемый `version`. Сервер обновляет только если текущий `version` совпадает; иначе — 409 (конфликт двух вкладок/устройств, TRANSITION-REVIEW пункт 2). При успехе `version` увеличивается на 1. Поздний ответ автосохранения, отправленный ДО размещения, но дошедший ПОСЛЕ (`status` уже `placed`) — тоже 409: PATCH черновика разрешён только для `status='draft'`.

### Распределение по размерам — два режима, один источник числа (R02)

- **Шаблон**: пользователь вводит количество по цвету и проценты по размеру (пример: 12,5/25/25/25/12,5 → 600 даёт 75/150/150/150/75, 400 даёт 50/100/100/100/50). Проценты должны в сумме давать 100% — новая функция `distributeQuantityByPercent` (`packages/domain/catalog`, рядом с `distributeQuantityByRatio`) проверяет это явно и **пересчитывает ячейки на сервере** тем же методом наибольших остатков, что уже используют `distributeQuantityByRatio`/`distributeQuantityBySize` (общий алгоритм внутри пакета, тай-брейк по возрастанию индекса размера). Клиент дублирует тот же алгоритм в TypeScript для мгновенной обратной связи при вводе (apps/web не зависит от доменных пакетов — граница уже такая для всего проекта), но окончательные числа, которые попадают в `production_order_variants`, — только серверные.
- **Вручную**: пользователь редактирует ячейки напрямую; итог цвета и заказа — сумма ячеек, вычисляется и показывается, не редактируется отдельно. Смена режима не пересчитывает уже введённые значения молча (сохраняются, пока пользователь явно не применит другой режим).
- «Сохранить шаблон» (именованный переиспользуемый набор процентов) — из A02, в T01 **не реализуется**: это отдельная небольшая фича поверх готового механизма процентов, не нужна для первого заказа и не входит в перечисленные в T01 критерии приёмки. Оставлено в `docs/MASTER_BACKLOG.md`-подобной заметке ниже, не блокирует остальное.

### Backfill старых партий (M2, НЕ выполняется в этом PR)

`production_orders.sewing_order_id` остаётся NULL для всех существующих партий после M1. UI считает `NULL` «одиночной партией прежнего пути» и показывает её как заказ из одной модели (совместимость, TRANSITION-REVIEW пункт 5). M2 (перенос старых партий 1:1 в синтетические шапки) — отдельная задача с резервной копией и разрешением владельца, не входит в T01. `production_orders.sewing_order_id` остаётся NULLABLE до отдельного решения M3.

### Откат

M1 аддитивна: откат — `DROP` новой таблицы/колонки/enum, данные существующих `production_orders` не меняются. Это допустимо ровно потому, что до M2 никакая рабочая партия не ссылается на `sewing_orders` — после M2 в production `DROP` перестаёт быть безопасным откатом (TRANSITION-REVIEW пункт 6), тогда откатом станет исправляющая миграция. Всё это применяется только к тестовой БД в рамках T01.

## Терминология (обновление глоссария CLAUDE.md)

| Русский термин | Код | Пояснение |
|---|---|---|
| Заказ на пошив | `sewingOrder` | Общая шапка над одной или несколькими партиями по моделям у одного цеха; собственный статус `draft/placed/cancelled` |

## Последствия

- Существующие экраны (`ProductionOrdersPage`, `BatchPassportPage`, паспорт партии, крой, ОТК, приёмка) не меняются — они продолжают работать с `production_orders` напрямую, как раньше.
- Новый путь создания заказа (`/sewing-orders/new`) становится основным в навигации; `/new-batch` и прямое `POST /production-orders` остаются доступны по прямой ссылке (тот же приём, что уже применён к «Новой партии» и «Цехам» ранее, `apps/web/src/layout/AppShell.tsx`).
- `costSnapshot`/подтверждение партии как отдельное действие сохраняется для случаев, когда партия создаётся НЕ через шапку (старый путь) — не убирается из паспорта партии.
- Требуется отдельная сверка (T05a-c) для `shipments`/компенсаций, чтобы они тоже ссылались на партию/заказ — не делается в этом ADR.
