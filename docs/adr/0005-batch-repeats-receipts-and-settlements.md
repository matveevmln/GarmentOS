# ADR 0005 — повтор партии, исправление приёмки и расчёты

Дата: 2026-10-10. Статус: реализовано по запросу владельца; результаты проверок — в `BATCH_OPERATIONS_VERIFICATION.md`.

## Рабочий сценарий

Маленький селлер работает с одним цехом Ак Сарай и обычно получает партию целиком. Повторный заказ должен использовать прошлый размерный состав без повторного заполнения. Ошибочный подсчёт и ошибочная запись платежа должны исправляться с историей. Этап пошива и расчёты с цехом независимы.

## Решение

### Повтор

«Повторить партию» открывает существующий мастер сразу на количестве. Переносятся модель, цвета, плановые количества по размерам и прежняя согласованная цена. Пользователь проверяет условия; прошлый срок не копируется. Единственный активный цех подставляется автоматически. Новая партия имеет отдельный UUID и номер; исходный заказ, спецификация и история не меняются.

Модель должна быть активна, варианты доступны. Разные цены по строкам и строки переделки не приводятся молча к одной цене: мастер объясняет ограничение и предлагает новый заказ модели. Незавершённый повтор хранится отдельно от обычного ввода; неизвестный результат отправленного обычного запроса нельзя заменить новым.

### Приёмка

Миграция 0035 добавляет журнал `receipt_corrections`, а не заменяет `production_orders`. При исправлении передаются UUID запроса, причина, ожидаемые прежние факты и новые целые количества по каждому SKU. Сервер проверяет компанию, право отката, неизменность прежних фактов и единственность строк. Повтор того же запроса возвращает результат; тот же UUID с другим содержимым отклоняется.

Под общей блокировкой партии одна транзакция записывает исправление, меняет фактические количества, добавляет знаковые движения `adjustment` и меняет остаток только на разницу. Исходные приходные движения сохраняются. Место первоначальной приёмки определяется из аудита; отсутствующий источник не угадывается. Нельзя уменьшить остаток ниже резерва. Ошибка одного SKU откатывает все строки. Изменение закрытой партии возвращает её в «Принято» для проверки.

**Ограничение:** при уже записанном ОТК или браке отдельное исправление приёмки запрещено. Для изменения этих фактов нужен согласованный сценарий исправления качества и связанных операций; он этим выпуском не реализован. Интерфейс объясняет причину. Исправление не стирает план, не возвращает деньги и не меняет сумму договорённости автоматически.

### Деньги

Журнал `batch_payments` связан с существующими `transactions`. Действительная оплата/возврат создаёт обе записи и аудит атомарно. У каждой операции явные направление, валюта RUB, сумма до копеек, автор, время и UUID для безопасного повтора. Расчёт производится в целых копейках.

«Исправить запись» добавляет противоположную операцию с `reversal_of_id`; оригинал остаётся, повторная отмена оригинала запрещена. Возврат ограничен записанной чистой оплатой. Если платёж уже частично возвращён, для отмены его учётного влияния сначала требуется проверить возврат. Это учёт уже совершённых действий, кнопки не переводят деньги.

Для черновика показывается плановая сумма; остаток оплаты не подтверждён и запись платежей недоступна до размещения.

Согласовано = сумма плановых платных строк; переделка бесплатна. Записано оплаты = оплаты минус возвраты с учётом исправлений. Осталось = максимум согласованного минус чистая оплата и нуля. Переплата видна отдельно. Недостача изделий не означает автоматическую скидку.

Старые транзакции без указанной валюты и старые отметки оплаченных счетов не объявляются подтверждёнными рублёвыми платежами. При наличии таких записей остаток «Не сверено»; требуется сверка, без повторного внесения тех же денег. После отмены партии старый аванс сохраняется, новая оплата запрещена, возврат и исправление записи доступны. Итоговые обязательства при отмене не предполагаются: остаток неизвестен до отдельного соглашения с цехом.

### Потеря связи

Веб-клиент сохраняет неизменный запрос до отправки. При сетевой ошибке или 5xx пользователь может только проверить/повторить этот же запрос с тем же UUID. Запрос восстанавливается после перезагрузки и входа того же пользователя; ключ включает компанию, пользователя и партию. Однозначный отказ бизнес-валидации позволяет исправить форму. Ошибки сессии/прав, отсутствующий endpoint и временные отказы (401/403/404/408/429) сохраняют прежний UUID: они не доказывают, что более ранняя отправка не была проведена. Локальное хранение не заменяет серверный журнал.

## Архитектура и границы

Модульный монолит сохранён: общие Zod-контракты в `shared-types`, правила в существующих доменных пакетах, оркестрация и права в API, PostgreSQL как источник фактов, интерфейс в текущем паспорте. Миграция только добавляет две таблицы и ограничения. История фактов не удаляется каскадом. Проверка целостности сопоставляет текущую приёмку с исходным приходом плюс журналом поправок.

Нет новых платёжных провайдеров, банковских переводов, изменения суммы соглашения, исправления ОТК/отгрузок и синхронизации незавершённых форм между устройствами. Эти возможности не следует выдавать за реализованные.


## Совместимость с прежним восстановлением прав

Старый deploy восстановил право отмены и стандартные разрешения вне журнала Drizzle. Перед обычными миграциями точечная сверка проверяет исходный hash и время предыдущей 0033, одно право с правильным модулем и полный набор грантов owner/director. Историческая рабочая база хранит hash SQL с переносами CRLF; Linux-сборка использует LF. Допустимы только эти два формата того же исходного SQL (без изменения текста или обрезки пробелов). Hash прежней записи сохраняется. Только при совпадении всех постусловий добавляется исходный hash/время 0034 в журнал; право, его ID и разрешения не пересоздаются. Более ранняя, повреждённая или неполная история останавливает сверку. Следующая миграция 0035 по-прежнему применяется обычным migrator. Исторические SQL не меняются. Сценарий проверен в транзакциях, которые откатывают тестовые изменения журнала и грантов.
