# DESIGN_SYSTEM_MAP.md — полная карта Design System GarmentOS

> **Решение зафиксировано владельцем проекта (2026-08-03): стек больше не расширяется, исследование остановлено, начинается реализация.** Источники сужены до трёх (в порядке приоритета): **shadcn/ui** — техническая база компонентов (Dialog/Select/Combobox/Command/Calendar/Drawer/Tooltip/Dropdown/Popover); **Origin UI** — готовые полированные паттерны (карточки/KPI/dashboard/формы/фильтры/списки/empty state/search); **Magic UI** — только микроанимации, точечно, не декоративно. Иконки — без изменений к уже принятому решению (`UI_FOUNDATION.md`, раздел 3): фирменный SVG-набор, Lucide только как донор контура для недостающих. Визуальный/UX-ориентир переопределён: **основной — amoCRM (карточный интерфейс, воздух, минимум цвета, правая панель вместо перехода, inline-редактирование) и МойСклад (плотность бизнес-данных, работа со статусами/складом/техкартами)**, вторичный — Linear/Stripe/Notion (скорость, финансовые таблицы, единообразие компонентов) — идеи, не визуальное копирование ни одного источника. §1 ниже (исследование Linear/Vercel/GitHub/ClickUp/Airtable/Telegram/Revolut/Slack) остаётся как справочный материал по конкретным паттернам, но перестаёт быть источником новых направлений поиска — все следующие решения проверяются против amoCRM/МойСклад в первую очередь.

> Расширяет `docs/UI_FOUNDATION.md` (уже утверждён владельцем проекта, остаётся в силе — Tailwind, политика иконок, расположение `design-system/` не пересматриваются). Тот документ покрывал ~30 компонентов под уже существующие 8 экранов. Этот — полная карта под систему, которая должна выдержать рост до 50-100 экранов без переделки: что строится сейчас, что строится в ближайших итерациях и почему, что описано как спецификация на будущее без кода.
>
> **Формат работы, зафиксированный владельцем проекта**: сначала карта (этот документ, без кода), затем визуальное утверждение карты, затем реализация Tier A/B-now, затем полноценный визуальный показ (скриншоты + интерактивные состояния + сравнение до/после) перед тем, как система считается финальной.

## 0. Как читать этот документ

- **Tier A** — фундаментальные примитивы, нужны буквально везде, уже есть готовый экран-потребитель. Строятся первыми, полностью.
- **Tier B-now** — очевидно понадобятся в ближайших экранах (не абстрактно «когда-нибудь»), строятся в этом же проходе.
- **Tier B-later** — описаны полностью (назначение/API/зависимости/источник), не строятся, пока не появится конкретный экран. Цель описания — чтобы реализация заняла часы, а не требовала повторного исследования.
- **Источник** — из приоритетного списка владельца проекта (shadcn/ui → Origin UI → Magic UI → Aceternity UI → Tailwind UI как референс → Radix UI → React Aria → Headless UI → Tremor → Mantine, в этом порядке предпочтения). Ни один компонент не берётся «как есть» — таблица показывает точку заимствования (логика/доступность), стилизация всегда наша (принцип из `UI_FOUNDATION.md`, раздел 0).

## 1. Исследование — конкретные выводы, не общие слова

Ниже не «Linear красивый, Stripe удобный» — а конкретные паттерны, которые GarmentOS реально заимствует, и откуда они взяты. Основано на устоявшихся, многократно описанных в дизайн-кейсах паттернах этих продуктов (не на live-браузинге в рамках этой сессии — это стоит сказать явно, а не выдавать за прямое наблюдение).

| Продукт | Конкретный паттерн | Что берём для GarmentOS |
|---|---|---|
| **Linear** | ⌘K — не «поиск», а основная точка входа в любое действие (создать issue, сменить статус, назначить); оптимистичный UI — действие визуально завершается мгновенно, синхронизация с сервером — фоном; один акцентный цвет, без градиентов | `GarmentCommandPalette` как способ создать заказ пошива/найти материал без похода через меню (совпадает с уже одобренной идеей «AI-командная строка», `docs/MASTER_BACKLOG.md` п.2.3); toast/optimistic-паттерн для форм создания — уже частично сделано (`toast.success` сразу после ответа API, не отдельный "синк" статус) |

## 2. Токены — расширение `Tokens/tokens.css`

Уже реализовано (см. `apps/web/src/design-system/Tokens/tokens.css`): `--color-*` (14 семантических цветов + success/warning/info tints), `--radius-*` (4 уровня), `--shadow-card`, `--font-sans`, `--text-*` (6 уровней типографики), `--z-index-*` (4 уровня), `--animate-duration-*` (3 уровня).

Что добавляется этим документом (реализовано в этом же проходе — низкий риск, не требует нового экрана-потребителя, это доработка существующего файла токенов, не новый компонент):

1. **Elevation** — сегодня один уровень тени (`--shadow-card`). Добавляется шкала: `--shadow-sm` (hover-приподнятие строки списка), `--shadow-card` (текущий, карточка в покое), `--shadow-lg` (открытый Dialog/Drawer/Popover — уже используется inline в `Dialog.tsx`/`Form/DatePicker.tsx` как `shadow-card`, выносится в отдельный именованный токен, чтобы модалка визуально «выше» обычной карточки).
2. **Dark mode — архитектурно, не полная реализация.** По явному запросу («Dark mode (архитектурно)» в вашем сообщении) — токены получают тёмный вариант через `@media (prefers-color-scheme: dark)`, переопределяющий те же имена переменных (`--color-background`, `--color-card` и т.д.), а не второй набор классов. Ни один компонент не меняется — они уже читают токены по имени. Это даёт системе готовность к тёмной теме без полного визуального QA тёмного режима сейчас (он не входит в объём этого прохода — принцип 3: делаем проводку, не полную фичу, пока нет запроса на тёмную тему как таковую).
3. **`font-variant-numeric: tabular-nums`** — токен `--font-numeric` для сумм/количеств/номеров заказов, чтобы колонки чисел визуально выравнивались (паттерн Stripe, §1).
4. **Motion — явные кривые, не только длительность.** `--ease-standard: cubic-bezier(0.4, 0, 0.2, 1)` (Material "standard easing", используется большинством современных SaaS для входа/выхода элементов) и `--ease-spring` (лёгкий overshoot для микроинтеракций типа нажатия кнопки/появления toast) — сегодня анимации Radix-компонентов используют браузерный дефолт, не фирменную кривую.

## 4. Самостоятельный UX-аудит текущих 8 экранов (не дожидаясь замечаний владельца)

Конкретные находки, не общие рассуждения:

1. **`ProductionOrdersPage` (форма-эталон) — выбор модели/цеха через `Select`, а не `Combobox`.** При росте каталога моделей за пределы ~15-20 записей прокрутка обычного `Select` станет медленнее поиска. Это реальный, не гипотетический риск — коллекция уже сегодня подразумевает десятки моделей на сезон (`PROJECT_VISION.md`). → `Combobox` в Tier B-now (§3.3).
2. **Ни один экран не показывает состояние «отправляется» на кнопке.** Между нажатием «Создать» и ответом сервера кнопка просто доступна для повторного нажатия — риск двойной отправки формы на медленной мобильной сети (принцип 20, мобильная связь в цеху/на складе). → loading-состояние `Button`, Tier B-now (§3.2).
3. **Иконки статусов в `ListCard` не имеют подписи при наведении/долгом нажатии.** Цвет и форма иконки понятны только тому, кто уже выучил систему — противоречит `UX_PRINCIPLES.md` §9 («понятность без обучения»). → `Tooltip`, Tier B-now (§3.8).
4. **7 из 8 экранов — плоские списки без hover-действий**, при клике на строку открывается либо ничего, либо полноэкранная форма редактирования. Быстрое действие («изменить статус», «позвонить поставщику») требует полного перехода. → hover-only `DropdownMenu` в `ListCard`, паттерн Notion (§1), Tier B-now.
5. **Нет полностраничного error-state.** Если API недоступен при первой загрузке списка (не при отправке формы), экран сегодня показывает пустой список — неотличимо от реального «нет данных». Прямое нарушение `UX_PRINCIPLES.md` §5. → Tier B-now.
6. **Суммы (цена в `ProductionOrdersPage`) визуально не выровнены как числа** — обычный шрифт без `tabular-nums`, значения разной длины «прыгают» при сравнении построчно. → токен `--font-numeric`, §2.

| Элемент | Сейчас в GarmentOS | Лучшая практика в индустрии | Почему это применимо |
