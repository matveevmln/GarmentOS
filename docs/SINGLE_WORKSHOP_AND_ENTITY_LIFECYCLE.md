# Один цех и жизненный цикл данных

Дата: 2026-10-05. Запрос владельца: создавать небольшие партии в Ак Сарай без предварительного заполнения реквизитов; проверить удаление сущностей и актуальность документации.

## Рабочий путь

Главная → Партии → Новая партия → модель → количество и размеры → согласованная цена → проверка → разместить. Единственный активный цех подставляется автоматически; сохранённый устаревший выбор заменяется единственным действующим цехом. Срок необязателен. Договор, ИНН, адрес, нормы материалов, закупки и поставщики не являются предварительными заданиями для пользователя.

Количество и цену нельзя выдумывать: пользователь задаёт их для конкретной партии. Автоматическое распределение по размерам можно поправить до размещения. Создание партии и связанной спецификации атомарно; повтор того же запроса после потери ответа возвращает ту же партию.

После размещения: Заказ → Пошив → Готовность → Приёмка → Закрытие. План и фактическая приёмка различаются; обычно принимается вся партия, но фактическое количество проверяется. Приёмка не заменяет ОТК и закрытие. Из модели можно открыть её партии и вернуться обратно.

## Проверка удаления и архива

Это аудит контроллеров API и веб-экранов, а не утверждение, что удаление реализовано для всех сущностей.

| Сущность | Доступный путь | Ограничение / пробел |
| --- | --- | --- |
| Незавершённый ввод новой партии на устройстве | «Очистить незавершённый ввод» после восстановления | Недоступно при неизвестном результате отправленного запроса; созданные модели остаются |
| Модель | Архив и восстановление в карточке; архив в списке | История партий, варианты и документы сохраняются; физического удаления нет |
| Размеры и цвета / SKU | Настройка ряда и добавление вариантов в модели | Универсального удаления SKU/цвета нет; нельзя удалять вариант, на который ссылаются партии |
| Характеристика модели | DELETE атрибута | Проверяется компания и право записи |
| Цех | Архив и восстановление в «Мой цех»; просмотр архива | Архивированный цех нельзя выбрать для новой партии; исторические партии доступны |
| Черновик / размещённая партия | Отмена с причиной в паспорте → вкладка «Закрытые» | Проверка прав и фактов; после приёмки/ОТК/закрытия обычная отмена запрещена; физического удаления нет |
| Спецификация | Отмена через существующий API/экран; связанная отмена партии | Старые распределения и история не стираются; PDF хранится версиями |
| Задание на раскрой | Отмена через API и подробный паспорт | Не должно продолжать действовать после отмены партии |
| Счёт / заказ продажи | Существующие API отмены | Не означает удаления платежей или складских движений; интерфейс не покрывает все сценарии |
| Оригинал документа и его версии | Сохранение оригинала и цепочки версий | Физического удаления и «корзины документов» в интерфейсе нет |
| Приёмка / ОТК / брак / платежи / движение остатков | История фактов сохраняется | Нет общего безопасного пути отмены ошибочного факта с компенсирующими операциями — отдельная задача |
| Материал / поставщик / закупка / склад / коллекция | Создание и чтение, отдельные операции процесса | В проверенных контроллерах нет универсального удаления/архива; скрытие раздела не удаляет данные |
| Отгрузка / инвентаризация | Создание и переходы процесса | Нет общего удаления черновика или отмены проведённой операции |

Нельзя добавлять DELETE с каскадом ко всем таблицам: это может убрать приёмку, оставив остаток, либо стереть модель из истории партии. Для справочников нужен обратимый архив; для проведённых операций — проверяемое исправление с журналом. Пользовательские данные в production в рамках проверки не удаляются.

## Архитектура и структура

Система остаётся модульным монолитом: один сервер с отдельными предметными модулями и PostgreSQL, один веб-клиент. Новая отдельная таблица «Партии» и миграция не вводятся: паспорт показывает существующий `production_order`.

| Где | Что хранится / за что отвечает |
| --- | --- |
| `apps/web` | Мобильный интерфейс и формы; не источник истины для статуса партии |
| `apps/api` | Права, проверка компании, транзакции и согласование связанных операций |
| `packages/domain` | Бизнес-правила: статусы, количество, отмена, неизменность снимка |
| `packages/shared-types` | Общие контракты и проверки входных/выходных данных |
| `packages/db-schema` | Схема базы и миграции |
| `infra` | Сборка, запуск, ремонт прав и проверка целостности |
| `docs` и `CLAUDE.md` | Решения, архитектура, правила проекта, журнал проблем и проверок |

Подробная карта: `ARCHITECTURE.md`, `DATABASE_SCHEMA.md`, `REPOSITORY_STRUCTURE.md`. Приоритет текущего рабочего сценария задан ADR 0004 и актуальным уточнением в `CLAUDE.md`: прежние исторические требования о двух цехах, полном снабжении и обязательном договоре не являются условием запуска небольшой партии.

## Что ещё важно и пока не закрыто

- Исправление ошибочной приёмки или оплаты: одного удаления строки недостаточно, нужна обратная операция с проверкой остатков и журналом.
- Условия оплаты: существующая система использует исторические значения по умолчанию. Их нельзя выдавать за подтверждённую договорённость владельца; требуется отдельная проверка реальных условий Ак Сарай.
- Документы с пустыми юридическими полями можно использовать для проверки данных, но нельзя считать готовыми к подписанию. Реквизиты не должны блокировать пошив и не должны выдумываться.
- Восстановление незавершённого ввода пока привязано к устройству; это не синхронизируемый серверный черновик. Сохранённая партия доступна с разных устройств.
- Проверка в Chromium с мобильными размерами не заменяет проверку на физическом Safari. Авторизованная сессия владельца на телефоне не доступна агенту.
- В документации есть исторические этапы и планы. Их следует сохранять как историю, явно отличая от текущего утверждённого процесса; наличие файла архитектуры не доказывает реализацию каждой описанной функции.

Новые пробелы перечислены в `PILOT_BUGS.md`; во время пилота это основной журнал проблем. Подготовленный текст для базы знаний — `NOTION_PROJECT_HUB.md`. Запись в Notion возможна только после подтверждённого подключения.
