# Дизайн-система GarmentOS — эталон и перенос в apps/web

> **Решено владельцем проекта (2026-08-02)**: единственный источник визуального языка GarmentOS — мобильный интерфейс `apps/prototype`, опубликованный на Vercel. `apps/web` не проектирует свой собственный визуальный стиль — он визуально продолжает прототип. Новый экран без готового эквивалента в прототипе сначала получает дизайн в этом же языке (токены/компоненты ниже), и только потом — функциональность. Этот документ фиксирует: (1) из чего состоит эталонный язык, (2) честный аудит того, что в `apps/web` ему сейчас соответствует, а что нет, (3) план переноса.

## 0. Честная оговорка, важная для плана ниже

`apps/prototype` — кликабельный демо-макет, не полноценный дизайн каждого экрана. Прямая проверка разметки (`apps/prototype/index.html`) показала: во всём прототипе **четыре** `<input>` элемента — две строки поиска и два поля в одном модальном окне приёмки партии. Ни одной формы создания/редактирования сущности (цех, поставщик, материал, модель, закупка, заказ пошива) в прототипе не спроектировано — нажатие «Новая закупка»/«Добавить материал» в прототипе просто показывает toast-уведомление, реальной формы за ним нет.

Это значит: **списки, карточки, детальные экраны, навигацию, статусы — переносим дословно** (эталон есть, копируем токены/классы/структуру); **формы создания/редактирования — проектируем заново, в том же визуальном языке** (эталона нет, но есть язык, из которого форма должна быть собрана: `.card`, `.modal-field`, отступы, радиusы, типографика). Ниже это разделено явно, чтобы не создалось ложное ощущение, будто для форм есть образец, который просто не скопировали.

**Итог раздела 1**: из ~20 структурных элементов дизайн-системы дословно перенесены 4 (палитра, радиусы/тени, шрифт, нижняя навигация), ещё 5 перенесены частично (иконки, статус-плашка, карточка, кнопка, пустое состояние), остальные 11 — не перенесены вовсе. Самое серьёзное расхождение — именно то, на которое вы указали: **таблицы вместо карточек** на каждом экране со списком (Цеха, Поставщики, Материалы, Склады, Модели, Закупки, Заказы пошива, SKU, BOM-позиции).

|---|---|---|---|---|---|
| Вход (Login) | — (в прототипе нет экрана логина, начинается сразу с Главной) | — | Карточка `.auth-card` близка к `.card` | Нет эталона вовсе — оформлен в токенах, но не по образцу конкретного экрана | Токены/радиусы уже верны, менять не нужно |
| Навигация (шапка + таб-бар) | `.topbar` + `.bottomnav` | Нижняя мобильная навигация | — | Верхний topbar не показывает название текущего экрана, показывает только логотип | Нижний таб-бар — переносить as-is |
| Цеха / Поставщики / Склады | — (в прототипе нет отдельных экранов для них, есть только общий паттерн `.list-card`) | — | — | **Таблица вместо `.list-card`**, нет поиска/фильтров | Ничего — переписать список на `.list-card` |
| Материалы | `materials` | — | Вкладки типа материала (`fabric/trim/packaging`) — уже частично реализованы как разные страницы, а не как `.filters`-вкладки на одной | **Таблица вместо `.list-card` с индикатором остатка (`.bar-track`)**, нет строки «хватает/ниже нормы» | Разделение по типу материала как концепция — верно, форма переключения — нет |

## 3. План переноса (по приоритету, без затрагивания бизнес-логики экранов)

Ключевой принцип плана: **компоненты, не экраны** — почти все находки выше устраняются заменой 2-3 переиспользуемых компонентов, а не переписыванием каждой страницы по отдельности.

### Шаг 1 — компонент `ListCard` вместо `DataTable` (наибольшее визуальное расхождение) — **закрыто 2026-08-02**
Новый компонент, воспроизводящий `.list-card`/`.thumb`/`.body`/`.badge` дословно по классам прототипа. Заменяет таблицы на Цехах/Поставщиках/Складах/Материалах/Закупках/Заказах пошива/BOM/SKU одним компонентом. `DataTable` полностью выведен из повседневного интерфейса (решение владельца проекта) — остаётся в кодовой базе неиспользуемым на случай будущего табличного режима для экспорта/массового анализа, не для обычной работы.

### Шаг 2 — `.filters` (пилюли статуса) и `.search` как общие компоненты — **закрыто 2026-08-02**
`FilterTabs`/`SearchBar`, использующие классы `.filters`/`.search` дословно из прототипа. Подключены к Цехам/Поставщикам/Материалам/Закупкам/Заказам пошива/Моделям — функциональные (client-side фильтр/поиск), не только визуальные (Master Backlog 1.5).

### Шаг 3 — `ModelGrid` для экрана Моделей — **закрыто 2026-08-02**
Сетка карточек с фото-плейсхолдером (градиент, выбираемый детерминированно по названию модели, как в прототипе).

### Шаг 4 — `Card`/`CardPad`/`CTA` как базовые примитивы — **закрыто 2026-08-02**
`.card`/`.card-pad` как переиспользуемые обёртки, `.cta`/`.cta.secondary` с фирменной тенью — используются всеми остальными компонентами.

Все четыре шага проверены Playwright на iPhone 13 и десктопном viewport по всем 7 названным экранам — ноль ошибок, ноль горизонтального переполнения. В процессе проверки скриншотами найден и исправлен реальный визуальный баг: `.list-card .title`/`.meta` не имели `display: block` (в оригинальном прототипе это `<div>`, наследующий блочное поведение по умолчанию; React-версия использовала `<span>` для валидности вложения в `<button>`) — заголовок и подпись слипались в одну строку без переноса.

### Шаг 5 — Формы создания/редактирования — **закрыто 2026-08-03**
Форма-эталон (заказ пошива) утверждена, затем применена ко всем 7 экранам (Цеха/Поставщики/Материалы/Склады/Модели/Карточка модели/Закупки): `Card` + `Input`/`Select`/`Combobox`/`NumberInput`/`MoneyInput` + `Button` (loading-состояние) + `toast` вместо статичных ошибок + `SkeletonList`/`ErrorState` для состояний загрузки/сбоя + `emptyActionLabel` в пустых состояниях. Каждый экран проверен на реальных данных (не только визуально) — форма отправляется, toast подтверждает, список обновляется, mobile+desktop, 0 ошибок консоли.

Честная находка, не решённая молча в рамках этого шага: карточка модели (`ProductDetailPage`) технически отвечает на 3 разных вопроса (модель / SKU / BOM) — формальное нарушение принципа 22. Разделение на отдельные маршруты — решение об информационной архитектуре, а не «перенос компонентов»; зафиксировано как открытый вопрос, не выполнено по собственной инициативе.

### Шаг 6 — Главная (Дашборд) и AI-брифинг
Сейчас у `apps/web` нет экрана Главной вообще (сразу редирект на Цеха) — это самое заметное отличие от того, что вы показываете на скриншоте. Требует: `.brief-card`, `.stat-grid`/`.stat-card`, переключатель видов (`.segmented`) — сознательно поставлено последним шагом, т.к. содержимое (реальная статистика: активные заказы, партии в работе у цехов) появится только после того, как реальные данные начнут накапливаться в ходе пилота — раньше это были бы карточки с нулями.

### Шаг 7 — Таймлайн/история сущности
`.timeline` для карточки модели/заказа/партии — привязан к `docs/PRINCIPLES.md` принципу 18.5 (единая история сущности), который уже спроектирован как read-model поверх `audit_log`/`document_links`/`notes`. Ставлю последним, т.к. зависит от покрытия `audit_log` (см. `docs/ARCHITECTURE_REVIEW.md`, пункт 4 сводной таблицы) — рисовать таймлайн, у которого нет полных данных для показа, преждевременно.

## 4. Как это стыкуется с планом «Railway → пилот»

Шаги 1-4 — чисто визуальные замены существующих экранов (Цеха/Поставщики/Материалы/Склады/Модели/Закупки/Заказы пошива уже работают функционально, меняется только обёртка) — не блокируют и не откладывают деплой на Railway, разумно сделать **до** первого входа Богдана и Артёма, чтобы первое впечатление от реальной системы сразу было «одна цельная система», а не то, что вы увидели на скриншотах. Шаг 5 (формы) — минимально необходимый мини-макет перед тем, как трогать все формы разом. Шаги 6-7 — сознательно после начала пилота, когда появятся реальные данные для отображения.
