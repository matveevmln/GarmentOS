## Фаза 1 — MVP: сквозной цикл на одном канале продаж

**Цель**: рабочий end-to-end поток для одной пилотной компании — от закупки до продажи на одном маркетплейсе.

Состав (соответствует границам MVP в `PROJECT_VISION.md`, п.6):

1. **Identity & Access** — компании, пользователи, роли (director/accountant/procurement/technologist/marketplace_manager/warehouse_keeper/contract_manufacturing_manager), базовый RBAC.
2. **Catalog** — модели, SKU (размер × цвет).
3. **Materials & Procurement** — материалы, поставщики, простые заказы поставщикам.
4. **BOM** — спецификации расхода, версионирование.
5. **Contract Manufacturing** (не «Production» — см. `docs/DATABASE_SCHEMA.md` п.0) — цеха-подрядчики (`workshops`), заказы пошива без внутренней стадийности (крой/пошив/ОТК — не наша операционка).
6. **Warehouse & Inventory** — приёмка, отгрузка, остатки по SKU, инвентаризация, включая склад-локацию у цеха для давальческого сырья.
7. **Sales & Orders** — ручное создание заказов + интеграция с Wildberries (остатки, цены, заказы).
8. **Honest Sign** — MVP-уровень: учёт кодов, базовые статусы (`issued → applied → sold`).
9. **Finance** — базовая себестоимость (материалы + услуги цеха), без полного P&L.
10. **Inbox** (добавлен 2026-07-24 по итогам `docs/USER_JOURNEY_AUDIT.md`) — Telegram-канал + загрузка файлов, AI-классификация входящих сообщений, one-tap подтверждение. См. `docs/INBOX_ARCHITECTURE.md`.

**Exit-критерий**: 1-3 пилотные компании ведут в системе реальные остатки и заказы минимум 4 недели подряд без критичных расхождений (см. критерий успеха №1 в `PROJECT_VISION.md`).

### Итерация 3 — статус и зафиксированные направления развития (2026-07-25)

**Первая партия домена утверждена владельцем проекта** (Identity & Access, Catalog, Materials & Procurement, BOM, Contract Manufacturing) — архитектура (модульная структура `domain/application/infrastructure/index.ts`, границы агрегатов, порты для межмодульных вызовов вроде `BomApprovalPort`, draft-first через `*Draft`+`confirm*`) прошла ревью и не пересматривается для оставшихся модулей второй партии (Warehouse & Inventory, Sales & Orders, Marketplace Integration, Honest Sign, Finance, Notifications) — они реализуются по тому же шаблону.

При ревью первой партии владелец проекта явно попросил зафиксировать здесь (не реализовывать сейчас) 4 направления развития:

1. **Bulk-операции для каталога.** Массовая генерация SKU (размеры × цвета × другие параметры одной операцией) — будущий **отдельный use case** в `packages/domain/catalog` (например, `bulkCreateProductVariants`), не изменение существующих `createProduct`/`createProductVariant` и не изменение границ агрегатов `Product`/`ProductVariant`. Реализуется, когда появится конкретный сценарий использования (Zero Input, `PRINCIPLES.md` принцип 17) — вероятно, вместе с `apps/web` (Итерация 11) или как часть Inbox-сценария «прислал прайс на 12 цветов сразу».
2. **Domain Events.** После завершения доменного слоя (обе партии Итерации 3) — архитектура доменных событий (`BomApproved`, `PurchaseOrderReceived`, `ProductionOrderConfirmed`, `ShipmentCreated` и т.п.), см. `docs/ARCHITECTURE.md` п.3 («Правило межмодульного взаимодействия», in-process event bus). **Не реализуется сейчас** — текущие межмодульные вызовы (Contract Manufacturing → BOM) идут через узкие порты (`BomApprovalPort`), не через шину событий; это осознанно, чтобы не проектировать шину до того, как появится второй-третий реальный сценарий подписки на событие. Кандидат на реализацию — при переходе к сквозному сценарию продажи (`docs/ARCHITECTURE.md` п.4.1: Sales → Warehouse → Honest Sign → Finance), который в этой партии реализуется как независимые модули без хореографии между ними (см. ниже) — это и есть первый реальный повод внедрить события, не раньше. Закрывает как решение риски 2.2/2.3 из `ARCHITECTURE_SELF_REVIEW.md`.
3. **Read Models / CQRS.** Карточки сущностей (Entity Timeline, `PRINCIPLES.md` принцип 18 п.5), аналитика/Reporting BI, история документов, дашборды — вероятно потребуют специализированные модели чтения отдельно от доменных use case. **Не реализуется сейчас** — зафиксировано как возможное направление, без изменения существующих use case. Естественное место реализации — Итерация 11 (`apps/web`) и Фаза 3 (BI-дашборды).
4. **Демо-база на реальных данных бизнеса.** После завершения всех доменных модулей Итерации 3 — полноценная демо-база (seed) на основе реальных моделей/поставщиков/тканей/цехов/документов владельца, для сквозной проверки всей системы. Интеграционные тесты продолжают использовать реальные бизнес-сценарии (как `scenario.spec.ts` в Contract Manufacturing), не абстрактные примеры — этот принцип не меняется и во второй партии.

**Явное архитектурное решение по хореографии между Sales/Warehouse/Honest Sign/Finance** (вторая партия): каждый из этих модулей во второй партии Итерации 3 реализуется **независимо**, с собственными use case и инвариантами, БЕЗ синхронных кросс-модульных вызовов между собой (в отличие от Contract Manufacturing → BOM, где связь была единственной и явно требовалась инвариантом). Сценарий "заказ на маркетплейсе → резерв остатка → гашение кода маркировки → проводка себестоимости" (`docs/ARCHITECTURE.md` п.4.1) остаётся описанным, но не сшитым между модулями до появления Domain Events (пункт 2 выше) — сшивать 4 модуля синхронными портами одним махом означало бы либо преждевременную связанность, либо предвосхищение шины событий без реального повода. `Warehouse` тем не менее реализует `reserveStock`/`releaseReservation` (поля `quantity_reserved` уже есть в схеме) — это готовит почву для будущей интеграции, не будучи самой интеграцией.


## Фаза 2 — Мультиканальность и комплаенс

**Цель**: расширить продажи на другие каналы и закрыть комплаенс полностью.

- Интеграция Ozon и Яндекс Маркет через тот же `MarketplaceConnector` интерфейс.
- Опт и розница (собственная витрина/точки продаж) как каналы.
- Полный цикл «Честного Знака»: вывод из оборота при продаже на маркетплейсе (через оператора ЭДО), обработка возвратов/пересортицы кодов.
- Финансовый модуль: управленческий P&L по модели/каналу/партии, экспорт в 1С.
- Уведомления: низкий остаток материалов, срыв сроков производства, рассинхронизация с маркетплейсом.
- Inbox: дополнительные каналы — email-алиас, WhatsApp Business API (требует коммерческого approval, дольше Telegram) — см. `docs/INBOX_ARCHITECTURE.md`, раздел 4.

**Exit-критерий**: 0 блокировок продаж из-за ошибок маркировки у пользователей системы (критерий успеха №4); директор получает P&L без участия бухгалтера (критерий №2).

## Фаза 3 — Планирование заказов у подрядчиков и аналитика

**Цель**: перейти от учёта к планированию и прогнозированию.

- Планирование распределения заказов между независимыми подрядными цехами: сроки, загрузка каждого цеха, рейтинг надёжности/качества по цеху — **не планирование собственных производственных мощностей**, которых у нас нет.
- BI-дашборды: маржинальность, оборачиваемость, ABC-анализ по SKU.
- Базовый прогноз спроса на основе истории продаж и сезонности.
- Рекомендации по точке перезаказа материалов на основе прогноза (а не только статичного `reorder_point`).

**Exit-критерий**: точность прогноза спроса измерена и используется минимум одним пилотным клиентом для планирования закупок.

## Фаза 4 — Масштабирование продукта (SaaS)

**Цель**: превратить внутренний продукт для пилотов в самостоятельный SaaS.

- Self-service онбординг новых компаний (регистрация, настройка без участия разработчиков).
- Полноценная мультитенантность в проде (если Фазы 1-3 использовали упрощённую модель для пилотов).
- Мобильные приложения: склад (сканирование штрихкодов/QR, инвентаризация), менеджер по производству (офлайн-доступ к статусам заказов у цехов).
- Партнёрские интеграции: логистика (СДЭК, Boxberry), банки/эквайринг, ЭДО.
- Публичный API и документация для интеграторов.

**Exit-критерий**: 100+ активных компаний-клиентов (цель 3 лет из `PROJECT_VISION.md`), self-service онбординг без участия команды разработки для типового клиента.

## Фаза 5 — Отраслевая зрелость

**Цель**: соответствует горизонту 5 лет из `PROJECT_VISION.md`.

- ML-модели: прогноз спроса следующего поколения, оптимизация точки перезаказа, рекомендации по ценообразованию на маркетплейсах.
- Расширение экосистемы интеграций.
- Открытая партнёрская программа.

## Принцип ведения роадмапа

- Каждая фаза начинается только после закрытия exit-критериев предыдущей — это фиксируется явно (не «примерно готово», а конкретная проверка).
- Изменение содержания фазы — через обновление этого файла в отдельном коммите/PR с обоснованием, не молчаливым дрейфом скоупа.
- Технический долг, отложенный сознательно ради скорости, фиксируется как явный пункт в начале следующей фазы, а не теряется.
