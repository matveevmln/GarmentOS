# UX_PRINCIPLES.md — операционные правила интерфейса GarmentOS

> Этот документ не заменяет и не дублирует `docs/PRINCIPLES.md` (принципы 17 «Zero Input», 20 «Mobile-First», 22 «Один экран — один вопрос») — он **детализирует их до проверяемых правил конкретного экрана/компонента**, чтобы при разработке нового экрана не нужно было каждый раз заново решать, как обрабатывать пустое состояние, ошибку или удаление. Владелец проекта запросил этот документ явно при утверждении `docs/UI_FOUNDATION.md` (2026-08-02).
>
> Аудитория: Богдан и Артём — владелец бизнеса и его партнёр, оба большую часть дня не за компьютером (склад, цех, машина, встречи с поставщиками). Каждое правило здесь — следствие этого факта, не абстрактная забота о «хорошем UX».

## 1. Один экран — один главный вопрос

См. `docs/PRINCIPLES.md`, принцип 22. Практическое расширение: если на экране есть переключатель вкладок/фильтр, который меняет **о чём** экран, а не **какие данные внутри одного и того же ответа** — это ошибка декомпозиции, экран нужно разделить. Пример: `/production-orders` отвечает на «что заказано в цехах», фильтр по статусу заказа — это уточнение одного и того же ответа (допустимо); отдельная вкладка «Финансы по заказам» на этом же экране была бы вторым вопросом (недопустимо, для этого отдельный экран).

## 2. 2–3 тапа до любого частого действия

См. `docs/PRINCIPLES.md`, принцип 20, п.5. Считается от главного экрана (`/workshops` — текущий `index`-редирект) до завершения действия, включая подтверждение. Частые действия сегодня: создать заказ пошива, добавить материал, посмотреть остаток склада. Проверяется вручную при ревью экрана (клик за кликом), не автоматическим тестом — метрика намеренно качественная, не количественная (иначе разработчик оптимизирует под метрику, а не под реальное неудобство).

## 3. Одинаковое поведение одинаковых элементов

Одна и та же роль элемента — одно и то же поведение и расположение на всех экранах:
- Первичное действие экрана (создать/сохранить) — всегда `Button` варианта `default`, всегда справа от вторичного действия в футере формы/модалки, никогда слева.
- Разрушительное действие (удалить/отменить) — всегда `Button` варианта `destructive`, всегда требует подтверждения через `Dialog` (см. §6 «Undo» — для необратимых операций подтверждение обязательно уже сегодня).
- Статус сущности (заказ/партия/документ) — всегда `StatusBadge` с одной и той же парой цвет→смысл во всех модулях (см. `apps/web/src/design-system/StatusBadge/StatusBadge.tsx` — единая таблица статус→тон, не переопределяется по месту).
- Дата — всегда `DatePicker` (см. `docs/UI_FOUNDATION.md`), никогда нативный `<input type="date">` (нечитаемый формат `mm/dd/yyyy` для русского пользователя — уже зафиксировано как решённая проблема в `Form/DatePicker.tsx`).
- Пустой список — всегда одна и та же композиция (иконка + заголовок + подсказка + кнопка действия, см. §4), не разный текст/вёрстка от экрана к экрану.

Нарушение этого правила не считается «мелким визуальным несоответствием» — оно прямо противоречит принципу из `CLAUDE.md` («любой новый экран обязан собираться исключительно из компонентов Design System») и должно блокироваться на Code Review.

## 4. Пустые состояния (Empty States)

Каждый список/экран, который может быть пустым, обязан показывать не пустое место и не голый текст «Нет данных», а три элемента вместе:
1. Заголовок, объясняющий, что здесь будет («Пока нет заказов пошива»).
2. Одна строка-подсказка, объясняющая, почему это полезно или что делать дальше.
3. Кнопка, ведущая прямо к действию, которое заполнит список (не просто «Обновить»).

Компонент: `ListCard` уже поддерживает `emptyTitle`/`emptyHint` (см. `apps/web/src/design-system/ListCard/ListCard.tsx`, продемонстрировано на `/design-system`). **Открытый пробел**: `emptyAction` (кнопка) в `ListCard` пока не реализован — на момент написания ни один реальный экран не был проверен на использование пустого состояния с кнопкой действия. Это фиксируется здесь как обязательное требование к следующей итерации, где `ListCard` используется на реальном экране (не как задача для отдельного согласования — сама композиция уже утверждена, остаётся техническая реализация).

## 5. Состояния ошибки (Error States)

Ошибка обязана отвечать пользователю на два вопроса одновременно: **что произошло** и **что делать дальше**. Технический текст исключения («500 Internal Server Error», «Network Error», необработанный текст с бэкенда) никогда не показывается напрямую пользователю.

Реализовано сегодня: `ProductionOrdersPage` использует `toast.error(...)` с текстом на русском языке, объясняющим суть проблемы (`docs/UI_FOUNDATION.md`, `design-system/Toast/Toast.tsx`). Правило для всех новых форм: любая ошибка API преобразуется в понятную русскоязычную фразу на уровне компонента экрана (не показывается сырой ответ сервера), и если ошибка требует действия пользователя (например, «сначала утвердите BOM») — текст должен называть это действие явно, а не просто констатировать отказ.

## 6. Undo (отмена действия)

Для необратимых операций (удаление, отмена заказа) — обязательное подтверждение через `Dialog` **до** выполнения действия (уже реализовано как паттерн, см. пример на `/design-system`, секция «Modal / Dialog»). Пост-фактум Undo (снек-бар «Отменить» после уже выполненного удаления) — не реализован ни в одном модуле, потому что **в `apps/web` сегодня нет ни одной операции удаления** ни на одном из 8 реальных экранов (Цеха/Поставщики/Материалы/Склады/Модели/Закупки/Заказы пошива/каталог компонентов). Это осознанно отложено (принцип 3, «эволюционная архитектура») — конкретный механизм (soft-delete + снек-бар с таймером против hard-delete) выбирается в момент появления первой реальной операции удаления, не заранее.

## 7. Автосохранение (Autosave)

Критично для длинных форм — Богдан/Артём могут закрыть вкладку браузера или потерять связь в цеху/на складе до завершения ввода. **Текущее состояние: не реализовано ни в одной форме.** Единственная многополевая форма сегодня (`ProductionOrdersPage` — модель/цех/цена/срок/список SKU) сохраняется целиком одним запросом при нажатии «Создать», без промежуточного сохранения черновика.

Это фиксируется как явный технический долг, а не молчаливый пробел:
- **Условие срабатывания**: реализуется для конкретной формы, когда время её заполнения на практике превышает ~30 секунд или больше одного пользователя пожаловался на потерю введённых данных (Zero Input, принцип 17 — не строим механизм, пока не доказана его необходимость на реальном использовании).
- **Механизм по умолчанию**, когда придёт время реализации: черновик состояния формы в `localStorage` по ключу формы (не серверный черновик — не требует нового доменного понятия «черновик заказа» ради UI-задачи), очищается при успешной отправке.

## 8. Mobile UX — одноручный доступ

См. `docs/PRINCIPLES.md`, принцип 20. Дополнение из аудита текущих экранов: главное действие экрана (создать заказ, добавить материал) должно быть в нижней трети экрана на мобильном (в зоне уверенного доступа большим пальцем), не только вверху страницы — сегодня кнопка «Создать» в `ProductionOrdersPage` расположена в форме, которая начинается сверху экрана; это допустимо для формы (пользователь всё равно скроллит вниз по мере заполнения полей), но для экранов-списков (`ListCard`) главное действие должно дублироваться в `GarmentFAB` (см. `docs/UI_FOUNDATION.md`, Tier B — не реализован, нет экрана-потребителя сегодня, все текущие списки открываются из формы создания на той же странице).

## 9. Accessibility (доступность)

Обязательный минимум для каждого нового компонента Design System (проверяется на Code Review, не только on-demand):

1. **Touch target ≥ 44×44px.** Все интерактивные элементы (`Button`, `SelectTrigger`, `DatePicker`-триггер, `Avatar`-кнопки) спроектированы с `h-11` (44px) минимальной высотой — уже выдержано во всех Tier A компонентах (`Button.tsx`, `Input.tsx`, `Select.tsx`, `Form/DatePicker.tsx`).
2. **Контраст текста.** Фирменная палитра (`Tokens/tokens.css`) подобрана так, что `--color-muted-foreground` (#75757e) на `--color-card`/`--color-background` (#ffffff/#fafaf9) даёт контраст выше порога WCAG AA (4.5:1) для обычного текста — не проверено автоматическим инструментом (нет CI-шага), это открытый пункт для следующей итерации, а не подтверждённый факт.
3. **Клавиатурная навигация.** Обеспечивается самим выбором Radix UI как основы (`docs/UI_FOUNDATION.md`) — `Dialog`/`Select`/`Popover` из коробки поддерживают `Tab`/`Esc`/стрелки без дополнительного кода поверх примитива.
4. **Видимое состояние фокуса.** Все Tier A компоненты используют `focus-visible:ring-2 focus-visible:ring-primary/30` — фокус виден, но не мешает мышиному/тач-взаимодействию (`focus-visible`, не `focus`).
5. **Читаемость на солнце (склад/цех/улица).** Фирменная палитра намеренно избегает низкоконтрастных светло-серых элементов управления (сравните с типичным admin-panel UI) — крупный чёрный текст на белой карточке, а не серый на сером. Отдельный «яркий режим» не проектируется — это было бы преждевременной сложностью без доказанной необходимости (принцип 3); правило зафиксировано здесь на случай, если жалоба на читаемость появится на практике, чтобы новый экран сразу решал проблему выбором цвета, а не игнорировал её.

## 10. Каталог компонентов — `/design-system`

Живая страница `apps/web/src/pages/DesignSystemPage.tsx` (маршрут `/design-system`, вне обычной навигации и вне `RequireAuth` — служебный маршрут для ревью, не пользовательский экран) демонстрирует все состояния компонентов из этого документа: кнопки во всех вариантах, поля ввода/`Select`/`DatePicker`, поиск/фильтры, все статусы `StatusBadge`, `Avatar` во всех тонах, `Card`/`ListCard` включая пустое состояние, `Skeleton` (переключаемый), `Dialog`, `Toast` (success/error). Любой новый Tier A/Tier B компонент обязан получить секцию на этой странице при добавлении — иначе его состояния не проверяются визуально и расхождение с остальной системой не будет замечено до продакшена.
