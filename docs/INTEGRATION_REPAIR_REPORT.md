# Проверка и ремонт связей GarmentOS — 2026-10-04

Проверка выполнена на отдельной локальной PostgreSQL с настоящими репозиториями и API. В Railway рабочие данные и настройки не изменялись. Этот отчёт описывает исправления в коде; их наличие в рабочем приложении зависит от ревью, объединения PR и выкладки.

## Подтверждённые ошибки и исправления

| Сценарий | Что воспроизведено до исправления | Результат исправления |
|---|---|---|
| Партия → склад | Неверный склад оставлял партию принятой; сбой второй строки оставлял первый остаток и факт приёмки | Статус, фактические количества, все остатки, движения и аудит сохраняются одной транзакцией; после сбоя можно повторить |
| Закупка → склад материалов | Сбой второй позиции оставлял закупку принятой и первый материал оприходованным | Полный откат операции, успешное повторение без удвоения |
| Повторная приёмка | Параллельные запросы могли прочитать прежний статус до записи | Блокировка операции на уровне Postgres; второй запрос видит новый статус и не проводит остаток повторно |
| ОТК → брак | Ошибка записи брака оставляла единственный финальный результат ОТК, который нельзя повторить | Результат ОТК, брак и аудит записываются вместе |
| Крой → расход материала | Сбой второго материала оставлял первый расход без факта кроя | Расход, возврат, факт, статус и аудит сохраняются вместе; корректировка использует ту же транзакцию |
| Строки факта кроя | Повтор одного материала списывал его дважды, сохраняя один факт | Дубли материалов и вариантов отклоняются до движений |
| Спецификация → партия | Два запроса размещали больше доступного; сбой аудита оставлял созданную партию при ответе с ошибкой | Проверка доступного количества и создание выполняются одной сериализованной операцией |
| Строки партии из спецификации | Дважды переданная строка обходила проверку доступного количества | Повтор строки отклоняется до создания партии |
| Подтверждение партии → снимок | Сбой аудита оставлял подтверждённый заказ и снимок после ответа с ошибкой | Статус, снимок и аудит подтверждения сохраняются вместе |
| Отмена партии → крой | Сбой отмены задания оставлял отменённый заказ с действующим кроем | Каскадная отмена заказа, его эксклюзивной спецификации и нетерминальных заданий выполняется целиком |
| Принадлежность компании | Приёмка и прямые складские действия принимали UUID чужого склада; закупка принимала чужой материал | Проверяется принадлежность склада, материала закупки и складского SKU компании |
| Принадлежность модели | В заказ пошива можно было добавить размер/цвет другой модели | Проверяется соответствие вариантов модели заказа |
| Ввод чисел → состояние формы | Количество/цена передавались форме только при потере фокуса; зависимые поля и доступность кнопок запаздывали | Значение передаётся при вводе; форматирование и ограничения остаются при потере фокуса |
| Навигация → существующие функции | Закупки, материалы, склады, поставщики, импорт и документы отсутствовали в основном меню | Существующие разделы доступны в боковом и мобильном меню; основной производственный путь остаётся первым |

## Как обеспечивается целостность

Реализовано уже принятое решение ADR 0001: синхронные вызовы application-сервисов внутри общей транзакции. `DatabaseTransaction` передаёт текущую транзакцию существующим DI-репозиториям через `AsyncLocalStorage`; одновременно выполняющиеся запросы не делят контекст. Вложенные транзакции репозиториев становятся savepoint внутри общей операции. Блокировки включают компанию, тип сущности и идентификатор и работают между экземплярами API.

Схема базы, правила количества фактической приёмки, возможность записать крой при нехватке материала, самостоятельный статус ОТК и неизменяемость снимка партии сохранены.

## Проверки

- До исправлений ошибки воспроизведены регрессионными тестами с настоящей БД. После каждой группы исправлений повторены соответствующие проверки.
- `apps/api/src/business-integrity.e2e.spec.ts`: приёмка, закупка, ОТК, крой, параллельные запросы, спецификация, подтверждение и отмена партии, границы компаний и моделей. Отдельно проверен независимый откат параллельных операций.
- Существующие сквозные тесты API проверяют спецификацию → партию → крой → приёмку → ОТК → фулфилмент, закупки/склад, документы, себестоимость и разграничение доступа.
- Браузерная проверка использует настоящие кнопки и API на тестовой компании: создание справочников, модели, размеров и цвета, спецификации и партии, переходы пошива, приёмку, ОТК и завершение. Проверяется сохранение после перезагрузки и отсутствие ошибок JavaScript.
- Общие `lint`, `typecheck`, `test`, `build` прошли. Всего 370 тестов: 193 доменных/схемных, 168 API (включая 18 новых регрессионных), 9 веб-клиента. Результат GitHub CI приводится в PR.

## Границы результата

Проверки на тестовой базе не устанавливают целостность уже существующих рабочих записей. Прямого доступа к production SQL и авторизованной пользовательской сессии рабочего сайта нет. Исторические записи не исправлялись автоматически.

Внешние подключения Telegram, Wildberries, маркировки и перевозчика требуют отдельной проверки с настоящими учётными данными. Наличие кода или тестового адаптера не означает рабочую интеграцию. Полный финансовый веб-интерфейс, транспортные интеграции и другие описанные в планах возможности этим ремонтом не добавляются.

PR №9 отвечает за восстановление пользовательской сессии; данный ремонт связей и кнопок представляет отдельный набор изменений. Для публикации полного результата нужны оба набора исправлений.
