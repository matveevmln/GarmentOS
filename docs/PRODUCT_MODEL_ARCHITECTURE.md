# Карточка модели — цифровой паспорт изделия (архитектура, без реализации)

> Связанные документы: [`DATABASE_SCHEMA.md`](./DATABASE_SCHEMA.md) (раздел 5 — Catalog, раздел 7 — BOM), [`PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`](./PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md) (разделы 8, 15, 16 — KPI, технологическая карта, MRP-lite — этот документ на них ссылается, не дублирует), [`DOCUMENT_ENGINE_ARCHITECTURE.md`](./DOCUMENT_ENGINE_ARCHITECTURE.md) (Immutable Original — используется для лекал/тех.документов ниже), [`PRINCIPLES.md`](./PRINCIPLES.md) (принцип 17 — Zero Input, принцип 19 — Immutable Original, принцип 22 — один экран/один вопрос — явно проверяется в разделе 9), `docs/MASTER_BACKLOG.md`, раздел 6 п.4 (Production Control Center / Dashboard — пересекается с разделом 15 этого документа, туда не переносится).
>
> **Статус: архитектура предложена, реализация не начата.** Владелец проекта явно сформулировал (2026-08-03): карточка модели — не CRUD-форма, а «цифровой паспорт», главный центр информации по изделию. Как и `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`, код не пишется до утверждения.
>
> **Главное правило проекта (зафиксировано владельцем дословно, повторяется здесь, чтобы не потерялось):** GarmentOS — система для селлера, полностью размещающего пошив на аутсорсе, не MES/ERP для фабрики. Каждое решение в этом документе проверено вопросом «нужно ли это селлеру, который не шьёт сам» — там, где предлагается что-то, выходящее за эту рамку, это отмечено явно.

## 0. Что уже есть — почти всё нужное уже спроектировано, просто разрозненно

Хорошая новость, прежде чем список нового: большая часть запрошенного уже существует как данные, просто не собрана на одном экране.

| Запрошено | Уже есть |
|---|---|
| Артикул, название, коллекция, сезон, категория, статус | `products` (`code`, `name`, `collectionId`, `season`, `category`, `status: draft/active/discontinued`) |
| SKU, размер, цвет, штрихкод | `product_variants` (`size`, `color`, `skuCode`, `barcode`) |
| Утверждённая спецификация (BOM) | `boms`/`bom_items`, версии, статус `draft/approved/archived` |
| Версии модели (v1/v2/v3) | **Уже есть, просто не показывается** — `boms.version` **уже автоинкрементируется** при каждом новом черновике BOM (`createBomDraft`, `existingCount + 1`) — «Худи Base v2» это буквально BOM версии 2 этой модели, ничего создавать не нужно, только вывести на экран (раздел 4) |
| Документы (лекала, сертификаты, договоры) | `documents`/`document_links` (Immutable Original, полиморфная связь) — уже спроектированный универсальный механизм |
| История изменений | `audit_log` (`entityType='product'`/`'bom'`) — уже пишется для критичных операций (Итерация 6) |
| История брака по модели | `production_orders.productId` → (после утверждения `batch_defects`, `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`) — уже достаточно связей, чтобы отфильтровать «весь брак этой модели», новых таблиц не требуется |
| История закупок по модели | `bom_items.materialId` → `purchase_order_items` (уже хранит цену/дату/поставщика) — read-model, не новая таблица |

Реально новое — 6 пунктов ниже (разделы 1-6), и один явный организационный принцип (раздел 9).

## 1. Фото — соглашение, не новая таблица

`documents` уже поддерживает произвольный `docType` (свободный текст, как `batch_defects.category` — рекомендованный словарь, не enum). Для модели вводится рекомендуемый набор значений (используется UI как фильтр вкладки «Фото»): `photo_product` (изделие на белом фоне), `photo_on_model` (на модели), `photo_detail` (деталь/фурнитура крупным планом), `photo_stage_sample` / `photo_stage_launch` / `photo_stage_production` / `photo_stage_packaging` (галерея по этапам — прямой ответ на пункт владельца проекта «фотогалерея по этапам»). Связь — `document_links` (`entityType='product'`). **Ничего нового в схеме.**

## 2. SKU — статус и QR

- **QR-код — не хранится**, генерируется на клиенте из уже существующего `skuCode`/`barcode` (обычная библиотека рендера QR, без сетевого запроса) — то же самое давно принято для штрихкодов, QR ничем принципиально не отличается.
- **Новое поле `product_variants.status`** (enum `active`/`discontinued`, по умолчанию `active`) — отдельно от уже существующего `deletedAt` (soft delete). Разница важна: `discontinued` — SKU больше не шьётся, но вся история (продажи, себестоимость, брак) должна остаться видимой в отчётах; `deletedAt` — SKU создан по ошибке и должен исчезнуть отовсюду. Сегодня этой разницы нет — «сняли с производства» и «удалили по ошибке» неразличимы.

## 3. Технологическая карта и нормы расхода — три коэффициента вместо одного

`bom_items` сегодня хранит `quantityPerUnit` + `wastePercent` (отходы кроя). Владелец проекта просит различать **три разных коэффициента**, а не один — они действительно разные по смыслу и должны применяться в разных формулах:

| Коэффициент | Поле (новое/есть) | Что означает | Где применяется |
|---|---|---|---|
| Отходы кроя | `wastePercent` (есть) | Ткань уходит в обрезки при раскрое | Расчёт закупки ткани |
| **Усадка** | `shrinkagePercent` (новое, nullable, default 0) | Ткань «садится» после стирки/обработки — нужно закупить больше, чем чистый расход | Расчёт закупки ткани (только для `materialType='fabric'`, для фурнитуры не имеет смысла) |
| **Норма брака (закупочный буфер)** | `defectAllowancePercent` (новое, nullable, default 0) | Ожидаемый % брака цеха — покупаем чуть больше материала заранее, а не докупаем в спешке после факта | Расчёт закупки (MRP-lite, `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`, раздел 16) |

Итоговая формула потребности материала (уточнение раздела 16 документа про партии):
`требуется = quantityPerUnit × totalQuantity × (1 + wastePercent/100) × (1 + shrinkagePercent/100) × (1 + defectAllowancePercent/100)`.

## 4. Версии модели — уже решено, нужен только экран

Как показано в разделе 0, `boms.version` уже инкрементируется автоматически. Предлагается:
- Карточка модели показывает список всех версий BOM (не только текущую approved), с датой утверждения и автором (`audit_log`).
- **Diff между версиями** — новый read-model (не таблица): сравнение `bom_items` двух версий по `materialId` — что добавлено, что убрано, что изменилось в количестве. Отвечает прямо на пример владельца проекта («заменили молнию», «заменили ткань») — это ровно разница двух версий BOM.
- **Лекала/тех.рисунки — перевести с `products.techPackUrl` (сегодня простая текстовая ссылка, без версий) на `documents`** (`docType='pattern'`/`'tech_drawing'`, `entityType='product'`) — используя уже существующий Immutable Original + `supersedesDocumentId` (принцип 19). Это устраняет реальный, сегодня существующий пробел: обновлённое лекало сейчас просто затирает старую ссылку, история не сохраняется — с переходом на `documents` каждая версия лекала остаётся навсегда, как и остальные документы.

## 5. Таблица размеров с реальными замерами — новая таблица

`product_variants` хранит только название размера («M», «44») — не физические измерения. Новая таблица `product_size_measurements`: `id`, `product_id` (FK), `size` (совпадает с `product_variants.size`), `measurement_name` (свободный текст: «длина изделия», «ОГ», «длина рукава», «ОБ» — набор измерений разный для худи/платья/брюк, поэтому не жёсткие колонки, а гибкая пара имя/значение — тот же принцип, что `batch_defects.category`), `value_cm` (numeric), `created_by`, `auditColumns`. Одна модель — один набор измерений на каждый размер (не привязано к цвету — цвет не меняет посадку).

## 6. Себестоимость — плановая (живая) и фактическая (историческая), две разные вещи

Важное разграничение, которое стоит явно проговорить, потому что запрос описывает обе сразу как одно:

- **Фактическая себестоимость** (уже спроектирована) — `cost_entries`, запись на конкретную партию/`productVariantId`, замороженная на момент расчёта (`materialCost`/`manufacturingCost`/`logisticsCost`/`overheadCost`) — историческая правда «сколько реально стоила эта партия».
- **Плановая (расчётная) себестоимость** — **новая**, не таблица, а live read-model на карточке модели: берёт approved BOM × **текущую** цену каждого материала (последняя цена из `purchase_order_items`, тот же принцип истории цен, что уже в `DATABASE_SCHEMA.md` раздел 0b) + текущую согласованную цену пошива в активных заказах цеха + оценку логистики/маркировки (константа или последняя фактическая) → «сколько будет стоить, если запустить партию сегодня». Именно она **пересчитывается автоматически** при изменении цены ткани (владелец проекта, пункт 15) — потому что она не хранится, а вычисляется заново при каждом открытии карточки.

Обе нужны одновременно и не заменяют друг друга: плановая — для решения «сколько стоит запустить новую партию сейчас», фактическая — для реального P&L по уже проданному товару.

## 7. Материалы модели — быстрая замена с предпросмотром себестоимости

Новый use case (не мутирующий, только предпросмотр): `simulateMaterialSubstitution(bomId, oldMaterialId, newMaterialId)` — пересчитывает плановую себестоимость (раздел 6) с одним заменённым материалом, ничего не сохраняет. Кнопка «Сохранить как новую версию BOM» после предпросмотра — вызывает уже существующий `createBomDraft` (раздел 4 этого документа, версия инкрементируется сама).

## 8. Инлайн-агрегаты на карточке модели — read-models, не новые таблицы

Всё нижеперечисленное — производные данные поверх уже существующих или запланированных (`PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`) сущностей, показывается на одной странице без перехода в другой раздел (это и есть «не десять разделов», раздел 9):

- **Производство**: выпущено всего / в производстве / готово / брак / переделано / отправлено / в пути / на складе — агрегат по `production_batches.status` (после утверждения того документа) для всех партий этой модели.
- **Закупки материалов этой модели**: какая ткань, у какого поставщика, по какой цене, когда, сколько раз — `bom_items.materialId` → `purchase_order_items` (`materialId`, `supplierId` через `purchaseOrders`, `unitPrice`, `orderedAt`).
- **Брак этой модели**: по цехам, по причинам (`batch_defects.category`/`detection_stage`, отфильтровано по `production_orders.productId`).
- **Аналитика**: выручка (из `order_items` по `productVariantId` модели), количество партий, средняя фактическая себестоимость (`cost_entries`), % брака, среднее время пошива (`production_batches.closed_at` − `created_at`), лучший/худший цех по этой модели (брак% + среднее время, тот же расчёт, что KPI цеха в `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` раздел 8, но отфильтрован по одной модели), динамика продаж (`orders.orderedAt` по месяцам).

## 9. Принцип экрана — одна страница, вкладки, не переходы

Прямая проверка принципа 22 (`PRINCIPLES.md`, «один экран — один вопрос»): карточка модели формально отвечает не на один вопрос, а на «всё об этой модели» — это осознанное, явное исключение из принципа 22, а не нарушение по недосмотру (тот же ход, каким принцип 22 уже сознательно не применяется к экрану модели сегодня — см. находку в `docs/WEB_DESIGN_SYSTEM.md`, ProductDetailPage). Разрешение конфликта — не десять экранов и не один длинный скролл, а **одна страница с вкладками** (Основное / SKU и размеры / Технологическая карта / Себестоимость / Производство / Закупки / Брак / Документы / Аналитика) — переключение без перезагрузки/перехода, статус загружается один раз. Это соответствует и амоCRM/МoйСклад-паттерну, который уже выбран ориентиром (`DESIGN_SYSTEM_MAP.md`).

## 10. Что сознательно НЕ входит сюда — проверка «нужно ли это селлеру»

Явно исключено, хотя формально относится к «всё о модели»:
- **Управление лекалами как CAD-объектами** (векторное редактирование, автоматическая раскладка) — это функциональность CAD/PLM-систем для фабрик, а не для селлера, который лекало только хранит и передаёт цеху файлом.
- **Пооперационный учёт пошива** (сколько времени на каждую строчку/операцию) — это MES-уровень фабрики, селлеру нужен только факт «в работе / готово / срок», уже покрыто `production_batches.status`/`progress_percent`.

## 11. Связь с Dashboard / Production Control Center

Раздел 8 этого документа (аналитика по модели) — частный случай уже зафиксированного, но неутверждённого предложения `docs/MASTER_BACKLOG.md`, раздел 6, п.4 («Центр управления производством», включая денежный поток/кассовый разрыв, дашборд «что требует внимания сегодня» — новые пункты 16-17 из последнего сообщения владельца проекта). **Этот документ не пытается спроектировать весь дашборд** — он слишком велик, чтобы не потерять качество внутри карточки модели. Как только карточка модели и `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` утверждены, отдельным следующим шагом — полноценная архитектура Dashboard/Cash-Flow (денежный поток, кассовый разрыв, лучшие/худшие модели-цеха-поставщики) поверх тех же read-model'ей, уже описанных здесь и в документе про партии.

## 12. Открытые вопросы владельцу проекта

1. **Статус «новинка»** (раздел 0, `products.status`) — сегодня enum `draft/active/discontinued`. «Новинка» — это отдельное состояние (нужно расширять enum) или просто визуальная пометка «модель младше N дней», вычисляемая автоматически, без ручного статуса (Zero Input)? Предлагаю второе.
2. **Норма брака как закупочный буфер** (раздел 3, `defectAllowancePercent`) — закладывается на уровне модели (одна цифра для всех цехов) или должна учитывать, что у разных цехов разный процент брака (тогда это не свойство BOM, а параметр расчёта конкретной партии с конкретным цехом)? Предлагаю: BOM хранит значение по умолчанию, расчёт партии может его переопределить для конкретного цеха.
3. **Таблица размеров** (раздел 5) — вводится вручную один раз на модель, или должна поддерживать разные замеры для разных цветов той же модели (обычно нет, но встречается)? Предлагаю: один набор на размер, без привязки к цвету, как описано.
