## 0. Статус документа

**Утверждён владельцем проекта (2026-07-25)** — оба пункта, требовавших бизнес-решения (матрица ролей — раздел 6, онбординг компании — раздел 9), решены явно. Итерация 5 реализуется без дополнительных остановок на основании этого документа.

## 1. Схема аутентификации: JWT access + refresh

**Решение**: access-токен (JWT, короткоживущий) + refresh-токен (непрозрачный, долгоживущий, хранится на сервере) — классическая пара, уже зафиксированная в `ARCHITECTURE.md`.

| Параметр | Значение | Обоснование |
|---|---|---|
| Алгоритм подписи | HS256, общий секрет | Симметричный ключ достаточен для монолита с одним издателем токенов (нет отдельных сервисов, которым нужно проверять токен без доступа к секрету). `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` уже зарезервированы в `.env.example` — решение согласуется с уже заложенной конфигурацией |
| TTL access-токена | 15 минут | Короткий срок жизни — основная защита: даже если токен скомпрометирован, окно атаки мало. Компенсируется тем, что клиент обязан молча обновлять токен через refresh |
| TTL refresh-токена | 30 дней, скользящее окно (обновляется при каждом refresh) | Пользователь не должен логиниться каждый день; 30 дней — стандартная практика для B2B-систем с невысокой чувствительностью к сессии |
| Payload access-токена | `sub` (userId), `companyId`, `roles` (массив кодов ролей) | **Не** кладём права (permissions) в токен — см. раздел 4. Роли меняются редко и это допустимый компромисс — гранулярные права пересчитываются на каждый запрос из БД/кэша, а не из токена |
| Ротация refresh-токена | При каждом `POST /auth/refresh` старый refresh-токен помечается использованным, выдаётся новый (refresh token rotation) | Стандартная защита от повторного использования украденного refresh-токена (см. раздел 2) |

## 2. Где хранится refresh-токен

**Решение**: в PostgreSQL, новая таблица `refresh_tokens` (домен Identity & Access, `packages/domain/identity`) — **не** в Redis.

Обоснование: refresh-токен — это состояние с требованием долговременной согласованности (отзыв должен быть надёжным даже после перезапуска Redis/потери кэша) — по принципу 14 (`PRINCIPLES.md`, Local-First: «собственная БД — единственный источник истины»), Redis у нас — кэш и очереди, а не хранилище состояния безопасности. Postgres уже источник истины для всего домена Identity.

Проектируемая структура (миграция, не код — будет реализована в самой Итерации 5):

| Поле | Назначение |
|---|---|
| `id` | PK |
| `user_id` | FK → `users.id` |
| `token_hash` | SHA-256 хэш токена (сам токен не хранится — если утечёт БД, токены нельзя использовать напрямую) |
| `family_id` | Идентификатор «семьи» токенов одной сессии логина — при обнаружении повторного использования уже отработанного токена отзывается вся семья (защита от кражи refresh-токена, см. ниже) |
| `issued_at`, `expires_at` | Срок действия |
| `revoked_at` | NULL, если активен |
| `replaced_by_id` | Ссылка на токен, которым заменён при ротации (аудит цепочки) |

**Reuse detection**: если приходит `refresh` с токеном, у которого `revoked_at IS NOT NULL` (то есть уже был использован раньше) — это сигнал кражи токена (два клиента используют один и тот же refresh одновременно). Реакция: отозвать всю `family_id` разом, потребовать полный повторный логин. Это стандартная практика (OAuth 2.0 Refresh Token Rotation, RFC 6749 best practices), реализуется как один SQL-запрос в use case, без внешних зависимостей.

## 3. Хранение паролей

**Решение**: оставить `scrypt` через `node:crypto` (`apps/api/src/identity/password-hasher.ts`), уже реализованный в Итерации 4 как временное решение — **перевести из статуса «заглушка» в статус «окончательное решение»**.

Обоснование (принцип 5, `PRINCIPLES.md` — Boring Technology): `scrypt` — принятый OWASP медленный KDF, входит в стандартную библиотеку Node.js без внешних зависимостей. Альтернатива (`argon2`) требует нативной компиляции (`node-gyp`) — а инфраструктура GarmentOS осознанно cloud-agnostic и должна одинаково работать на self-hosted серверах разной конфигурации (`docs/INFRASTRUCTURE.md`); нативный биндинг — дополнительный источник проблем сборки без значимого выигрыша в безопасности для наших требований. Если позже появятся конкретные аудиторские/комплаенс-требования к конкретному алгоритму — пересматривается отдельным ADR (принцип 3, эволюционная архитектура).

## 4. Роли

Схема БД уже спроектирована в Итерации 2 (`packages/db-schema/src/schema/identity.ts`): `roles` (глобальные предустановленные — `company_id IS NULL` — или кастомные ролью компании), `permissions`, `role_permissions`, `user_roles` (many-to-many — пользователь может иметь несколько ролей, что важно для маленьких компаний, где один человек закрывает 2-3 зоны ответственности — `PROJECT_VISION.md`, раздел 3).

**Решение владельца проекта (2026-07-25)**: MVP поставляется с 7 предустановленными глобальными ролями (`company_id = NULL`) — не 1:1 с персонами `PROJECT_VISION.md`, а укрупнённо, под реальные зоны ответственности маленькой команды:

| Код роли | Название | Зона ответственности |
|---|---|---|
| `owner` | Владелец | Полный доступ, включая системные настройки (управление пользователями/ролями) |
| `director` | Директор | Полный доступ ко всем бизнес-модулям, кроме системных настроек |
| `accountant` | Бухгалтер | Финансы (чтение+запись), чтение остального для расчёта себестоимости и сверки |
| `procurement_manager` | Менеджер закупок | Материалы/поставщики/закупки **и** цеха-подрядчики/заказы пошива (закупка ткани и размещение заказа в цех — одна зона ответственности в малой команде) |
| `marketplace_manager` | Менеджер маркетплейсов | Каталог моделей/SKU, карточки и остатки на WB/Ozon, заказы с маркетплейсов |
| `warehouse_keeper` | Кладовщик | Склад, приёмка/отгрузка/инвентаризация, применение кодов маркировки |
| `viewer` | Просмотр | Только чтение везде, без единого права на запись |

**Принципиальное правило (обязательно для реализации)**: роли — это **исключительно данные** (строка в `roles` + набор строк в `role_permissions`), не перечисление в коде. Прикладной код (guard'ы, use case, контроллеры) не имеет права ветвиться по `role.code` (`if (role === 'director')`) — единственная проверка в коде: «есть ли у текущего пользователя permission X», где X получен агрегированием permissions всех ролей пользователя. Это даёт то, что прямо потребовал владелец проекта: роль можно завести, переименовать или изменить набор прав без единой правки кода — обычной миграцией данных в `roles`/`role_permissions`, в том числе на уровне конкретной компании (кастомная роль, `roles.company_id = <company>`), что уже поддерживается схемой.

Отсутствие отдельной роли под BOM/спецификации (например, «технолог») — осознанно: в 7-ролевой модели `bom.write`/`bom.approve` предустановлены только `owner`/`director` (раздел 6) — реалистично для малой команды, где спецификации либо ведёт сам владелец, либо это делегируется через кастомную роль компании, если появится выделенный технолог.

## 5. Права (permissions)

**Формат кода права**: `<module>.<action>`, где `module` — один из 11 доменных модулей (`identity`, `catalog`, `procurement`, `bom`, `contract_manufacturing`, `warehouse`, `sales`, `marketplace_integration`, `honest_sign`, `finance`, `notifications`), `action` — `read` или `write` (создание/изменение/переходы статуса — единый уровень, не дробим на create/update/delete: в доменных use case и так дискретные операции с собственными проверками инвариантов, дробить права до уровня отдельного use case — избыточная гранулярность для 7 ролей и 1-3 пилотных компаний, принцип 3).

**Одно осознанное исключение**: `bom.approve` — отдельное право от `bom.write`. Обоснование: утверждение BOM — единственный жёсткий кросс-модульный инвариант в системе (`BomApprovalPort`, без утверждённого BOM нельзя разместить заказ пошива) — кто может *создать* черновик спецификации и кто может её *утвердить* осознанно разные зоны ответственности (технолог составляет, технолог или директор утверждает) даже в MVP.

Итого: 11 модулей × `read`/`write` (22 права) + `bom.approve` = **23 права**.

## 6. Матрица permissions по ролям — утверждена (2026-07-25)

`R` = read, `W` = write, `A` = approve (только `bom`). Пусто — нет доступа вовсе (ни само право не выдано, ни соответствующие эндпоинты не видны в UI/ответах API).

| Модуль | owner | director | accountant | procurement_manager | marketplace_manager | warehouse_keeper | viewer |
|---|---|---|---|---|---|---|---|
| identity | RW | | | | | | |
| catalog | RW | RW | R | R | RW | R | R |
| procurement | RW | RW | R | RW | | R | R |
| bom | RW, A | RW, A | R | R | | | R |
| contract_manufacturing | RW | RW | R | RW | | R | R |
| warehouse | RW | RW | R | R | R | RW | R |
| sales | RW | RW | R | | RW | R | R |
| marketplace_integration | RW | RW | | | RW | | R |
| honest_sign | RW | RW | R | | | RW | R |
| finance | RW | RW | RW | | | | R |
| notifications | * | * | * | * | * | * | * |

`*` — `notifications` не подчиняется ролевой матрице: это не право на модуль, а проверка на принадлежность конкретной записи конкретному пользователю (см. раздел 7). Любой аутентифицированный пользователь читает и отмечает прочитанными **только свои** уведомления — независимо от роли.

`identity` (управление пользователями/ролями компании) — только `owner`. `director` получает `RW` на все остальные 10 модулей осознанно (в малой компании директор должен иметь возможность сделать что угодно в бизнесе, не упираясь в собственную ролевую модель — `PROJECT_VISION.md`, раздел 3: «роли — это не жёсткие должности»), но не может менять состав пользователей/ролей компании — это прерогатива `owner`.

Эта матрица — начальное состояние для предустановленных ролей, засеваемое миграцией в `roles`/`permissions`/`role_permissions` (не константа в коде — см. раздел 4). Каждая компания может переопределить её для себя через кастомную роль.

## 7. RBAC или RBAC + ABAC

**Решение: чистый RBAC**, без общей ABAC-модели.

Единственное место, где проверка выходит за пределы «есть ли у роли право на модуль» — упомянутая выше проверка владения записью в `notifications` (пользователь видит только свои уведомления). Это **не** ABAC в общем смысле (нет политик по атрибутам ресурса, нет контекстных условий времени/местоположения/etc.) — это тот же паттерн, что уже применяется во всех репозиториях с Итерации 3: `findById(companyId, id)` — проверка принадлежности по одному дополнительному полю, только не `companyId`, а `userId`. Реализуется одной строкой в use case `markNotificationRead`, изменений архитектуры не требует.

Введение полноценной ABAC (например: «кладовщик видит только свой склад», «менеджер по производству видит только назначенные ему цеха») в MVP **не проектируется** — ни один сценарий из `PROJECT_VISION.md`/`USER_JOURNEY_AUDIT.md` этого не требует. Если такой сценарий появится на практике у пилотных компаний — это будет новым, осознанным решением с отдельным ADR, а не расширением текущей реализации по ходу дела (принцип 3).

## 8. Мультитенантность на уровне авторизации

Уже сформулировано как решённый вопрос в `ARCHITECTURE.md`, раздел 6: `company_id` инжектируется через контекст запроса один раз на входе, домен и use case о нём не думают. Итерация 5 — это ровно та точка, где это становится реальностью, а не декларацией:

- `companyId` **перестаёт быть полем DTO**, присылаемым клиентом (как временно было в Итерации 4 — см. явный честный ответ на аналогичный вопрос в истории Итерации 4). Извлекается исключительно из `req.user.companyId`, куда его кладёт `JwtAuthGuard` после проверки токена.
- Во всех ~40 существующих эндпоинтах 11 модулей поле `companyId` убирается из тела запроса (Zod-схемы в `packages/shared-types`) и заменяется на `@CurrentUser()` параметр-декоратор в контроллере, передающий `companyId`/`userId` в сервис. Это механический, но не маленький рефакторинг — весь объём Итерации 5, не «заодно с чем-то ещё».
- Единственные эндпоинты, которые по определению не имеют аутентифицированного `companyId` на входе — `POST /auth/login` (публичный) и создание компании/первого пользователя (см. раздел 9 — там же открытый вопрос).

## 9. Онбординг новой компании — решено (2026-07-25): CLI, не публичный HTTP API

`PROJECT_VISION.md` (раздел 6) явно относит self-service регистрацию компаний к Фазе 2+ — в MVP этого нет. Решение: создание компании выводится из HTTP API вовсе.

Конкретные последствия для уже реализованного в Итерации 4 кода:

- `CompaniesController` (`POST /v1/companies`) **удаляется** из публичной поверхности `apps/api`. Вместо него — служебный CLI-скрипт (`apps/api/src/bootstrap-company.script.ts`, запуск `pnpm --filter @garmentos/api bootstrap-company -- --name "..." --owner-email "..." --owner-full-name "..." --owner-password "..."`), который через `NestFactory.createApplicationContext` переиспользует ту же DI-проводку (`IdentityService`), что и HTTP-контроллеры, но выполняется локально на сервере тем, кто занимается внедрением пилота — без открытого сетевого эндпоинта вообще. Создаёт компанию, первого пользователя и сразу назначает ему роль `owner` (раздел 4) — одна операция, не два отдельных шага.
- `UsersController` (`POST /v1/users`) **остаётся** в HTTP API, но становится аутентифицированным и защищённым правом `identity.write` (только `owner`, раздел 6) — это добавление новых пользователей в **уже существующую** компанию, обычная операция, не бутстрап.
- `identity.e2e.spec.ts` (Итерация 4) перестаёт быть тестом «создать компанию через HTTP» — компания в тестах создаётся напрямую в БД (как это уже делают 9 из 11 остальных e2e-наборов) или через тот же bootstrap-скрипт; тест `POST /v1/users` переписывается на аутентифицированный сценарий (логин под `owner` → создание второго пользователя).

Обоснование: меньше поверхность атаки (нет сетевого эндпоинта, создающего тенанта без всякой аутентификации), не требует придумывать и защищать отдельный bootstrap-секрет, согласуется с тем, что self-service всё равно не планируется до Фазы 2 — операционно, онбордингом пилотов и так занимается инженер/команда внедрения, для которых CLI не менее удобен, чем форма.

## 10. Аудит действий

Полноценный `audit_log` (кто/когда/что изменил, `before_json`/`after_json`) — отдельная Итерация 6 по `ROADMAP.md`, **не реализуется в Итерации 5**. Смешивать их — нарушать уже согласованный порядок итераций.

Итерация 5 обеспечивает то, что Итерации 6 понадобится: `req.user.id` доступен на каждом аутентифицированном запросе и уже сейчас пробрасывается в доменные use case как необязательный `createdBy` (заложено с Итерации 3 — ни один существующий use case не меняется).

Отдельно от `audit_log` — события самой аутентификации (успешный/неуспешный логин, обновление токена, обнаружение повторного использования refresh-токена из раздела 2) логируются структурированными логами (`NestJS Logger`, апгрейд на Pino/OpenTelemetry — Итерация 7) уже в Итерации 5: это данные о безопасности самой сессии, а не бизнес-аудит доменной операции, и логически относятся к auth-слою, а не к `audit_log`.

## 11. Сервисные аккаунты и API-ключи

**Решение: не реализуются в Итерации 5 и в MVP вообще.**

Обоснование: ни один текущий сценарий не требует, чтобы внешняя система вызывала API GarmentOS. Интеграции с маркетплейсами (Wildberries/Ozon) — исходящие: GarmentOS сам обращается к их API через `MarketplaceConnector` (`ARCHITECTURE.md`, п.5.1), используя учётные данные из `marketplace_accounts.api_credentials_encrypted` — это отдельный, уже спроектированный механизм, не связанный с аутентификацией пользователей GarmentOS. Будущий Telegram-бот Inbox (Итерация 9) по структуре монолита будет ещё одним NestJS-модулем внутри `apps/api`, вызывающим use case внутрипроцессно — ему тоже не требуется отдельный сервисный аккаунт для вызова собственного же API.

«Открытый API и партнёрская программа для интеграторов» из `PROJECT_VISION.md` (горизонт 5 лет) — это когда вопрос реально встанет: отдельный ADR на API-ключи/OAuth2 client credentials в момент появления первого внешнего интегратора, не раньше.

## 12. Готовность к будущим интеграциям (WB, Ozon)

Аутентификация пользователей (этот документ) и хранение учётных данных маркетплейсов (`marketplace_accounts.api_credentials_encrypted`, реализовано в Итерации 4) — уже два независимых механизма, что и требуется: смена одного не задевает другой.

Найден смежный, но отдельный от auth пробел: `apiCredentialsEncrypted` сейчас в `apps/api` принимается и хранится как есть — реального шифрования при записи нет, несмотря на название поля (комментарий-заглушка в схеме БД: «Зашифровано на уровне приложения»). Это не относится к Итерации 5 (это не аутентификация пользователя), но требует отдельной короткой задачи — симметричное шифрование (AES-256-GCM) с мастер-ключом из переменной окружения перед реализацией Wildberries-коннектора (Итерация 10), иначе секреты маркетплейсов пилотов будут храниться в открытом виде в БД. Фиксирую здесь, чтобы не потерялось, реализуется отдельно от RBAC.

## 13. Готовность к AI-инициированным действиям (Inbox, будущий AI Production Assistant)

Владелец проекта явно зафиксировал правило на будущее (2026-07-25): **AI не должен обладать собственными правами**. Это не новое ограничение для Итерации 5, а прямое следствие уже принятого принципа 15 (`PRINCIPLES.md`, AI-First) и паттерна draft-first, которым построены все use case с Итерации 3 — здесь оно явно закрепляется применительно к Auth:

- В модели ролей/permissions (разделы 4-6) **нет и не будет** роли или сервисного аккаунта «AI» — решение раздела 11 (никаких сервисных аккаунтов) распространяется и на AI-модули без исключений.
- Любое действие, инициированное AI (Inbox — Итерация 9; будущий AI Production Assistant — расчёт спецификаций/материалов из текста/голоса, см. `docs/ROADMAP.md`, Фаза 2), выполняется **строго от имени аутентифицированного человека**, который его подтвердил (тот же JWT/сессия, те же permissions — не отдельный путь авторизации для «запросов от AI»). Технически это уже гарантировано архитектурой Inbox (`docs/INBOX_ARCHITECTURE.md`, раздел 2: AI создаёт черновик/предложение, человек подтверждает одним нажатием — подтверждение вызывает тот же самый use case, что и ручной ввод) — Итерации 5 достаточно не создавать альтернативный путь авторизации в обход этого правила.
- **Требование к будущей Итерации 6** (`audit_log`, не реализуется сейчас, фиксируется, чтобы не потерять к моменту проектирования): запись аудита AI-подтверждённого действия должна прослеживать три разных факта — (1) кто из пользователей подтвердил (уже есть, `audit_log.user_id`), (2) что именно предложил AI (нужна nullable-ссылка `audit_log.inbox_suggestion_id → inbox_suggestions.id`, где уже хранится предложенное действие и предзаполненные поля), (3) что было выполнено фактически (`before_json`/`after_json`, уже спроектировано). Это добавление одного nullable FK при проектировании Итерации 6, не архитектурное изменение.

## 14. Что войдёт в реализацию Итерации 5

1. Миграция: таблица `refresh_tokens` + сид 7 предустановленных ролей и 23 permissions (разделы 4-6) в `packages/db-schema`.
2. `packages/domain/identity`: новые доменные сущности/use case — `authenticateUser` (проверка email+пароль), управление ролями пользователя, `RefreshTokenRepository`/`RoleRepository`/`PermissionRepository` порты.
3. `apps/api/src/auth/`: `AuthController` (`/auth/login`, `/auth/refresh`, `/auth/logout`), `JwtAuthGuard`, `PermissionsGuard` + `@RequirePermissions(...)` декоратор, `@CurrentUser()` декоратор. Резолюция прав пользователя — короткий Redis-кэш (TTL 60 секунд) поверх join-запроса `user_roles → role_permissions`, инвалидируется явно при изменении ролей пользователя (не источник истины — только защита от лишней нагрузки на БД на каждый запрос).
4. `apps/api/src/bootstrap-company.script.ts` — CLI-бутстрап компании (раздел 9), удаление `CompaniesController` из HTTP-поверхности.
5. Рефакторинг всех 11 существующих модулей `apps/api`: удаление `companyId` из тел запросов, простановка `@RequirePermissions`/`@CurrentUser()` на каждый контроллер согласно матрице раздела 6; `UsersController` — переход на `identity.write`.
6. Rate-limiting на `/auth/login` (`@nestjs/throttler`) — базовая защита от перебора паролей.
7. E2e-тесты на реальном Postgres по уже устоявшемуся паттерну Итерации 4: логин → доступ с правильной ролью → 403 без нужного permission → 401 без токена → refresh → reuse detection → logout.
