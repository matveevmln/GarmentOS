# Стандарты качества GarmentOS

> Конкретизация принципов из [`PRINCIPLES.md`](./PRINCIPLES.md) в проверяемые правила. Если правило нельзя проверить автоматически или ревью — это пожелание, а не стандарт, и его нужно либо доработать, либо убрать отсюда.

## 1. Definition of Done для любой фичи/PR

Фича не считается завершённой, пока не выполнено всё:

- [ ] Код проходит `lint` и `typecheck` без подавления ошибок (`// eslint-disable` требует комментария с обоснованием и ревью).
- [ ] Написаны unit-тесты для доменной логики (application/domain слои) и минимум один интеграционный/e2e тест для сквозного сценария, если фича его затрагивает.
- [ ] Обновлена релевантная документация (`docs/ARCHITECTURE.md`, `docs/DATABASE_SCHEMA.md`, глоссарий в `CLAUDE.md`), если фича меняет модель, схему или контракт.
- [ ] Миграции БД (если есть) — обратимые (`down`-миграция присутствует) и проверены на копии продовых данных перед мержем в `main` (после появления прод-данных).
- [ ] Для полей/операций с ПДн или финансовыми/маркировочными данными — явно проверено соответствие принципу 10 из `PRINCIPLES.md`.
- [ ] Минимум одно ревью от другого разработчика (человека), даже если CI зелёный.

## 2. Тестирование

| Уровень | Инструмент | Что покрывает | Требование |
|---|---|---|---|
| Unit | Vitest | Доменная логика, use cases, утилиты | Обязательно для каждого доменного модуля; целевое покрытие критичной логики (расчёт себестоимости, списание остатков, статусы кодов маркировки) — **100% ветвлений**, не общий процент ради процента |
| Интеграционные | Vitest + тестовая БД (docker) | Репозитории, взаимодействие модулей через application services | Обязательно для каждого нового endpoint'а API |
| Контрактные | Мок-серверы на основе OpenAPI-спецификаций внешних API | Коннекторы маркетплейсов и ГИС МТ | Обязательно перед подключением реального внешнего API — минимизирует риск сломать интеграцию из-за смены контракта |
| E2E | Playwright | Ключевые пользовательские сценарии (создание производственного заказа → приёмка на склад → продажа) | Обязательно для сценариев из `ARCHITECTURE.md`, раздел 4 |

**Изоляция тестовой БД (закрыто 2026-08-02, `ARCHITECTURE_REVIEW.md`, находка 2.3)**: интеграционные/e2e-тесты `apps/api` никогда не подключаются к той же базе, что обычная разработка или прод, даже если в `.env` указан один и тот же базовый `DATABASE_URL`. `apps/api/vitest.setup.ts` подставляет суффикс `_test` к имени базы данных до того, как любой `*.spec.ts`-файл успевает прочитать переменную окружения (dotenv не переопределяет уже установленную переменную, поэтому собственный `config(...)` каждого spec-файла не может её перезаписать обратно). Это защищает не только от загрязнения БД тестовым мусором, но и от сценария «кто-то по ошибке прогнал `pnpm test` с `.env`, указывающим на Railway» — тестовый прогон физически не может задеть prod-данные, потому что подключается к другому имени базы на любом хосте, включая Railway.

**Явная позиция по покрытию**: процент покрытия строк — не самоцель. Обязательное требование — покрытие *критичных инвариантов* (нельзя продать больше остатка, нельзя погасить код маркировки дважды, себестоимость не может быть отрицательной). CI проверяет наличие тестов на такие инварианты через ревью, не только через coverage-порог, но общий порог по проекту фиксируется на уровне **не ниже 80%** для доменного слоя как защитный минимум.

## 3. CI Gates (обязательны для мержа в `main`)

1. `pnpm lint` — без ошибок.
2. `pnpm typecheck` — без ошибок (TypeScript strict mode).
3. `pnpm test` — все тесты зелёные.
4. `pnpm build` — все приложения и пакеты монорепо собираются.
5. Проверка миграций БД (dry-run применения на чистой тестовой базе).
6. Проверка на утечку секретов (сканирование diff на паттерны ключей/токенов) перед мержем.

Ни один gate не отключается точечно ради конкретного PR («на этот раз пропустим») — если gate мешает регулярно, его пересматривают как правило, а не обходят разово.

## 4. Код-ревью

- Минимум один аппрув от человека, знакомого с затронутым модулем.
- Ревьюер обязан проверить: соответствие границам модуля (`REPOSITORY_STRUCTURE.md`), соответствие терминологии (глоссарий `CLAUDE.md`), наличие тестов на инварианты, отсутствие бизнес-логики в presentation-слое.
- Значимые архитектурные отклонения от `docs/ARCHITECTURE.md`, обнаруженные в ревью — блокируют мерж до оформления ADR или отклонения изменения.

## 5. Производительность

- Целевой p95 latency для API-запросов чтения (списки остатков, каталог) — **< 300 мс** при типичном объёме данных пилотной компании (порядка 10 тыс. SKU, 100 тыс. движений склада).
- Синхронизация с маркетплейсом не должна создавать заметную нагрузку на пользовательские API-запросы (см. `ARCHITECTURE.md` п.9 — воркеры масштабируются отдельно от API).
- Любой отчётный запрос, агрегирующий более одного модуля (например, P&L по каналу), проектируется с учётом объёма данных на 3 года вперёд, а не только на текущий пилотный объём — исторические таблицы (`stock_movements`, `marking_code_events`) растут быстрее справочников.

## 6. Безопасность

- Секреты (API-ключи маркетплейсов, ГИС МТ) — только в переменных окружения/секрет-хранилище, шифруются в БД (`api_credentials_encrypted`), никогда не логируются.
- Любой новый внешний интеграционный эндпоинт проходит проверку на самые частые уязвимости (инъекции, небезопасная десериализация, SSRF при обращении к внешним URL из вебхуков).
- Доступ к данным всегда фильтруется по `company_id` — тест на «утечку между тенантами» обязателен для любого нового репозитория/запроса, читающего доменные таблицы.
- Плановый security review перед каждым релизом, который добавляет новую внешнюю интеграцию или меняет модель прав доступа.

## 7. Naming и стиль кода

- TypeScript strict mode, `noImplicitAny`, `strictNullChecks` — включены на уровне корневого `tsconfig`, наследуются всеми пакетами.
- Единый форматтер (Prettier/Biome) — форматирование не обсуждается в ревью, оно автоматическое.
- Именование сущностей и полей — строго по глоссарию `CLAUDE.md`.

## 8. Architecture Decision Records (ADR)

Любое решение, которое:
- меняет выбор из `docs/TECH_STACK.md`,
- вводит новую границу модуля или меняет существующую,
- вводит исключение из принципа в `docs/PRINCIPLES.md`,

оформляется как `docs/adr/NNNN-краткое-название.md` по стандартному шаблону (контекст → рассмотренные варианты → решение → последствия) **до** реализации, не постфактум.

## 9. Релизный процесс

- Semantic versioning для публичного API (когда он появится в Фазе 4).
- Changelog (`CHANGELOG.md` на уровне каждого `apps/*`) обновляется при каждом релизе с пользовательскими последствиями (не техническими деталями коммитов).
- Миграции БД, ломающие обратную совместимость, разворачиваются по схеме expand-migrate-contract (см. `DATABASE_SCHEMA.md`, раздел 15) минимум в двух релизах.

## 10. Что происходит, если стандарт не выполняется

Нарушение стандарта — не повод для скрытого исключения, а повод для явного решения: либо исправить перед мержем, либо задокументировать как осознанный технический долг с тикетом и сроком устранения (см. принцип «явный технический долг» в `ROADMAP.md`).

## 11. Ревью-гейт итерации (обязателен начиная с Фазы 1)

См. `docs/PRINCIPLES.md`, принцип 16. Ни одна итерация Фазы 1+ (`docs/ROADMAP.md`) не считается завершённой, пока не пройдена явная последовательность:

1. **План** — что делаем и почему именно в этом объёме (соответствует Definition of Done, раздел 1).
2. **Реализация** — код + миграции, если есть.
3. **Тесты** — согласно разделу 2.
4. **Документация** — обновление `docs/ARCHITECTURE.md`/`DATABASE_SCHEMA.md`/глоссария, если итерация меняет модель или контракт.
5. **Architecture Review** — соответствует ли реализация границам модуля (`REPOSITORY_STRUCTURE.md`), Dependency Inversion (домен не знает об инфраструктуре), не нарушен ли Local-First/мультитенантность (`ARCHITECTURE.md`, пп.6, 11).
6. **Code Review** — стандартное ревью человеком (раздел 4).
7. **Security Review** — фильтрация по `company_id` в каждом новом запросе (раздел 6), отсутствие секретов в коде, проверка новых внешних вызовов на SSRF/инъекции.
8. **Performance Review** — соответствие целевым p95 (раздел 5) там, где итерация добавляет запросы к данным, растущим быстрее справочников (`stock_movements`, `marking_code_events` и т.п., см. `DATABASE_SCHEMA.md`).
9. **UX Review** — для итераций, добавляющих/меняющих UI (`apps/web`, Inbox/Telegram-бот) или пользовательский сценарий ввода данных: проверка по критериям Zero Input (`docs/PRINCIPLES.md`, принцип 17) — клики, ручной ввод, реюз данных, авторасчёты, автозаполнение документов, авто-проверка ошибок. Для чисто доменных/API итераций без пользовательского сценария — пропускается явно, не молча.
10. **AI Review** — проверка «двери» из `ARCHITECTURE.md` п.12: может ли будущий AI-агент выполнить то же действие через уже существующий API/событие, не в обход домена? Обязательна для итераций, добавляющих новые доменные операции или события; для чисто инфраструктурных итераций (например, скелет CI) — пропускается явно.

Найденные на любом из этапов 5–10 замечания исправляются **до** перехода к следующей итерации — не копятся в бэклог "когда-нибудь". Итерация, не прошедшая ревью-гейт, не помечается завершённой в `docs/ROADMAP.md`.
