# Master Backlog — единый план развития GarmentOS

> **Назначение.** Единственное место, куда попадают все будущие задачи проекта — находки аудитов, технический долг, идеи новых модулей, пересмотры приоритетов. `docs/ROADMAP.md` остаётся источником истины по **фазам и порядку итераций**; этот документ — источник истины по **приоритету и обоснованию** внутри и поперёк итераций. Заведён 2026-08-02 по итогам первого профессионального UX-аудита прототипа (`apps/prototype`) и явного запроса владельца проекта: «не бросаться исправлять всё подряд, сначала — план».
>
> **Статус: план, реализация не начата.** Как и с `docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` — сначала документ, код только после утверждения владельцем проекта.

## 0. Как читать этот документ

Каждый пункт размечен пятью полями:

- **Этап** — куда попал и почему именно сюда.
- **Оценка времени** — грубая, в днях разработки одним агентом/разработчиком, не календарных сроках.
- **Затронутые части системы** — какие пакеты/модули меняются.
- **Риск для архитектуры** — может ли сломать существующие инварианты/контракты.
- **Более правильное решение** (если есть) — альтернатива очевидному «просто почини», когда она существенно дешевле или надёжнее.

Четыре этапа:

| Этап | Критерий попадания |
|---|---|
| **1 — До первого запуска** | Без этого систему нельзя показывать реальному пользователю как рабочую — либо она выглядит сломанной, либо создаёт неверные ожидания, либо блокирует уже запланированный по `ROADMAP.md` сквозной сценарий. |
| **2 — До первых клиентов** | Можно прожить первую неделю пилота без этого, но не дольше — иначе трение накопится и начнёт мешать. |
| **3 — После появления пользователей** | Осознанно ждёт реального использования (принцип, уже зафиксированный в `ROADMAP.md`: «новые идеи — по итогам реального использования, не заранее придуманные»). |
| **4 — Version 2.0 / масштабирование** | Рост продукта за пределы пилотов: новые каналы, новые рынки, ML. |

## 1. Важное методологическое уточнение, прежде чем читать этапы

**`apps/prototype` не патчится — он одноразовый.** Находки UX-аудита (`docs/` — см. отчёт от 2026-08-02) описывают экраны кликабельного прототипа, который по своему назначению (`docs/REPOSITORY_STRUCTURE.md`, раздел «Структура apps/prototype/») перестаёт развиваться после утверждения направления и заменяется `apps/web` (Итерация 11). Правильное действие — не чинить нерабочий поиск/фильтры внутри `apps/prototype`, а зафиксировать их как **acceptance-критерии Итерации 11** с первого дня её реализации. Единственное исключение — если владелец проекта планирует показывать именно этот прототип ещё нескольким партнёрам/инвесторам в ближайшие недели: тогда есть смысл в 2-3 самых дешёвых демо-патчах ради доверия к демонстрации (отмечено отдельно в Этапе 1 пометкой «прототип»).

## 6. Новые ERP-модули, отсутствующие в текущей архитектуре

Владелец проекта явно предложил дополнить архитектуру, если увижу пробел. Три предложения — не гипотетические, каждое привязано к конкретному разрыву в уже описанных сценариях:

1. **Возвраты с маркетплейса (`packages/domain/returns`).** `docs/ARCHITECTURE.md`/`ROADMAP.md` описывают продажу (Sales → Warehouse → Honest Sign → Finance), но не обратный путь. Для реального бренда на Wildberries возвраты — не исключение, а рутинная еженедельная операция: влияет на остаток (возврат на склад), код маркировки (повторный ввод в оборот или списание) и финансы (возврат оплаты/удержание). Без этого модуля Sales-цикл описан только наполовину. Место в roadmap — Этап 3, сразу как только пойдут первые реальные продажи (см. 3.6).

2. **Ценообразование и маржа (`packages/domain/pricing`).** Сегодня `agreedUnitPrice` в `production_orders` — это только сторона себестоимости пошива. Розничная цена на конкретном канале, скидки, маржа по SKU — нигде не смоделированы. Директор не может увидеть реальную маржинальность, не сверяя вручную несколько источников. Место — Этап 2 (2.7), раньше, чем полноценный BI Фазы 3, потому что нужен уже при управлении более чем одной активной моделью.

3. **AI Daily Briefing как отдельный, явно поименованный use case.** Не то же самое, что общий `AI Production Assistant` (расчёт спецификаций из текста) — это **другой** сценарий: периодическая (не по запросу) синтетическая сводка по реальным сигналам системы. Технически укладывается в существующий bounded context `ai-production-assistant`, но заслуживает отдельного упоминания в `AI_PRODUCTION_ASSISTANT_ARCHITECTURE.md`, потому что меняет типовой паттерн модуля с «человек попросил → AI ответил» на «AI сам решил, что стоит сказать». Первая версия — 1.15 (Этап 1), полная — 3.7 (Этап 3).

Ранее (до 2026-08-03) в этом разделе не предлагался четвёртый модуль — полноценное планирование загрузки подрядчиков — отдельным пунктом, так как он уже был в `docs/ROADMAP.md` (Фаза 3) в правильном месте, лёгкая read-витрина к нему уже учтена как 2.6.

4. **«Центр управления производством» (Production Control Center) + производственный диспетчер — предложено владельцем проекта 2026-08-03, требует явного решения, не реализовано.** В рамках работы над дизайн-системой владелец проекта запросил полноценный модуль планирования производства (мощности цехов/очередь/приоритеты/производственный календарь), автоматический пересчёт себестоимости/резервов/потребности в закупках при каждом изменении, и главный экран-дашборд («за 10 секунд понять состояние бизнеса»: партии в работе, перегруженные цеха, что купить сегодня, задержки, брак, деньги в незавершённом производстве, ожидаемая прибыль по открытым партиям). Это не доработка дизайн-системы — это новая бизнес-логика (правила приоритизации очереди, момент автоматического запуска партии при поступлении материалов, формула стоимости WIP), подпадающая под `CLAUDE.md` раздел 6, пункт 8(б) («решение, кодирующее бизнес-логику — привлекается владелец проекта явно»). Три причины не реализовывать молча в рамках текущей итерации дизайн-системы:
   - Пересекается впрямую с `docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` — тем же самым жизненным циклом партии (крой→пошив→ОТК→брак→финансовая сверка), который **сам ещё не утверждён** («предложено 2026-07-27, ждёт утверждения»). Строить диспетчер и авто-пересчёт поверх неутверждённой архитектуры означает дважды переделывать, если она изменится при утверждении.
   - Полноценное планирование загрузки подрядчиков уже сознательно размещено в Фазе 3 `docs/ROADMAP.md` (см. абзац выше) — этот запрос фактически предлагает поднять его в текущую итерацию, что прямо касается `CLAUDE.md` раздел 0, правило 4: «если тебя просят добавить фичу вне текущей итерации по роадмапу — сначала уточни, не преждевременно ли это».
   - Экран-дашборд («Центр управления производством») отвечает сразу на много вопросов одним экраном («что в работе», «что купить», «где брак», «сколько денег заморожено», «какая прибыль ожидается») — требует отдельной проверки на принцип 22 («Один экран — один вопрос», `docs/PRINCIPLES.md`) перед проектированием, а не берётся как есть из формулировки запроса.

   **Статус**: зафиксировано здесь как предложение, ожидающее решения владельца — не реализуется до (а) утверждения `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` и (б) явного подтверждения, что это переносится из Фазы 3 в текущую работу, а не выполняется по графику `ROADMAP.md`.

   **Дополнено 2026-08-03**: владелец проекта расширил дашборд явным денежным блоком — оплаты поставщикам/цехам/карго/фулфилменту, долги, предоплаты, остатки, **кассовый разрыв, денежный поток** — и аналитикой (лучшие/худшие модели/цеха/поставщики, % брака, средний срок производства/поставки, средняя себестоимость, динамика прибыли). Это тот же модуль, не новый — read-model поверх сущностей, которые появятся при утверждении `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` (разделы 14-25, включая график предоплаты 70/30) и `PRODUCT_MODEL_ARCHITECTURE.md` (раздел 8 — аналитика по модели). Полная архитектура этого дашборда/денежного потока — намеренно отдельный, следующий шаг **после** утверждения этих двух документов (`PRODUCT_MODEL_ARCHITECTURE.md`, раздел 11), не проектируется одновременно с ними, чтобы не потерять качество.

### 10.3. Дешевле, чем кажется: Cash Flow не требует нового модуля

`finance` уже хранит всё необходимое: `invoices` (`amount`, `due_date`, `status`, привязка к заказу/закупке/партии) и `transactions` (`type: income/expense`, `reference_type`/`reference_id`, `occurred_at`, `created_by` — по конвенции аудит-полей на каждой таблице). «Долг цеху» = `invoices.amount − SUM(transactions по этому же reference)`; «аванс поставщику» = обычная `expense`-транзакция, случившаяся раньше приёмки. Единственное реальное расширение схемы — добавить `transactions.method` (`cash/bank_transfer/card`, для различения «наличная доплата» от банковского перевода, как показано в прототипе) и договорить набор значений `invoices.status` (`unpaid/partially_paid/paid/overdue`). Всё остальное — read-model и экран в `apps/web`, не новый bounded context. Ошибочный путь — проектировать отдельный модуль «Cash Flow» с нуля, дублируя то, что уже есть в `finance`.

### 10.4. Требует явного решения владельца — не реализуется молча

1. **Создание новой компании через UI-форму** (упомянуто в списке примеров CRUD) **противоречит уже принятому решению**: онбординг компании — только через CLI-бутстрап, HTTP-эндпоинт `POST /companies` намеренно удалён (`AUTH_ARCHITECTURE.md`, раздел 9; `PROJECT_VISION.md` — self-service регистрация — Фаза 2+). Сейчас в системе одна реальная компания. **Рекомендация: не строить UI создания компании в Итерации 11** — решение остаётся в силе, пока не появится вторая реальная компания и вместе с ней реальный повод для self-service. Если нужно другое — это явный пересмотр архитектурного решения (`CLAUDE.md`, раздел 6, пункт 8), а не часть Итерации 11 по умолчанию.
2. **Управляемые справочники «валюта» и «способ оплаты» как произвольные пользовательские сущности.** Валюта уже — сознательно фиксированное бизнес-правило (`PRINCIPLES.md`, №21: KGS для учёта, RUB для спецификаций цеху), не открытый список для добавления новых валют пользователем — расширение до полноценного мультивалютного справочника не обосновано текущим масштабом (одна страна закупки, один язык спецификаций). **Рекомендация: не строить общий CRUD «валюты»/«способы оплаты»** — способ оплаты закрывается одним enum-полем `transactions.method` (см. 10.3), валюта остаётся правилом принципа 21. Пересмотреть, если реально появится вторая страна пошива с другой валютой спецификации — тогда это ADR, не расширение по инерции.

### 10.5. Прямой ответ на главный вопрос

**Сможет ли владелец завтра начать работать без программиста?** Нет — не потому, что архитектура слабая (она, наоборот, необычно глубоко продумана для этой стадии — RBAC, полная связанность документов, неизменность оригиналов, Zero Input были спроектированы заранее, а не постфактум), а потому, что `apps/web` — единственный слой, где всё перечисленное становится доступно человеку без Postgres-клиента, — ещё не начат. Backend готов гораздо основательнее, чем можно понять по прототипу (`apps/prototype`), который сознательно ничего не вызывает по-настоящему (см. `docs/MASTER_BACKLOG.md`, раздел 1). Точный порядок до этого момента — Этап 1 этого документа целиком.
