# Master Backlog — единый план развития GarmentOS

> **Назначение.** Единственное место, куда попадают все будущие задачи проекта — находки аудитов, технический долг, идеи новых модулей, пересмотры приоритетов. `docs/ROADMAP.md` остаётся источником истины по **фазам и порядку итераций**; этот документ — источник истины по **приоритету и обоснованию** внутри и поперёк итераций. Заведён 2026-08-02 по итогам первого профессионального UX-аудита прототипа (`apps/prototype`) и явного запроса владельца проекта: «не бросаться исправлять всё подряд, сначала — план».
>
> **Статус: план, реализация не начата.** Как и с `docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` — сначала документ, код только после утверждения владельцем проекта.

## 0. Как читать этот документ

Каждый пункт размечен пятью полями:

- **Этап** — куда попал и почему именно сюда.
- **Оценка времени** — грубая, в днях разработки одним агентом/разработчиком, не календарных сроках.
- **Затронутые части системы** — какие пакеты/модули меняются.
- **Риск для архитектуры** — может ли сломать существующие инварианты/контракты.
- **Более правильное решение** (если есть) — альтернатива очевидному «просто почини», когда она существенно дешевле или надёжнее.

Четыре этапа:

| Этап | Критерий попадания |
|---|---|
| **1 — До первого запуска** | Без этого систему нельзя показывать реальному пользователю как рабочую — либо она выглядит сломанной, либо создаёт неверные ожидания, либо блокирует уже запланированный по `ROADMAP.md` сквозной сценарий. |
| **2 — До первых клиентов** | Можно прожить первую неделю пилота без этого, но не дольше — иначе трение накопится и начнёт мешать. |
| **3 — После появления пользователей** | Осознанно ждёт реального использования (принцип, уже зафиксированный в `ROADMAP.md`: «новые идеи — по итогам реального использования, не заранее придуманные»). |
| **4 — Version 2.0 / масштабирование** | Рост продукта за пределы пилотов: новые каналы, новые рынки, ML. |

## 0.5. Pilot v1 — текущий приоритет проекта (зафиксировано 2026-08-04)

**Переименовано владельцем проекта явно**: следующий этап называется не «Railway» (техническая задача), а **Pilot v1** — первый Production Sprint. Ровно четыре цели, ничего сверх них:

1. Деплой на Railway (production-ready, не «работает на глаз» — `infra/PRODUCTION_CHECKLIST.md`).
2. Первая настоящая компания владельца проекта — не демо, без тестовых данных (`bootstrap-company.script.js`, не `seed-demo.script.js`).
3. **2–3 настоящие модели и 2 настоящих цеха**, не одна модель/один цех — расширено владельцем проекта: разные нормы расхода ткани, разные цены пошива, разные условия договора и сроки вскрывают ошибки, которые не проявляются на единственном сценарии.
4. Первая настоящая производственная партия — полный цикл своими руками: создание партии → спецификация → PDF → отправка бухгалтеру цеха → предоплата 70% → закупка ткани → закупка фурнитуры → передача материалов → крой → пошив → упаковка → фулфилмент → ОТК → возврат брака (если есть) → повторное производство → Red Express → получение документов → прибытие партии.

**Главное правило, начиная с этого момента** (дословно, владелец проекта): *«Приоритетом становится не количество нового функционала, а возможность ежедневно использовать GarmentOS в реальной работе. Любая новая функция должна проходить проверку вопросом: поможет ли она провести следующую реальную партию быстрее, проще или надёжнее? Если нет — откладывать её в Backlog.»* Зафиксировано также в `CLAUDE.md`, раздел 6.

**Во время пилота новый функционал не добавляется** — каждая найденная проблема фиксируется в `docs/PILOT_LOG.md`, решения о доработках принимаются только после прохождения полного цикла одной партии, не по ходу.

### Мастер первого запуска — решение, не откладывание молча

Владелец проекта попросил экран (не скрипт) для создания компании: название, ИНН, реквизиты, подписант, печать, адрес, телефон, логотип. Решение: **для самого Pilot v1 использовать существующий `bootstrap-company.script.js`** (уже работает, уже проверен, поля названия/email/пароля владельца покрывает) — строить новый экран прямо сейчас означало бы добавлять функционал перед пилотом, что прямо противоречит правилу выше. ИНН/реквизиты/печать/логотип у `bootstrap-company` сегодня не запрашиваются — если понадобятся для реальной спецификации/договора уже в первой партии, добавить как поля `companies` и параметры скрипта (дёшево, без UI), не как повод строить экран. Настоящий экран-мастер — первый кандидат в задачи **после** прохождения пилота, если ручной CLI-запуск окажется неудобным на практике (это и предстоит увидеть в `docs/PILOT_LOG.md`), не раньше.

### Freeze архитектуры на время пилота (зафиксировано владельцем проекта, 2026-08-04)

Дословно: *«Перед Pilot v1 зафиксируй архитектуру. До окончания первой реальной партии запрещается менять схему БД, менять жизненный цикл партии и менять бизнес-процессы без крайней необходимости. Все идеи записываются в Backlog и реализуются только после завершения пилота.»*

Это ужесточение уже действующего правила «во время пилота новый функционал не добавляется» (выше) — здесь явно и отдельно названы три вещи, которые нельзя трогать даже в виде «мелкого улучшения»: схема БД (миграции), жизненный цикл партии (`docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`), бизнес-процессы (последовательность use case). «Крайняя необходимость» — это найденный в проверке выше (`Обязательно закрыто до пилота`) блокирующий баг уровня версионности спецификаций, не «было бы удобнее». Всё остальное — в этот документ или `docs/PILOT_LOG.md`, без реализации, до завершения одной полной партии (критерий — см. ниже).

### Реальные данные — запрет смешивания (зафиксировано владельцем проекта, 2026-08-04)

Дословно: *«Запрещается смешивать: тестовые модели; демо-партии; настоящие партии; реальные документы. После запуска Pilot v1 рабочая база содержит только реальные данные. Все эксперименты проводить только в отдельной dev-базе.»*

Практическое следствие: после того как `bootstrap-company.script.js` создал первую настоящую компанию на Railway-БД, в эту же БД **больше никогда** не запускается `seed-demo.script.js` (уже отмечено как «не для пилота» в `infra/PRODUCTION_CHECKLIST.md`, п.16, — здесь распространяется на весь период пилота, не только на момент до деплоя) и не создаются модели/партии «на попробовать». Любая проверка гипотезы («как это будет выглядеть, если...») — на отдельной dev/staging БД (`DATABASE_URL`, отличный от Railway production, тот же принцип изоляции, что уже действует между `pnpm test` и dev/prod — `infra/RAILWAY_DEPLOY.md`, раздел «Изоляция от локальной разработки/тестов»), никогда не в Railway production после первого реального запуска.

### Критерий завершения Pilot v1 (зафиксировано владельцем проекта, 2026-08-04)

Дословно: *«Pilot закончен тогда и только тогда, когда одна настоящая партия пройдёт весь цикл: Спецификация → Оплата → Закупка → Передача → Крой → Пошив → Фулфилмент → ОТК → Red Express → Москва → Закрытие партии без Excel.»*

Явно **не** метрика успеха: количество экранов, количество коммитов, количество реализованных модулей. Единственный критерий — одна реальная партия, полностью проведённая через систему, без единой таблицы Excel как параллельного источника истины на каком-либо шаге. До этого момента Pilot v1 не считается завершённым, независимо от того, сколько дополнительных инструментов (Dashboard, Recovery, Audit и т.д.) уже готово — эти инструменты обслуживают прохождение партии, они не заменяют его как критерий.

### «Теперь мы им пользуемся» (зафиксировано владельцем проекта, 2026-08-04)

Дословно: *«Теперь мы не разрабатываем GarmentOS. Теперь мы им пользуемся. Каждое улучшение должно рождаться из реальной работы с системой, а не из предположений.»*

Психологический и операционный переход, а не просто ещё одно правило приоритизации: с начала Pilot v1 источник следующих задач — `docs/PILOT_LOG.md` (что реально помешало провести партию), а не гипотезы о том, что могло бы быть полезно. Это распространяется на всех, кто предлагает доработки в этот период, включая AI-агента, работающего в этом репозитории (`CLAUDE.md`, правило 9) — инициатива по улучшениям остаётся в силе, но её источник сузился с «замечено в коде» до «замечено при реальной эксплуатации».

### Dogfooding — режим работы внутри Pilot v1 (зафиксировано владельцем проекта, 2026-08-04)

Владелец проекта предложил называть этот этап не «Pilot v1», а «Dogfooding» — команда сама становится первым пользователем GarmentOS. Формальное имя фазы во всех документах остаётся **Pilot v1** (массовое переименование сейчас было бы правкой ради правки, запрещённой Freeze выше) — «Dogfooding» фиксируется здесь как дух этапа: с этого момента мы не строим GarmentOS, мы живём внутри него.

Три практических следствия, действующих до конца Pilot v1:

1. **Правило «никакого Excel».** Дословно: *«Нельзя пользоваться Excel, если ту же операцию можно выполнить в GarmentOS. Даже если в GarmentOS пока неудобнее.»* Неудобство — повод завести строку в `docs/PILOT_BUGS.md`, не повод обойти систему; иначе именно те проблемы, ради обнаружения которых существует пилот, останутся незамеченными.
2. **`docs/PILOT_BUGS.md` — единственный журнал проблем.** Не GitHub Issues, не этот документ (`docs/MASTER_BACKLOG.md`) — во время пилота новые находки идут только туда, в строгом табличном формате (дата/партия/что делали/что ожидали/что произошло/критичность/как исправили/статус). `docs/PILOT_LOG.md` остаётся дневником вех (деплой, создание компании, смена статуса партии) — разделение объяснено в самом `docs/PILOT_LOG.md`. Этот документ (`MASTER_BACKLOG.md`) не принимает новые пункты, пока `docs/PILOT_BUGS.md` не будет разобран целиком после завершения пилота.
3. **Метки критичности и порядок исправления.** Каждая проблема в `docs/PILOT_BUGS.md` — ровно одна метка: 🔴 блокирует проведение партии, 🟡 замедляет работу, 🟢 просто неудобно. Исправление всегда сверху вниз — сначала все открытые 🔴, затем 🟡, затем 🟢, даже если 🟢 исправить быстрее.

### День запуска и Roadmap v2 (зафиксировано владельцем проекта, 2026-08-04)

Фундамент подтверждён завершённым для Pilot v1 — разработка новых возможностей остановлена до сигнала из реальной эксплуатации. Запуск на Railway — не «как получится», а отдельный явный чек-лист `docs/LAUNCH_DAY.md`: Railway развёрнут → домен → HTTPS → вход → PDF → реальная компания → реальные модели/цеха → первая партия → первая настоящая спецификация → PDF отправлен цеху → первая запись в `docs/PILOT_LOG.md`. С момента, когда отмечен последний пункт, GarmentOS перестаёт быть проектом разработки и становится рабочим инструментом.

**После завершения первой реальной партии** (критерий — раздел выше, «Критерий завершения») — полноценный разбор Pilot v1 по `docs/PILOT_BUGS.md` и `docs/PILOT_LOG.md`, и только тогда формируется **Roadmap v2**. До этого момента новых roadmap-документов не заводится.

## 1. Важное методологическое уточнение, прежде чем читать этапы

**`apps/prototype` не патчится — он одноразовый.** Находки UX-аудита (`docs/` — см. отчёт от 2026-08-02) описывают экраны кликабельного прототипа, который по своему назначению (`docs/REPOSITORY_STRUCTURE.md`, раздел «Структура apps/prototype/») перестаёт развиваться после утверждения направления и заменяется `apps/web` (Итерация 11). Правильное действие — не чинить нерабочий поиск/фильтры внутри `apps/prototype`, а зафиксировать их как **acceptance-критерии Итерации 11** с первого дня её реализации. Единственное исключение — если владелец проекта планирует показывать именно этот прототип ещё нескольким партнёрам/инвесторам в ближайшие недели: тогда есть смысл в 2-3 самых дешёвых демо-патчах ради доверия к демонстрации (отмечено отдельно в Этапе 1 пометкой «прототип»).

## 6. Новые ERP-модули, отсутствующие в текущей архитектуре

Владелец проекта явно предложил дополнить архитектуру, если увижу пробел. Три предложения — не гипотетические, каждое привязано к конкретному разрыву в уже описанных сценариях:

1. **Возвраты с маркетплейса (`packages/domain/returns`).** `docs/ARCHITECTURE.md`/`ROADMAP.md` описывают продажу (Sales → Warehouse → Honest Sign → Finance), но не обратный путь. Для реального бренда на Wildberries возвраты — не исключение, а рутинная еженедельная операция: влияет на остаток (возврат на склад), код маркировки (повторный ввод в оборот или списание) и финансы (возврат оплаты/удержание). Без этого модуля Sales-цикл описан только наполовину. Место в roadmap — Этап 3, сразу как только пойдут первые реальные продажи (см. 3.6).

2. **Ценообразование и маржа (`packages/domain/pricing`).** Сегодня `agreedUnitPrice` в `production_orders` — это только сторона себестоимости пошива. Розничная цена на конкретном канале, скидки, маржа по SKU — нигде не смоделированы. Директор не может увидеть реальную маржинальность, не сверяя вручную несколько источников. Место — Этап 2 (2.7), раньше, чем полноценный BI Фазы 3, потому что нужен уже при управлении более чем одной активной моделью.

3. **AI Daily Briefing как отдельный, явно поименованный use case.** Не то же самое, что общий `AI Production Assistant` (расчёт спецификаций из текста) — это **другой** сценарий: периодическая (не по запросу) синтетическая сводка по реальным сигналам системы. Технически укладывается в существующий bounded context `ai-production-assistant`, но заслуживает отдельного упоминания в `AI_PRODUCTION_ASSISTANT_ARCHITECTURE.md`, потому что меняет типовой паттерн модуля с «человек попросил → AI ответил» на «AI сам решил, что стоит сказать». Первая версия — 1.15 (Этап 1), полная — 3.7 (Этап 3).

Ранее (до 2026-08-03) в этом разделе не предлагался четвёртый модуль — полноценное планирование загрузки подрядчиков — отдельным пунктом, так как он уже был в `docs/ROADMAP.md` (Фаза 3) в правильном месте, лёгкая read-витрина к нему уже учтена как 2.6.

4. **«Центр управления производством» (Production Control Center) + производственный диспетчер — предложено владельцем проекта 2026-08-03, требует явного решения, не реализовано.** В рамках работы над дизайн-системой владелец проекта запросил полноценный модуль планирования производства (мощности цехов/очередь/приоритеты/производственный календарь), автоматический пересчёт себестоимости/резервов/потребности в закупках при каждом изменении, и главный экран-дашборд («за 10 секунд понять состояние бизнеса»: партии в работе, перегруженные цеха, что купить сегодня, задержки, брак, деньги в незавершённом производстве, ожидаемая прибыль по открытым партиям). Это не доработка дизайн-системы — это новая бизнес-логика (правила приоритизации очереди, момент автоматического запуска партии при поступлении материалов, формула стоимости WIP), подпадающая под `CLAUDE.md` раздел 6, пункт 8(б) («решение, кодирующее бизнес-логику — привлекается владелец проекта явно»). Три причины не реализовывать молча в рамках текущей итерации дизайн-системы:
   - Пересекается впрямую с `docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` — тем же самым жизненным циклом партии (крой→пошив→ОТК→брак→финансовая сверка), который **сам ещё не утверждён** («предложено 2026-07-27, ждёт утверждения»). Строить диспетчер и авто-пересчёт поверх неутверждённой архитектуры означает дважды переделывать, если она изменится при утверждении.
   - Полноценное планирование загрузки подрядчиков уже сознательно размещено в Фазе 3 `docs/ROADMAP.md` (см. абзац выше) — этот запрос фактически предлагает поднять его в текущую итерацию, что прямо касается `CLAUDE.md` раздел 0, правило 4: «если тебя просят добавить фичу вне текущей итерации по роадмапу — сначала уточни, не преждевременно ли это».
   - Экран-дашборд («Центр управления производством») отвечает сразу на много вопросов одним экраном («что в работе», «что купить», «где брак», «сколько денег заморожено», «какая прибыль ожидается») — требует отдельной проверки на принцип 22 («Один экран — один вопрос», `docs/PRINCIPLES.md`) перед проектированием, а не берётся как есть из формулировки запроса.

   **Статус**: зафиксировано здесь как предложение, ожидающее решения владельца — не реализуется до (а) утверждения `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` и (б) явного подтверждения, что это переносится из Фазы 3 в текущую работу, а не выполняется по графику `ROADMAP.md`.

   **Дополнено 2026-08-03**: владелец проекта расширил дашборд явным денежным блоком — оплаты поставщикам/цехам/карго/фулфилменту, долги, предоплаты, остатки, **кассовый разрыв, денежный поток** — и аналитикой (лучшие/худшие модели/цеха/поставщики, % брака, средний срок производства/поставки, средняя себестоимость, динамика прибыли). Это тот же модуль, не новый — read-model поверх сущностей, которые появятся при утверждении `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md` (разделы 14-25, включая график предоплаты 70/30) и `PRODUCT_MODEL_ARCHITECTURE.md` (раздел 8 — аналитика по модели). Полная архитектура этого дашборда/денежного потока — намеренно отдельный, следующий шаг **после** утверждения этих двух документов (`PRODUCT_MODEL_ARCHITECTURE.md`, раздел 11), не проектируется одновременно с ними, чтобы не потерять качество.

   **Дополнено 2026-08-03 (второй раз, тот же день)**: владелец проекта сузил и уточнил один конкретный экран внутри этого дашборда — **«Паспорт партии»** (рабочее название владельца, альтернативы: «Экономика партии»/«Калькулятор партии») — карточка одной конкретной производственной партии (не сводный дашборд по всем партиям сразу — значит, не подпадает под принцип 22 так же строго, как общий «Центр управления производством»): себестоимость (ткань/пошив/фурнитура/упаковка/прочее), цена спецификации и разница, сумма всей партии, чек-лист закупок (на складе/не хватает/уже заказано — MRP-lite, `PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`, раздел 16, не реализовано), график оплат (предоплата/остаток), в будущем — маржа по каналам продаж. Ключевое архитектурное требование к этому экрану: **Snapshot партии** — себестоимость считается на момент подтверждения заказа и больше никогда не пересчитывается автоматически, даже если позже изменятся цены материалов/BOM/карточка цеха (иначе «спецификация месячной давности покажет новые цены» — прямая цитата владельца проекта).

   **Реализовано 2026-08-04.** Утверждён UX-макет (desktop + mobile, публичный артефакт-превью), затем построен реальный экран `apps/web/src/pages/BatchPassportPage.tsx` (маршрут `/production-orders/:id`, открывается кликом по строке в списке заказов пошива) поверх нового агрегирующего эндпоинта `GET /production-orders/:id/passport` (`apps/api/src/reporting/batch-passport.service.ts` — тот же паттерн Reporting/BI, что и `AttentionService`/`CostingService`: композиция Contract Manufacturing + Catalog + Document Engine + Finance в одном ответе, `BatchPassportResponseDto` в `@garmentos/shared-types`). Реализованы только блоки с реальным источником данных: заголовок/статус/просрочка, «Экономика партии» (из `costSnapshot`, включая честную пустую формулировку вместо нуля, если чек ещё не подтверждён), грубый степпер статуса, «Документы» (реальный список версий спецификации + рабочая кнопка «Открыть» — попутно закрыт реальный пробел: `GET /documents/:id/file` теперь отдаёт байты PDF, раньше `fileUrl` никак не был достижим из браузера при локальном хранилище), таблица «Размеры и цвета», «История» (по факту зафиксированных событий, не выдуманная лента). «Материалы»/«ОТК»/«Логистика» показаны как честные пустые состояния с объяснением, что именно появится и от какого нереализованного раздела архитектуры это зависит — не убраны с экрана совсем, чтобы форма экрана была утверждена целиком, но и не подменены нулями. Найден и исправлен по ходу реальный дефект в самой генерации спецификаций: повторная генерация создаёт независимый документ, а не новую версию через `supersedesDocumentId` (несколько документов одновременно с `isCurrentVersion=true`) — экран определяет «текущую» версию по дате создания, а не по этому полю; сама генерация не исправлена (отдельная задача, не в объёме этого экрана). Не реализовано в этом заходе: чек-лист закупок (MRP-lite), маржа по каналам, действие «выставить счёт» прямо с экрана (Finance не имеет собственного UI в `apps/web` вообще — самостоятельный, больший пробел).

## 7. Технический долг, который стоит закрыть сейчас — пока нет реальных пользователей

1. **Разграничение `apps/prototype`/`apps/web` как процесс, не только факт.** Риск: повторно чинить то же самое дважды (один раз в прототипе ради демо, второй раз по-настоящему). Зафиксировано в разделе 1 этого документа — держать явным правилом, не разовым напоминанием.
2. **Domain Events — отложенный, теперь наступивший триггер.** `ROADMAP.md` (Итерация 3, направление развития №2) ещё 2026-07-25 предсказал: «кандидат на реализацию — при переходе к сквозному сценарию... это и есть первый реальный повод, не раньше». Лента событий и AI-брифинг (Этап 1) и полноценный Entity Timeline (Этап 2) — этот повод. Не откладывать снова без нового обоснования.
3. **Общая утилита форматирования валюты/чисел.** Смешение ₽/сом на карточке модели — не только UX-находка, но и признак того, что форматирование сумм ещё не стандартизировано как часть `packages/ui-kit`. Заложить это с первого компонента `apps/web`, не после того, как разъедется по 10 экранам.
4. **`MVP_CHECKLIST.md` схлопывается в этот документ после первого реального запуска.** Сам `MVP_CHECKLIST.md` уже фиксирует это правило («после раздела 🟡 — переход от проектирования к эксплуатации»). ### 10.3. Дешевле, чем кажется: Cash Flow не требует нового модуля

`finance` уже хранит всё необходимое: `invoices` (`amount`, `due_date`, `status`, привязка к заказу/закупке/партии) и `transactions` (`type: income/expense`, `reference_type`/`reference_id`, `occurred_at`, `created_by` — по конвенции аудит-полей на каждой таблице). «Долг цеху» = `invoices.amount − SUM(transactions по этому же reference)`; «аванс поставщику» = обычная `expense`-транзакция, случившаяся раньше приёмки. Единственное реальное расширение схемы — добавить `transactions.method` (`cash/bank_transfer/card`, для различения «наличная доплата» от банковского перевода, как показано в прототипе) и договорить набор значений `invoices.status` (`unpaid/partially_paid/paid/overdue`). Всё остальное — read-model и экран в `apps/web`, не новый bounded context. Ошибочный путь — проектировать отдельный модуль «Cash Flow» с нуля, дублируя то, что уже есть в `finance`.

### 10.4. Требует явного решения владельца — не реализуется молча

1. **Создание новой компании через UI-форму** (упомянуто в списке примеров CRUD) **противоречит уже принятому решению**: онбординг компании — только через CLI-бутстрап, HTTP-эндпоинт `POST /companies` намеренно удалён (`AUTH_ARCHITECTURE.md`, раздел 9; `PROJECT_VISION.md` — self-service регистрация — Фаза 2+). Сейчас в системе одна реальная компания. **Рекомендация: не строить UI создания компании в Итерации 11** — решение остаётся в силе, пока не появится вторая реальная компания и вместе с ней реальный повод для self-service. Если нужно другое — это явный пересмотр архитектурного решения (`CLAUDE.md`, раздел 6, пункт 8), а не часть Итерации 11 по умолчанию.
2. **Управляемые справочники «валюта» и «способ оплаты» как произвольные пользовательские сущности.** Валюта уже — сознательно фиксированное бизнес-правило (`PRINCIPLES.md`, №21: KGS для учёта, RUB для спецификаций цеху), не открытый список для добавления новых валют пользователем — расширение до полноценного мультивалютного справочника не обосновано текущим масштабом (одна страна закупки, один язык спецификаций). **Рекомендация: не строить общий CRUD «валюты»/«способы оплаты»** — способ оплаты закрывается одним enum-полем `transactions.method` (см. 10.3), валюта остаётся правилом принципа 21. Пересмотреть, если реально появится вторая страна пошива с другой валютой спецификации — тогда это ADR, не расширение по инерции.

### 10.5. Прямой ответ на главный вопрос

**Сможет ли владелец завтра начать работать без программиста?** Нет — не потому, что архитектура слабая (она, наоборот, необычно глубоко продумана для этой стадии — RBAC, полная связанность документов, неизменность оригиналов, Zero Input были спроектированы заранее, а не постфактум), а потому, что `apps/web` — единственный слой, где всё перечисленное становится доступно человеку без Postgres-клиента, — ещё не начат. Backend готов гораздо основательнее, чем можно понять по прототипу (`apps/prototype`), который сознательно ничего не вызывает по-настоящему (см. `docs/MASTER_BACKLOG.md`, раздел 1). Точный порядок до этого момента — Этап 1 этого документа целиком.
