## 3. Фактические цепочки UI → API → домен → сохранение

Проверено чтением кода (Explore/статический анализ), без запуска. Каждая цепочка — с точными путями.

### 3.1. Модель, цвета, размеры
- UI: `apps/web/src/pages/ProductsPage.tsx` (список + форма "Новая модель") → `apps/web/src/pages/ProductDetailPage.tsx` (карточка модели, "Размерный ряд", "Добавить цвет на все размеры").
- API: `POST /products`, `POST /product-variants`, размерный ряд — `product_sizes` (см. ниже).
- Домен: `packages/domain/catalog` — `createProduct`, `createProductVariant`.
- Хранение: `products`, `product_variants`, `product_sizes` (`packages/db-schema/src/schema/catalog.ts`).
- **Парные размеры и веса** — уже полноценно реализованы: `product_sizes.sortOrder` + `product_sizes.ratioWeight` (numeric, `packages/db-schema/src/schema/catalog.ts:128-129`), владелец вводит вес, не готовое количество и не процент (комментарий в схеме, строка 113).

### 3.2. Распределение количества по размерам/цветам — **уже реализован ровно тот алгоритм, что описан в требованиях**
`packages/domain/catalog/src/application/distribute-size-quantities.ts`:
- `distributeQuantityByRatio(ratios, totalQuantity)` — основной механизм, по весам модели.
- `distributeQuantityEvenly(groupCount, totalQuantity)` — равное распределение (используется для деления между цветами).
- Общий приватный `distributeByWeights` реализует **largest remainder method**: целые части (`Math.floor`), остаток раздаётся по наибольшим дробным частям, тай-брейк — по индексу в исходном порядке (строки 61-79). Проценты/веса не обязаны суммироваться в конкретное число — только пропорции.
- **Совпадение с примером из требований не случайное**: комментарий в самом коде (строка 15, 85-88) буквально приводит веса `185/381/381/381/186` — тот же пример, что в `docs/GOS-PARTY-V1.md` раздел 5, "Пример 600 изделий первого цвета". Это значит, что модель «Стеганка» с такой размерной раскладкой уже когда-то заводилась в системе (реальные тестовые/пилотные данные или тот же образец, что использовался при разработке фичи) — рекомендую уточнить у владельца, не является ли эта карточка модели уже существующей записью, которую нужно переиспользовать, а не создавать заново.
- **Вывод: пункт 5 требований ("предлагаемый алгоритм") — не предложение, а уже работающая реализация.** Использовать без переделки.

### 3.4. Заказ на пошив (production order) — **один заказ = одна модель, подтверждено на уровне схемы**
- Схема: `packages/db-schema/src/schema/contract-manufacturing.ts` — `productionOrders.productId: uuid("product_id").notNull()` (строка ~88-90) — единственный, не-nullable FK на одну модель. Позиции по SKU — в `productionOrderVariants.productVariantId`, все варианты которого принадлежат ЭТОЙ ЖЕ модели.
- shared-types: `createProductionOrderSchema` и `createProductionOrderFromQuantitySchema` (`packages/shared-types/src/contract-manufacturing/schemas.ts`) — оба берут ровно один `productId: z.string().uuid()`.
- **Вывод: сегодня один заказ технически не может содержать позиции разных моделей.** "Выбрать цех и одну или несколько моделей" (раздел 3, шаг 1 требований) на один заказ пошива — не реализуемо без изменения схемы. См. раздел 6 (архитектурный вопрос) ниже.
- **Два разных, параллельных входа создания заказа** (оба в текущем меню):
  1. `apps/web/src/pages/NewBatchWizardPage.tsx` (`/new-batch`) — старый, полный мастер: цех → материал → модель → нормы расхода (BOM) → заказ. Убран из меню 2026-09-12 ("Model-first Minimal Core"), маршрут не удалён, доступен по прямой ссылке.
  2. `apps/web/src/pages/ProductionOrdersPage.tsx` (`/production-orders`, в меню) — аккордеон "Создать производственную партию": модель → матрица цвет×размер (количество) → пресеты стоимости пошива → цех → создать. **Без BOM/материалов** (комментарий в коде: "новый визард ... не требует выбора BOM").
- Ни один из двух не требует создания фиктивных материалов, закупок или оплат для самого создания заказа (проверено: `createProductionOrderSchema`/`createProductionOrderFromQuantitySchema` не содержат обязательных полей материалов/закупок/оплат; отсутствующий BOM при создании авто-заводится пустым, невидимым пользователю — `order.bomId` всегда заполнен техническим значением). **Соответствует требованию раздела 1.**
- Инлайн-создание недостающей модели/цеха **внутри мастера заказа** (`ProductionOrdersPage.tsx`) — **отсутствует**: и модель, и цех выбираются из `Combobox` без опции "создать" (проверено: компонент `Combobox` не имеет `onCreate`/`allowCreate`, в файле нет диалога создания модели/цеха). Пользователь должен уйти на `/products` или `/workshops`, создать запись, вернуться — при этом состояние формы заказа (`useState`, не персистентное) теряется полностью.

### 3.6. Раскрой (задание + факт)
- Домен: `packages/domain/cutting` — `CuttingOrderStatus = "draft" | "issued" | "completed" | "cancelled"`, `createCuttingOrder`, `issueCuttingOrder`, `recordCuttingFact`, `cancelCuttingOrder`.
- UI: не отдельный экран — вкладка "Раскрой" внутри `BatchPassportPage.tsx`.
- **Материалы в факте кроя — необязательны**: `cuttingFactSchema` (`packages/shared-types/src/cutting/schemas.ts`) не имеет `.min(1)` на массив `materials` — пустой массив проходит валидацию; доменная проверка (`record-cutting-fact.ts`) просто не выполняет цикл при пустом массиве. **Значит фиктивный материал не нужен даже для факта кроя** — только план/факт количества по цветам/размерам. Соответствует требованию раздела 1.
- Норма расхода (`materialNorms`) фиксируется в `cost_snapshot` заказа при подтверждении и читается кроем как есть — раскрой никогда не видит "живую" карточку BOM модели (историческая память, `production-order-snapshot.adapter.ts`).
- Докрой (несколько заданий подряд на один заказ) — поддержан: `cuttingOrders.listByProductionOrder` возвращает массив, не одну запись; глоссарий `CLAUDE.md` подтверждает это явно спроектированным поведением.

### 3.7. Пошив — только статус, без даты
- `BatchPassportPage.tsx`: кнопки "Начали шить"/"Пошив завершён" меняют статус заказа (`in_progress`/`sewing_completed`) через `POST /production-orders/:id/status`.
- **Поле ожидаемой даты сдачи (или "15 дней с подсказкой") — не найдено нигде в `apps/web/src`.** Есть только общее `dueDate` на самом заказе (задаётся при создании, не изменяется отдельным действием "начали шить, ожидаем через N дней"). Требование раздела 3, шаг 7 ("указать фактический старт пошива и ожидаемую дату... 15 дней — изменяемая подсказка") **не реализовано** — нужен новый функционал (не переделка существующего).

### 3.8. Приёмка (получение на склад) — **одноразовая операция, не накопительная**
- Guard: `assertCanReceive` (`packages/domain/contract-manufacturing/src/domain/production-order.ts:259-268`) разрешает приёмку только из статусов `ready_for_pickup`/`shipped_to_fulfillment`. Комментарий в коде прямо называет `"received"` терминальным статусом ("закрытие заказа = приёмка").
- `markReceived` в Drizzle-репозитории **перезаписывает** (`.set()`, не инкремент) `receivedQuantity` каждого варианта.
- **Вывод: сегодня нельзя вызвать приёмку второй раз на том же заказе** (например, сначала пришло 600 из 1000, через неделю — оставшиеся 400). Требование раздела 3, шаг 8 ("возможны частичные получения") и S09 ("возможны частичные получения") — **не реализовано** технически, это реальный пробел, а не то, что "просто не показано в UI".
- В рамках ОДНОГО вызова приёмки допускается расхождение план/факт по количеству (`assertReceivedVariantsValid` допускает over/under-receipt) — это разовая сверка, не многократное накопление.

### 3.9. ОТК — **один результат на заказ, тоже не накопительно**
- Схема: `production_order_qc_results` — `uniqueIndex("production_order_qc_results_order_idx").on(table.productionOrderId)` (`packages/db-schema/src/schema/quality-control.ts:36`). Комментарий в файле: "не история, один финальный результат".
- **Вывод: технически по одному заказу может существовать ровно ОДНА запись ОТК, когда-либо.** Требование "возможны несколько проверок по частям" (раздел 3, шаг 9; S10) прямо противоречит текущей схеме — это не вопрос UI, а ограничение на уровне уникального индекса БД. Нужна миграция схемы (либо снять уникальность и ввести агрегирование "накопленные годные/брак/непроверено" поверх истории записей, либо другой подход) — см. раздел 6.

### 3.10. Брак и компенсация — **уже частично соответствует требованиям, лучше, чем ожидалось**
- `production_order_defects` (`packages/db-schema/src/schema/defect.ts`) — факт брака, привязан к `productionOrderId` (и опционально к конкретному `productVariantId` — можно указать брак без разбивки по SKU).
- `production_order_defect_compensations` — отдельная таблица связи "этот брак решён вот этой строкой вот этого нового заказа", допускает **несколько частичных компенсаций на один дефект** (`quantity` в каждой строке — своя часть). Комментарий в коде прямо говорит: связь **никогда не создаётся автоматически** только по наличию `sourceProductionOrderId`/`variantType='rework'` — только явным действием пользователя.
- **Это уже реализует ровно то, что просит раздел 5 требований**: "Частично исправленные изделия закрывают только соответствующую часть исходного брака. Остаток остаётся открытым... не считаются исправленными автоматически." Использовать без переделки.
- **Чего нет**: агрегата "открытый брак по МОДЕЛИ через все её заказы" — индексы `production_order_defects` только по `(companyId, productionOrderId)`, нет пути "дай мне все непокрытые дефекты продукта X". `defect-summary` эндпоинт (`apps/api/src/defect/defect.controller.ts`, `production-orders/:id/defect-summary`) — тоже по одному заказу, не по модели. UI "Следующий заказ" в `BatchPassportPage.tsx` — контекст только конкретного заказа-источника, не общий список открытых исправлений модели. **Требование S11 "при повторе модели предложить открытые исправления" — не реализовано** (данные для этого в принципе есть через join, но ни запроса, ни экрана нет).

## 6. Терминология и уровень группировки — не вводить новую сущность batch

Проверено: `production_orders` УЖЕ и есть партия ("батч") — глоссарий `CLAUDE.md` называет её `productionOrder`, комментарии в коде (`defect.ts:11`) прямо говорят "уже существующим production_orders — том же, что уже служит партией". Отдельной таблицы `production_batches` **нет и не нужно** — совпадает с прямым запретом задания придумывать новую сущность batch.

**Единственный настоящий архитектурный вопрос — многомодельный заказ** (раздел 3.4): сегодня `production_orders.product_id` — одиночный NOT NULL FK. Два варианта:

- **(A) Изменить схему**, разрешив заказу ссылаться на несколько моделей (новая промежуточная таблица позиций уровня "модель в заказе", ниже уровня SKU-вариантов). Требует миграции, задевает cost_snapshot (сегодня один снимок на заказ — на модель или на заказ целиком?), влияет на раскрой/приёмку/ОТК, которые все читают `order.productId` напрямую.
- **(B) Не менять схему** — трактовать "один заказ с несколькими моделями" как пользовательский сценарий на уровне UI: один проход мастера создаёт НЕСКОЛЬКО `production_orders` (по одной на модель), объединённых общим цехом и, возможно, общей меткой/датой создания для визуальной группировки в UI (не в БД). У каждой — свой план/факт/сроки, как и требует раздел 5 требований ("по каждой собственные факты и сроки").

**Рекомендация: (B).** Она прямо совпадает с явным указанием требований "не вводить дополнительный уровень группировки, пока аудит не показал необходимость" — а аудит (этот документ) не нашёл ни одного места ниже уровня заказа (раскрой/приёмка/ОТК/компенсация), которому нужна была бы мультимодельность внутри одной записи; каждая из этих операций и так оперирует одним `productionOrderId` за раз. Вариант (A) стоит держать в уме только если владелец явно скажет, что ему нужен ОДИН документ/акт на несколько моделей сразу (единая PDF-спецификация на несколько моделей одному цеху) — сегодня специфика уже поддерживает несколько строк (`specification_items`) без ограничения на одну модель, так что даже это не требует правки схемы заказа.

## 7. Расхождения со старыми решениями — pilot freeze, spec-first, источники дизайна

Это критический раздел — задание прямо требует не объявлять прежние ограничения отменёнными.

### 7.1. Freeze архитектуры (CLAUDE.md, правило 10)
`CLAUDE.md` фиксирует (владелец, 2026-08-04, подтверждено 2026-08-04 повторно): **"фундамент GarmentOS завершён для Pilot v1... прекращаем разработку новых возможностей... **Прямое расхождение**: `docs/GOS-PARTY-V1.md` запускает НОВЫЙ, довольно большой пласт функциональности (S01, S08 дата, S09 частичные получения, S10 частичное ОТК, S11 проактивные исправления, S12 целиком) — то есть именно то, что freeze прямо запрещает делать "по предположению о полезности". Раздел 1 самого `GOS-PARTY-V1.md` признаёт это лишь косвенно ("текущий этап — документация и аудит... это не разрешение на миграции production"), но не говорит прямо, что freeze **снимается или временно приостанавливается** этим решением владельца.

**Предлагаю**: не считать freeze автоматически снятым. Нужна явная фраза владельца (даже одна строка в `docs/GOS-PARTY-V1.md` раздел 1 или отдельный ADR) вида "GOS-PARTY-V1 — осознанное решение продолжить разработку до/вместо завершения условий Pilot v1 из раздела 0.5 CLAUDE.md, потому что [причина]". Без этого T01 формально противоречит правилу, которое сам же репозиторий требует соблюдать. Это единственный пункт, где я явно останавливаюсь и прошу подтверждения, а не действую по умолчанию — согласно правилу 8 CLAUDE.md ("необходимость изменить уже принятое архитектурное решение" — freeze и есть такое решение).

### 7.2. Реальные данные vs тестовые

### 7.3. Источник дизайна
`CLAUDE.md` раздел 1: `docs/UI_MIGRATION_PLAN.md` — "единый источник дизайна GarmentOS", прототип `matveevmln/garmentos-ea4078f2` как источник визуальной истины, `apps/web` — источник функциональности/данных. `GOS-PARTY-V1.md` раздел 2 вводит СВОЙ отдельный набор картинок-референсов (V01–V04, четыре группы макетов из разговора с владельцем), явно предупреждая, что "различия... между картинками не являются разными дизайн-системами" и "реализацию собрать из существующих компонентов после аудита".

Сам `GOS-PARTY-V1.md` уже предвидит это и просит не путать новые макеты с новой дизайн-системой — считаю это уже согласованным, не конфликтом, а явно описанным приоритетом ("последние прямые решения владельца → этот текст → уточнённые макеты → ранние картинки", раздел 2). ## 8. Блокеры для первой реальной партии
