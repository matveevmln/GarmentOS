## 13. Многомодельный заказ — минимальное решение

### 13.1. Требование
Контракт §0 п.3, A02, B01, §10: один заказ на пошив назначен одному цеху, содержит несколько моделей, имеет общий штаб; его партии связаны с ним постоянно; создание атомарно.

### 13.2. Что переиспользуется без изменений
- `production_orders` остаётся **партией = одна модель внутри заказа**. Всё, что уже работает от партии, не трогается: `production_order_variants` (план по SKU), раскрой, приёмка, ОТК, брак, компенсации, `cost_snapshot`, `BatchPassportPage`, спецификация order-first (`specifications.production_order_id`, одна на партию).
- `production_orders.workshop_id` сохраняется (денормализация), чтобы не менять десятки мест чтения.
- Распределение по размерам — `distributeQuantityByRatio`, отдельно по каждому цвету.
- Атомарность — по прецеденту `identity.service.ts:86-106` (`db.transaction` + репозитории, созданные на `tx`, + уникальный индекс как защита от повтора). Репозитории контрактного производства уже принимают `DbOrTx` (`drizzle-contract-manufacturing-repository.ts:91,163`).

### 13.3. Что добавляется (одна новая таблица и одна колонка)
Название — утвердить в ADR; рабочее: таблица `sewing_orders`, в коде `sewingOrder`, термин «Заказ на пошив». Глоссарий `CLAUDE.md` обновляется тем же ADR: «Заказ на пошив» → `sewingOrder`, «Партия (модель в заказе)» → `productionOrder`.

`sewing_orders`:
| Поле | Назначение |
|---|---|
| `id`, `company_id NOT NULL` | Изоляция компании |
| `workshop_id NULL` | Пусто допустимо только в черновике; обязательно при размещении |
| `number integer NULL`, уникальность `(company_id, number)` | Номер заказа, выдаётся при размещении внутри транзакции |
| `status` enum `draft / placed / cancelled` | Только жизненный цикл самого заказа; производство, качество и перемещения — производные от партий (R07) |
| `draft_payload jsonb NULL` | Серверный черновик формы A02 (модели, цвета, количества, режим распределения); не localStorage |
| `version integer NOT NULL DEFAULT 1` | Защита от конфликта двух вкладок при автосохранении |
| `client_request_id text NULL`, уникальность `(company_id, client_request_id)` | Идемпотентность размещения |
| `created_by`, `created_at`, `updated_at` | Автор и время |

`production_orders.sewing_order_id uuid NULL` → FK на `sewing_orders.id`, индекс; частичный уникальный индекс `(sewing_order_id, product_id) WHERE sewing_order_id IS NOT NULL` — одна партия на модель в заказе. Связь постоянная: API для переноса партии в другой заказ не создаётся.

Почему черновик в `draft_payload`, а не сразу в `production_orders`: у партии обязательны цех, модель и план (`NOT NULL`); ослабить эти поля — значит тронуть все места, где их читают. Черновик хранится на шапке, партии создаются только при размещении.

### 13.4. Атомарное размещение
`POST /sewing-orders/:id/place` (название предварительное, не существующий endpoint) с `client_request_id`:
1. `db.transaction`: блокировка шапки `SELECT … FOR UPDATE`; если статус уже `placed` с тем же `client_request_id` — вернуть существующий результат (повтор без дубля).
2. Проверка: цех компании, минимум одна модель, у каждой положительный итог, модели и варианты принадлежат компании.
3. Для каждой модели — существующий `createProductionOrderDraft` с репозиториями на `tx`, с `sewing_order_id`; BOM-порт тоже на `tx`.
4. Номер заказа, статус `placed`, `draft_payload` сохраняется как исходный план.
5. Любая ошибка → откат целиком; частичного заказа не бывает.
Подтверждение партий (`draft → placed`, снимок стоимости) в T01 не меняется: остаётся действием по каждой партии.

### 13.5. План миграций
- **M1 (T01, аддитивная)**: enum + `sewing_orders` + `production_orders.sewing_order_id NULL` + индексы. Данные не меняются; откат — удалить колонку и таблицу. В T01 применяется только к тестовой БД.
- **M2 (отдельно, с разрешением владельца, после резервной копии)**: backfill — для каждой партии без шапки создать шапку 1:1 (компания, цех, автор, время создания; статус: `draft`→`draft`, `cancelled`→`cancelled`, остальные → `placed`), заполнить FK. Идемпотентно (`WHERE sewing_order_id IS NULL`), с проверкой совпадения количеств. Сначала — на копии в тестовой БД.
- **M3 (позже, по решению)**: `sewing_order_id NOT NULL` — только когда все пути создания партий создают шапку: `ProductionOrdersPage`/`from-quantity`, spec-first `POST /specifications/:id/production-order`, «Следующий заказ», AI/Telegram `createFromText`. До M3 `NULL` означает «одиночная партия прежнего пути», UI показывает её как заказ из одной модели.

### 13.6. Отвергнутые варианты
- Несколько несвязанных `production_orders` одним нажатием — нет общего штаба и постоянной связи.
- Перенести `product_id` из `production_orders` в новую таблицу позиций — затрагивает раскрой, приёмку, ОТК, брак, стоимость, паспорт; чрезмерный объём.
- Использовать `specifications` как шапку — это одномодельный коммерческий документ со своим жизненным циклом; контракт E02 требует, чтобы спецификация ссылалась на заказ, а не была им.

### 14.2. Отсутствующий UI
Ни одна страница `apps/web/src` не обращается к `/shipments` [код]. Чтения нет: `GET /v1/shipments` → 404 [выполнено].

### 14.3. Семантические разрывы
- Зачисление в назначение происходит при `dispatch`, не при получении — «в пути» не существует как остаток [выполнено P2c].
- `deliver` не принимает фактические количества; частичное получение и расхождения не фиксируются [выполнено P2d].
- `dispatch` не атомарен по строкам: каждая строка — своя транзакция; при нехватке на второй строке первая уже перемещена, статус остаётся `planned`, повтор переместит её снова [код].
- `updateStatus` без условия по текущему статусу — параллельные `dispatch` могут пройти оба [код]; в P2b одна попытка этого не воспроизвела.
- `shipped_at`/`delivered_at` — время сервера, даты события нет (R11) [код].
- `createShipment` не проверяет, что склады и SKU принадлежат компании; `createdBy` берётся из тела запроса [код].

### 14.4. Недостающие связи
- С партиями: у `shipment_items` нет `production_order_id`; происхождение сохраняется только полиморфной ссылкой движения (`reference_type='shipment'`), но не партией-источником [код].
- С качеством: `stock_items` — ключ `(warehouse_id, product_variant_id)`, без партии и без состояния качества; годные и брак неразличимы в остатке (R12) [код + выполнено P3a].
- С производством: отправка из цеха на фулфилмент сейчас — это статус `shipped_to_fulfillment` партии, а не отгрузка; остаток появляется только при приёмке.

### 14.5. Вывод
Для C02/C03/C05/D02 модуль `shipments` — **основа для переиспользования**, а не с нуля: нужны чтение, фактическое получение по строкам с частичными порциями, остаток «в пути», атомарный `dispatch` с проверкой под блокировкой, ссылка строки на партию и признак качества, проверка владения складом. Это задачи T05a–T05c, не T01.
