# Задание T00 для Claude Code

Модель: Claude Opus. Все отчёты, пояснения и документация — на русском.

Мы начинаем GarmentOS — Штаб партии v1 (`GOS-PARTY-V1`). Источник новых требований — `docs/GOS-PARTY-V1.md`. Прочитай его полностью, затем инструкции репозитория. Если документ не приложен и отсутствует, запроси его, не восстанавливай требования по памяти.

Цель этой задачи: исследовать текущую реализацию и подготовить конкретный план первого рабочего участка для модели «Стеганка». Это аудит и документация, не реализация функционала.

1. Укажи текущую ветку, SHA, состояние рабочего дерева. Сохрани чужие изменения. Прочитай CLAUDE.md, применимые AGENTS.md, архитектуру, схему БД, дизайн-систему и актуальные правила окружений. Не объявляй локальную версию версией production.
2. Проследи фактические цепочки UI → API → домен → сохранение: модели, цвета/размеры, цеха, заказы, спецификации/PDF, задания и результаты кроя, приёмки, ОТК, исправления и отправки.
3. Составь таблицу соответствия S01–S12: существующие файлы, endpoints, таблицы, степень готовности, конкретный пробел, способ проверить. Различай «найдено в коде», «выполнено в тестовом окружении» и «не проверено».
4. Найди действующий эталон/генератор спецификации. Укажи путь, входные данные, ограничения и версионирование. Не создавай новый шаблон без проверки существующего и подтверждения эталона владельцем.
5. Разбери поддержку нескольких моделей в заказе, частичных фактов/получений/ОТК и сохранения связи старого брака с новой сдачей. Не придумывай новую сущность batch без сопоставления со старой терминологией.
6. Выяви обязательные материалы/BOM/оплаты, блокирующие упрощённый путь. Предложи согласованное изменение правил; не обходи ограничения пустыми фиктивными записями.
7. Отдельно опиши расхождения старых pilot freeze, источников дизайна и spec-first процесса с новыми требованиями владельца. Предложи точечные обновления документации/ADR. Не объявляй все прежние ограничения отменёнными.
8. Подготовь план T01 с конкретными файлами, API, изменениями схемы при необходимости, сохранением старых данных и проверками. Для архитектурных решений дай варианты только там, где есть существенный выбор, и одну аргументированную рекомендацию.
9. Сохрани результат в `docs/GOS-PARTY-V1-AUDIT.md`. Не меняй функциональный код, зависимости, схему БД или production. Не выполняй push/deploy/миграции и не создавай тестовые записи в рабочей БД.

Проверки — только безопасные и относящиеся к аудиту. Нет доступа к БД/браузеру — явно укажи непроверенное; не считай сборку доказательством полного рабочего процесса.

Финальный отчёт:
- Ветка/SHA и что реально проверено.
- Что используем без переделки, что исправляем, что отсутствует.
- Блокеры создания первой реальной партии.
- Точный план T01, риски и вопросы только о недостающих бизнес-данных.
- Пути изменённых документов и результаты выполненных проверок.

Остановись после аудита. Реализацию выполнять следующим отдельным заданием после разбора отчёта с владельцем.
