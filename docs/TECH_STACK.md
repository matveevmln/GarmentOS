# Технологический стек GarmentOS

> См. также [`ARCHITECTURE.md`](./ARCHITECTURE.md) для контекста, в котором используется каждая технология.

Принцип выбора стека: **один язык (TypeScript) на всех уровнях**, скучные (boring), проверенные технологии с большим сообществом — команда должна быстро нанимать людей и быстро находить ответы на вопросы, а не бороться с экзотикой. Подробнее — принцип «скучные технологии» в `docs/PRINCIPLES.md`.

## Backend

| Технология | Назначение | Почему |
|---|---|---|
| **TypeScript** (strict mode) | Основной язык | Один язык для backend/frontend/shared-types снижает когнитивную нагрузку и дублирование типов (см. `packages/shared-types`) |
| **NestJS** | Backend-фреймворк | Модульная структура из коробки (совпадает с архитектурным стилем модульного монолита), DI, декораторы для контроллеров/валидации, зрелая экосистема (guards, interceptors, pipes) |
| **Node.js LTS** | Рантайм | Стабильность, широкая поддержка библиотек для интеграций (HTTP-клиенты, очереди, работа с S3) |

## Frontend

| Технология | Назначение | Почему |
|---|---|---|
| **React + TypeScript** | UI-библиотека | Огромная экосистема компонентов для таблиц/форм — критично для ERP-интерфейсов с большим количеством табличных данных |
| **Vite** | Сборка SPA | Внутренний инструмент (ERP) не требует SSR/SEO — SPA проще в разработке и деплое, чем Next.js для этого случая |
| **TanStack Query** | Работа с серверным состоянием | Кэширование, инвалидация, оптимистичные обновления — стандарт для data-heavy приложений |
| **TanStack Table** | Таблицы данных | Виртуализация больших таблиц (остатки по SKU, заказы) — критично для производительности |
| **Zustand** | Локальный UI-стейт | Минимальный boilerplate по сравнению с Redux для несложного клиентского состояния |
| **React Hook Form + Zod** | Формы и валидация | Zod-схемы переиспользуются между фронтом и бэком через `packages/shared-types` |

## База данных и хранение

| Технология | Назначение | Почему |
|---|---|---|
| **PostgreSQL** | Основная реляционная БД | Транзакционная целостность критична для домена (остатки, коды маркировки, финансы); зрелые возможности (JSONB для гибких атрибутов, партиционирование при росте, RLS для мультитенантности в будущем) |
| **Drizzle ORM** | ORM / query builder | Типобезопасность «из коробки» без генерации кода на каждый чих (в отличие от Prisma), близость к SQL — важно для сложных отчётных запросов ERP (агрегации по складам/каналам/периодам); лёгкий доступ к «сырому» SQL, когда нужно |
| **Redis** | Кэш + очереди (через BullMQ) | Стандарт де-факто для обеих задач, не требует отдельной инфраструктуры под очереди |
| **BullMQ** | Фоновые задачи (джобы) | Синхронизация с маркетплейсами, обработка «Честного Знака», генерация отчётов — всё I/O-bound и должно ретраиться/масштабироваться независимо от API |
| **S3-совместимое хранилище** (например, Yandex Object Storage / MinIO для dev) | Файлы: фото товаров, файлы техкарт, экспортные отчёты | Дешёвое масштабируемое хранение бинарных данных вне БД |

## Инфраструктура и DevOps

| Технология | Назначение | Почему |
|---|---|---|
| **pnpm workspaces** | Управление монорепозиторием | Быстрая установка зависимостей, строгая изоляция версий между пакетами |
| **Turborepo** | Оркестрация сборки/тестов монорепо | Кэширование задач, параллельный запуск lint/test/build только для изменённых пакетов |
| **Docker / Docker Compose** | Локальная разработка и сборка образов | Единообразное окружение (Postgres, Redis, API, воркеры) для всех разработчиков |
| **GitHub Actions** | CI/CD | Достаточно для старта, не требует отдельной инфраструктуры; см. `QUALITY_STANDARDS.md` для gate-ов |
| Хостинг: **облако с локализацией данных в РФ** (кандидаты: Yandex Cloud, VK Cloud, Timeweb Cloud) либо self-hosted | Продакшен-окружение | Требование 152-ФЗ/242-ФЗ к локализации ПДн граждан РФ — **открытый вопрос, требует решения владельца бизнеса**, см. `ARCHITECTURE_SELF_REVIEW.md` |

## Явно не выбрано на старте (и почему)

| Что рассматривалось | Почему отложено |
|---|---|
| Микросервисы | Преждевременная сложность при текущем масштабе команды и нагрузки (см. `ARCHITECTURE.md`, п.1) |
| GraphQL | REST + OpenAPI проще для CRUD-тяжёлого ERP-домена; GraphQL добавит сложность без явной выгоды на этом этапе |
| Prisma ORM | Drizzle выбран за близость к SQL и производительность на сложных отчётных запросах; решение зафиксировать как ADR при первой реализации схемы |
| Next.js для frontend | SSR/SEO не нужны для внутреннего ERP; решение может быть пересмотрено, если появится публичная витрина/маркетинговый сайт как отдельное приложение |
| Kubernetes | Избыточно для MVP; Docker Compose/managed-контейнеры достаточно, путь к k8s открыт архитектурно (stateless API, см. `ARCHITECTURE.md` п.9) |

Любое отклонение от этой таблицы в процессе реализации — повод завести ADR в `docs/adr/`, а не молча заменить технологию.
