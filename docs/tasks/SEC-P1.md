# SEC-P1 — изоляция компаний в складе и отгрузках

Статус при выдаче: READY. Модель для выполнения: Claude Sonnet; все ответы, документация и результаты проверок — на русском. Если модель нельзя проверить, не утверждать её название как факт.

## Цель и полномочия

Исправить воспроизведённый в T00 доступ пользователя одной компании к складу другой компании. Это самостоятельное исправление безопасности существующего поведения, разрешённое поручением владельца продолжать работу; оно не принимает T00 целиком и не запускает T01. Разрешены код, постоянные тесты, необходимые точечные изменения API и документации в отдельной ветке. Не выполнять третий полный аудит.

Прочитать CLAUDE.md, применимые AGENTS.md, docs/tasks/README.md, docs/WORK_QUEUE.md, docs/GOS-PARTY-V1-TRANSITION-REVIEW.md и относящиеся к SEC-P1 разделы docs/GOS-PARTY-V1-AUDIT.md. При необходимости сверить архитектуру и схему. Исходные пути найти в репозитории, не предполагать их по памяти.

## Старт и границы

1. Обновить refs, убедиться, что чужие незакоммиченные изменения сохранены. Создать отдельную ветку fix/gos-sec-p1-tenant-isolation от актуальной gos-party-v1/review-security-handoff. Зафиксировать исходный SHA и базу PR. Если такая ветка уже есть — сначала проверить выполненное, не перезаписывать.
2. В своей ветке изменить статус SEC-P1 на IN_PROGRESS. T00 оставить REVIEW, T01 BLOCKED. Задание SEC-P1 не требует дополнительного принятия T00.
3. Работать только с отдельной dev/test БД. До запуска миграций/тестов убедиться по конфигурации, что это не production; секреты не выводить. Не запускать production deploy, seed или миграции рабочей базы.
4. Не менять момент зачисления shipments, модель остатков, жизненный цикл ремонта и многомодельного заказа в этой задаче. Сопутствующие независимые находки записать в существующий журнал проблем и отчёт. Не проводить массовое форматирование, обновление зависимостей и CI.

## Реализация

- Составить краткую карту существующих внешних входов для чтения остатков и операций приёмки, списания, перемещения, резервирования/снятия резерва, создания и изменения состояния отгрузки. Проверить фактически существующие операции; новые endpoints только ради проверки не добавлять.
- companyId и идентификатор автора брать из доверенного контекста авторизации. Не доверять companyId/createdBy из тела запроса; подменённое значение отклонять или исключать из внешнего DTO согласно существующему API-контракту. Сохранить RBAC.
- Перед любыми изменениями проверять принадлежность источника, назначения и каждого SKU компании операции, включая связь SKU с моделью, если companyId хранится на модели.
- Применить защиту в доменном/application слое, доступном всем соответствующим входам; одной проверки в UI/контроллере недостаточно. Системные вызовы должны передавать доверенный контекст явно.
- Отгрузку получать с ограничением по компании. Повторно проверить её ссылки при выполнении операции: старые ошибочные записи не должны обходить защиту после исправления.
- Для операции с несколькими строками чужая ссылка даже в последней строке отклоняет запрос без изменения бизнес-данных всех строк. Проверять весь набор до первой записи; если для этого необходима транзакция — использовать существующий подход. Не объявлять решённой всю атомарность логистики вне проверенного сценария.
- Существующий чужой объект и отсутствующий объект не должны раскрывать данные другой компании. Использовать согласованный проектом ответ 403/404; не возвращать 500.
- Не исправлять исторические производственные записи автоматически и не переносить остатки между компаниями. Если найдены потенциальные последствия старого поведения, описать план отдельной сверки без чтения рабочей БД.

## Обязательные доказательства

Постоянные интеграционные regression-тесты на отдельной БД с синтетическими компаниями A и B:

1. Воспроизвести исходный SEC-P1 тестом до исправления и показать, что он падает по причине доступа к чужому складу. После исправления тот же тест проходит.
2. Пользователь A не может изменить остаток склада B, использовать чужой склад как источник/назначение или чужой SKU на своём складе.
3. Для многопозиционного запроса первая строка допустима, последняя — чужая: количества, резервы, движения, строки и состояния отгрузок не меняются. Сравнить состояние до/после; security-лог отказа допустим.
4. Нельзя прочитать чужие остатки/отгрузку через существующие входы. Отсутствие endpoint отметить, не изображать проверку.
5. Чужая отгрузка и синтетическая старая отгрузка со ссылками на чужой склад/SKU не исполняются и не меняют данные.
6. Подмена автора/компании в запросе не приводит к выполнению от чужого имени. Проверить путь с реальной авторизацией API, не только прямой вызов service с вручную переданным companyId.
7. Положительные сценарии своей компании продолжают работать; ограничения ролей сохраняются. Проверить затронутые внутренние вызовы и типы после изменения сигнатур.

Матрица тестов должна связывать существующие операции с проверками склада/SKU/автора. Сходные случаи можно параметризовать. Изучить scripts перед запуском, выполнить относящиеся к изменению тесты, typecheck, lint и сборку согласно обязательным правилам проекта. Предсуществующие сбои отделить от новых, привести команды и exit codes. Если выполнить проверку невозможно — явно отметить, не выдавать статический анализ за успешный прогон. Тесты сохранить в репозитории, временные зонды не считать достаточным результатом.

При достаточной проверке поставить SEC-P1 в REVIEW, открыть draft PR в gos-party-v1/review-security-handoff, приложить отчёт и ссылку на задачу. Не принимать собственную работу как ACCEPTED, не сливать PR, не деплоить и не начинать T01. Если блокер — записать точную причину BLOCKED и выполненную часть. Обычные технические решения принимать самостоятельно; реальные параметры Стеганки не нужны для этого исправления.
