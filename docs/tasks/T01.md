# T01 — модель, заказ на пошив и штаб партии

Статус: PREPARED. Кодовая задача для Claude Sonnet после ревью SEC-P1 и принятия архитектурного ADR. Основа: `docs/GOS-PARTY-V1-EXECUTION.md`, экранный контракт A02/A03/B01 и R01/R02/R05/R07, аудит T00 §13/18, `docs/GOS-PARTY-V1-TRANSITION-REVIEW.md`. Все ответы и отчёты — на русском.

## Результат для селлера

Войти в тестовую веб-версию → «+ Заказ на пошив» → при необходимости тут же создать цех и модель → выбрать цвета, парные размеры и количества → сохранить/открыть черновик → нажать «Создать заказ» один раз → увидеть сохранённый штаб с партиями выбранных моделей. Вернуться через меню/после перезагрузки; те же модели, количества и действия остаются. Для первой «Стеганки» форма не требует ткани, материалов, оплат и фото.

## Перед кодом

- Разобрать текущие web/API/DB точки входа и завершить ADR с одним источником данных: `sewing_orders` как шапка, существующие `production_orders` как партии модели, включая существующие spec-first и AI-пути. Документировать точное поведение «Создать заказ»: какая операция делает дочерние партии пригодными для следующего шага, без обязательной серии подтверждений каждой партии. Не показывать статус «размещено», если доменные guards следующего шага всё ещё считают партии черновиками.
- ADR описывает независимые статусы, ограничения company/workshop, уникальность номера, повтор команды, позднее автосохранение, старые draft/placed/cancelled, идемпотентный backfill, совместимость URL, отсутствие DROP как rollback после записи данных. Перед кодом зафиксировать цепочку ссылок: модель → вариант → партия → шапка → документ/крой.
- Проверить, какая ветка была принята и актуальные SHA PR #5/#6/#7. Не копировать код из старой ветки поверх новых коммитов, не писать в main или Railway. Не принимать SEC-P1 автоматически только по отчёту.

## Реализация, вертикальный путь

1. Добавить только необходимые аддитивные миграции. Создание, изменение черновика, размещение, получение одного заказа и списка из одной схемы. Авторизованная компания и цех/модели/SKU проверяются до фиксации, операция из нескольких моделей атомарна. Каждый сохранённый план должен иметь явный снимок размеров/цветов/количества и соответствующий идентификатор модели, чтобы изменение справочника задним числом не меняло заказ.
2. Режимы распределения: шаблон с долями ровно 100%, largest remainder отдельно по каждому цвету и ручные ячейки. Количество в ячейках целое ≥ 0. Итоги вычисляются и валидируются на сервере; изменение количества цвета после ручного ввода требует явного решения пользователя, не тихого перерасчёта. Для цвета 600: 75/150/150/150/75; для 400: 50/100/100/100/50.
3. Черновик допускает неполные данные; размещение проверяет минимум цех/модель/варианты/положительный объём. Автосохранение учитывает version/status; старый запрос не может перезаписать размещённый заказ. Один client_request_id с тем же нормализованным содержимым возвращает тот же результат, с другим — 409; другой ключ у уже размещённой шапки не создаёт вторую группу партий. Уникальность номера обеспечена при параллельных запросах.
4. Старые заказы сохранить: миграция связывает существующие партии с шапками без пересоздания, сохраняя идентификаторы, номера, статусы, связи со спецификациями и крой. Повтор миграции ничего не удваивает. Все старые способы создания должны прикреплять партию к одной шапке или быть совместимым адаптером до окончательного переключения. Не хранить второй конфликтующий экземпляр заказа.
5. Web из существующих компонентов GarmentOS: каталог моделей, форма создания модели и цеха без потери незавершённого заказа, форма матрицы, выбор сохранённых цветов и размеров, индикация «Сохраняем / Сохранено / Не сохранено — повторить», список заказов, штаб с партиями. Любая кнопка A02/A03/B01 либо имеет реальное действие, либо удалена до реализации; ошибки сети/конфликт вкладок видны, введённые данные не теряются.
6. Сохранять старые URL и операции для существующих заказов. Новый пункт «Заказы на пошив» ведёт в один штаб; старые маршруты либо открывают соответствующую партию штаба, либо пока остаются доступными вне основного меню без изменения истории. При переходе кроя/спецификации сохранять связь с идентификатором партии.

## Приёмка

- API на тестовой БД: две модели → одна шапка и две партии; ошибка второй модели → ничего не создано; чужие цех, модель или SKU → 403/404 без частичного создания; параллельные запросы → нет дублей; старый автосейв после размещения → 409; повтор того же ключа и payload возвращает ту же шапку, изменение payload — 409; старые заказы доступны по ID и после повторного backfill.
- UI Playwright: создать в форме модель/цех, сохранить черновик, перезагрузить, продолжить, разместить один раз, увидеть обе партии в карточке, повторно войти через «Заказы на пошив». Два цвета с приведённым примером; некорректные доли; две вкладки; неработающий API; мобильная ширина.
- Тесты на синтетических данных; проработать edge 1/7/1001, а также пять парных размеров. Запустить typecheck, целевые тесты, lint, build, доступный browser E2E. Красные внешние зависимости зафиксировать, не выдавать сборку за полный пользовательский проход.
- В отчёте — исходный/итоговый SHA, миграции, реальные страницы/API/схемы, запись плана в БД, список выполненных A02/A03/B01, ссылки на подтверждение в браузере, непроверенное и точная команда теста. Результат в отдельном draft PR и статус REVIEW. Запрет деплоя/production миграции сохраняется.
