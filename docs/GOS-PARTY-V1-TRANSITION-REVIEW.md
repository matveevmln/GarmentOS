Прогоны Claude в тестовой БД не воспроизводились этим ревьюером; их результаты остаются атрибутированными отчёту Claude. Документ дополняет очередь заданием SEC-P1 и не разрешает production-деплой. К владельцу обращаться за неизвестными бизнес-фактами и необходимыми разрешениями на действия с рабочими данными/публикацией. Готовые ограниченные задания можно выполнять доступной моделью разработки. Качество принимать по доказательствам, а не названию модели. ## Вердикт по обновлённому T00

Аудит стал пригодной основой для планирования: исправлены ошибочные выводы, есть соответствие A01–E02/R01–R12 и разделение видов доказательств. Это не свидетельство готовности приложения. Не требуется третий полный аудит. До реализации T01 внести следующие уточнения в ADR и задание.

## Стратегия перехода

Сохранить текущий стек, авторизацию, компанию/права, каталог, подходящие PDF и округление. Добавить общую шапку заказа над существующими партиями по моделям. Доработать семантику кроя, приёмок, качества, ремонта и перемещений: новый UI поверх ошибочного учёта недопустим.
Не строить второй независимый склад и две копии заказов. Новые экраны читают общие сохранённые данные. Старые пути временно служат совместимости, затем убираются из основной навигации; старые ссылки ведут в соответствующий новый контекст. Удаление старого кода — отдельный завершающий шаг после проверки всех вызывающих путей. Исторические данные сохраняются.

## Обязательные уточнения ADR/T01

1. Одно пользовательское «Создать заказ» не должно приводить к обязательному повторному подтверждению каждой партии только из-за внутренней реализации. В аудите шапка placed содержит дочерние draft: определить и отобразить точную семантику, не выдавать дочерние партии за запущенные. Повторную техническую фиксацию объединить с первой реальной операцией при необходимости, проверив снимок и старые guards.
2. Черновик: обновление draft_payload и размещение проверяют status и version под блокировкой. Поздний запрос автосохранения не меняет уже размещённый план.
3. Идемпотентность: тот же ключ с другим содержимым — конфликт; иной ключ после размещения не создаёт второй набор партий. Номера выделять атомарно, не MAX+1 без защиты.
4. Компания и цех шапки должны совпадать с дочерними партиями во всех путях. Проверить нормализацию повторного выбора модели. Не полагаться только на UI.
5. Backfill старых draft: существующие дочерние партии уже есть. Нельзя при размещении синтетической шапки создавать их заново. Спроектировать явную совместимость legacy-записей, сохранить номера, ссылки и план. Проверить повторный запуск переноса.
6. Удаление новых таблиц/колонок НЕ безопасный откат после начала записи реальных данных. Разделить возврат приложения к совместимой версии и откат данных; в production после новых записей предпочесть исправляющую миграцию. Проверить восстановление резервной копии до переноса.
7. Старые compensation-записи не переименовывать автоматически в назначения ремонта: раньше они уменьшали открытый брак. Сначала определить отображение legacy-семантики и сверку; новая логика не должна молча открывать или закрывать старые обязательства.
8. Existing shipments переиспользовать только после исправления владения, атомарности и момента зачисления. Отдельно решить перенос уже имеющихся in_transit, поскольку назначение по старой логике могло быть пополнено ранее. Новый deliver не должен пополнить его второй раз.

## Приоритет

Первый кодовый пакет: SEC-P1 — изоляция компаний в складских и shipment-операциях. Подтвердить воспроизведение постоянным regression-тестом, проверить источник/назначение/SKU и author из авторизованного контекста, отсутствие частичных записей при отказе и положительный сценарий своей компании. Отдельная ветка/PR и тестовая БД. Не расширять его до всей логистики. Публикация исправления — отдельное решение после проверки, не автоматический деплой.
Затем T01 — шапка и сохранённый заказ с поправками выше. P4/планирование ремонта в крое обязательно до реальной работы с кроем; P6 и полноценная семантика ремонта — до использования компенсаций. Проверка статуса сама по себе не доказывает исправление брака.
Временные зонды полезны для расследования; воспроизводящие дефекты тесты должны остаться в исправляющих PR, без секретов и рабочих данных.

## Подключения

Для текущего процесса достаточно GitHub read для ревьюера и GitHub write/терминала/браузера/отдельного Postgres для Claude. Отчёт сообщает о наличии этих возможностей у Claude; пригодность подтверждается конкретными запусками. После установки Codex Connector создание отдельной ветки через подключение ревьюера проверено успешно 2026-09-24. Это не означает автоматический запуск Claude.
Read-only сведения Railway полезны для плана развёртывания и фактических миграций, не повод автоматически открывать production-БД на запись. Прямые изменения данных и публикация сохраняют отдельную границу разрешений. Новые плагины, Figma, Redis/S3 и сервер автоматизации не являются предварительным условием T01. Исследовать существующее хранилище файлов, не заменять его ради концепции.
