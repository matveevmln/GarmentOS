# Аудит дня владельца бизнеса в GarmentOS (2026-07-24)

> Цель документа: проверить архитектуру не с точки зрения полноты схемы, а с точки зрения реальной пользы — «какие действия пользователь сможет выполнять быстрее благодаря этому» (см. `docs/PRINCIPLES.md`, принцип 17 «Zero Input»). Владелец бизнеса проводит целый рабочий день, работая только в GarmentOS, преимущественно с телефона. Ниже — полный путь по 11 шагам с разбором: действия / данные / документы / уведомления / отчёты / ошибки / автоматизация. Найденные пробелы зафиксированы в разделе итогов и закрыты до продолжения Итерации 3.

## 1. Закупка ткани

| | |
|---|---|
| Действия | Открыть поставщика (или создать) → создать закупку → указать материал, кол-во, цену → отправить |
| Данные | Поставщик, материал, кол-во, цена/ед., дата заказа, ожидаемая дата поставки |
| Документы | Заказ (генерируется системой), инвойс от поставщика (прикладывается как `documents`, `doc_type=invoice`) |
| Уведомления | «Заказ отправлен»; «Поставка просрочена» (`expected_date` прошёл, `status != received`) |
| Отчёты | Открытые закупки; история цен по материалу (`purchase_order_items.unit_price` + `ordered_at`, уже спроектировано) |
| Ошибки | Опечатка в цене; дублирование заказа тому же поставщику в тот же день; забыли `expected_date` |
| Автоматизация | **Автозаполнение цены из последней закупки этого материала у этого поставщика** (реюз данных); алерт при отклонении цены >X% от истории («цена выросла на 15% — подтвердить?»); **алерт по точке перезаказа** — см. пробел №1 |

## 2. Закупка фурнитуры

Идентично шагу 1 (`materials.type=trim`). Ключевая экономия: если фурнитура уже закупалась для другой модели — предложить того же поставщика и последнюю цену одним нажатием, не искать заново.

## 3. Создание модели

| | |
|---|---|
| Действия | Название → коллекция (реюз существующей) → категория → BOM (материалы+нормы) → фото/техпак → SKU-матрица (размер×цвет) |
| Данные | Сезон, коллекция, категория, BOM, размерная сетка, цвета |
| Документы | Техпак (`products.tech_pack_url`) |
| Уведомления | «BOM не завершён» (модель активна, BOM в статусе `draft`) |
| Отчёты | Модели по коллекции; **плановая себестоимость по BOM** (см. пробел №3) |
| Ошибки | Заказ в цех создаётся раньше, чем BOM утверждён — см. пробел №6 |
| Автоматизация | **Генерация SKU-матрицы одним действием** (выбрал S/M/L/XL × бордо/чёрный → 8 SKU за раз, не 8 форм) — см. пробел №2 |

## 4. Размещение заказа в цехе

| | |
|---|---|
| Действия | Модель → цех (по специализации) → количество по SKU → система сама считает нужный материал → подтвердить |
| Данные | Цех, кол-во по SKU, `agreed_unit_price`, `due_date` |
| Документы | Заказ; спецификация для цеха (авто-PDF из BOM + разбивки по SKU); договор (`documents`) |
| Уведомления | «Заказ создан»; «Срок подходит» (`due_date` − N дней); «Просрочка» |
| Отчёты | Активные заказы по цехам; загрузка каждого цеха; рейтинг цеха (план vs факт срока — требует `receivedAt`, см. пробел №5) |
| Ошибки | Материала на складе может не хватить — см. пробел №4; нет проверки перегрузки цеха (Future, Фаза 3) |
| Автоматизация | **Авто-расчёт нужного материала** = `bomItem.quantityPerUnit × Σ(SKU qty) × (1+wastePercent)`; при нехватке — предложение заказа у последнего поставщика по последней цене |

## 5. Передача материалов в цех

| | |
|---|---|
| Действия | Подтвердить передачу авто-рассчитанного списка (шаг 4) — правки только при фактическом расхождении |
| Данные | Список материалов+кол-во (предзаполнено) |
| Документы | Накладная на передачу давальческого сырья (авто-PDF из `stock_movement`) |
| Уведомления | «Материалы переданы в цех Х» |
| Отчёты | **«Сколько материала сейчас у каждого цеха»** — сумма `stock_items` по складам `type=workshop` — ключевой отчёт для контроля давальческого сырья |
| Ошибки | Передать больше, чем есть на складе — см. пробел №4 |
| Автоматизация | В идеале — ноль ручного ввода, только подтверждение предзаполненного |

## 6. Контроль производства

| | |
|---|---|
| Действия | Отслеживание статуса; обновление по факту звонка/сообщения от цеха |
| Данные | Статус, ETA, комментарии |
| Документы | Фото прогресса (`documents`, `doc_type=photo`) |
| Уведомления | «Заказ просрочен»; **«Цех не отвечал N дней»** (эскалация при отсутствии обновлений) |
| Отчёты | Все активные заказы по статусам; заказы с риском просрочки (`due_date` через 3 дня, статус ещё `placed`) |
| Ошибки | Нет реального контроля прогресса без коммуникации с цехом — это узкое место процесса, не только системы |
| Автоматизация | **Это самый ручной шаг во всём цикле — и именно здесь Universal Inbox даёт наибольший выигрыш**: цех пишет «Заказ готов» + фото → AI предлагает «Обновить статус заказа №152 на ready_for_pickup? Прикрепить фото?» — пользователь подтверждает одним нажатием, не открывая форму (см. `docs/INBOX_ARCHITECTURE.md`) |

## 7. Приёмка

| | |
|---|---|
| Действия | Подтвердить получение партии — фактическое кол-во по SKU может отличаться от заказанного |
| Данные | Фактическое кол-во по SKU, фото готовой продукции |
| Документы | Акт приёмки (авто), фото, сертификаты |
| Уведомления | «Приёмка завершена»; «Расхождение факт/заказ >X%» |
| Отчёты | Процент брака/недопоставки по цеху (основа рейтинга, Фаза 3) — вычисляется из заказанного (`production_order_variants.quantity`) vs фактически принятого (сумма `stock_movements` типа `receipt` со ссылкой на этот заказ) — **не нужна новая колонка**, это read-model |
| Ошибки | Забыли зафиксировать расхождение — тогда себестоимость/остаток разъедутся с реальностью |
| Автоматизация | **Авто-списание материала у цеха по BOM при подтверждении приёмки** (иначе это ручная работа); **авто-расчёт фактической себестоимости партии** прямо в `cost_entries` (material_cost из BOM×цена + manufacturing_cost из `agreed_unit_price×qty`) — не руками бухгалтера |

## 8. Склад

| | |
|---|---|
| Действия | Просмотр остатков; периодическая инвентаризация |
| Данные | Фактическое кол-во по SKU (при инвентаризации) |
| Документы | Акт инвентаризации |
| Уведомления | Расхождение инвентаризации выше порога |
| Отчёты | Остатки по SKU/складам; расхождения инвентаризации (ключевой критерий успеха проекта, `PROJECT_VISION.md`) |
| Ошибки | Расхождение факта и учёта |
| Автоматизация | Алерт при расхождении. **Сознательно не проектируем** min-stock алерт для готовых SKU (в отличие от материалов) — решение «шить новую партию» зависит от продаж/сезона, не механический перезаказ; уточнить с владельцем, если окажется нужным |

## 9. Экспорт

| | |
|---|---|
| Действия | Создать отгрузку: склад-источник/назначение, перевозчик, SKU+кол-во (авто из остатка), документы |
| Данные | Даты, tracking number, перевозчик |
| Документы | CMR/накладная/декларация/фото при погрузке (`documents`) |
| Уведомления | «Отгрузка вышла»; «Задерживается»; «Прибыла» |
| Отчёты | Товар в пути (все `shipments` со статусом `in_transit`); сроки доставки по перевозчику |
| Ошибки | Отправить больше, чем есть на складе-источнике — тот же класс проверки, что и в шаге 5 |
| Автоматизация | Авто-подсчёт доступного к отгрузке = остаток минус зарезервированное |

## 10. Продажа на Wildberries/Ozon

| | |
|---|---|
| Действия | Практически нет ручных действий — заказы приходят через синхронизацию |
| Данные | Из API площадки |
| Документы | Нет доп. документов (кроме внутреннего заказа и кода «Честный Знак») |
| Уведомления | Рассинхронизация остатка; ошибка синхронизации (не «новый заказ» на каждый заказ — это шум, а не польза) |
| Отчёты | Продажи по SKU/каналу/периоду; расхождение «наш остаток vs остаток на площадке» |
| Ошибки | Остаток разошёлся с площадкой; задвоение заказа |
| Автоматизация | Полностью автоматический процесс — GarmentOS только реагирует на события |

## 11. Анализ прибыли

| | |
|---|---|
| Действия | Открыть дашборд → увидеть маржу за секунды |
| Данные | Нет ручного ввода — всё агрегируется |
| Отчёты | P&L (выручка − material_cost − manufacturing_cost − logistics_cost − overhead_cost) по модели/коллекции/цеху/каналу/периоду; сравнение план (BOM-расчёт) vs факт себестоимости |
| Ошибки | Если `cost_entries` не рассчитаны для каких-то заказов — маржа занижена/искажена без предупреждения — см. пробел №8 |
| Автоматизация | Полный авто-расчёт при приёмке (шаг 7); P&L — read-model, не хранимая таблица (уже решено в `DATABASE_SCHEMA.md`) |

## Итог: найденные пробелы и решения

| № | Пробел | Решение | Где закрывается |
|---|---|---|---|
| 1 | `materials.reorder_point` существует, но не описан механизм, который его использует | Явное правило Notifications: остаток материала < `reorder_point` → уведомление + предзаполненное предложение заказа у последнего поставщика по последней цене | Domain-слой (Итерация 3), Notifications |
| 2 | Нет описанного «bulk-создания» SKU-матрицы (размер×цвет за одно действие) | Явный use case `generateSkuMatrix(sizes[], colors[])` — создаёт все `product_variants` одним вызовом | Domain-слой (Итерация 3), API (Итерация 4) |
| 3 | Нет описанного авто-расчёта плановой себестоимости по BOM до реального производства | Read-model в Reporting/BI: `plannedCost = Σ(bomItem.quantityPerUnit × latestMaterialPrice)` | Reporting/BI (Фаза 2-3), не новая таблица |
| 4 | Нет проверки остатка перед `transfer`/`dispatch` — можно передать/отгрузить больше, чем есть | Доменный инвариант Warehouse-модуля: запрет операции при недостаточном `quantity_on_hand − quantity_reserved` | Domain-слой (Итерация 3), обязательный unit-тест |
| 5 | `production_orders` не имеет поля фактической даты завершения | Добавлено `production_orders.receivedAt` (timestamp, nullable) — см. `DATABASE_SCHEMA.md` | Схема (эта правка) |
| 6 | Нет описанного правила «нельзя создать заказ в цех без утверждённого BOM» | Доменный инвариант Contract Manufacturing: `production_order` требует `bom.status = 'approved'` | Domain-слой (Итерация 3) |
| 7 | Нет механизма эскалации при отсутствии обновлений от цеха | Решается Universal Inbox естественным образом — см. `docs/INBOX_ARCHITECTURE.md` | Inbox-модуль |
| 8 | Нет отчёта «заказы без рассчитанной себестоимости» | Read-model в Reporting/BI: список `production_orders.status=received` без соответствующего `cost_entries` | Reporting/BI |
| 9 | **Главный пробел**: весь ручной ввод (шаги 1-4, 7, 9) предполагает форму за формой — противоречит цели «минимум ручного ввода» | Universal Inbox — см. `docs/INBOX_ARCHITECTURE.md` | Новый модуль, приоритизирован в `ROADMAP.md` |

Пробел №5 — единственное изменение непосредственно в уже реализованной схеме БД (Итерация 2); остальные — задачи следующих итераций, зафиксированные явно, чтобы не потеряться.
