# MVP Checklist — готовность к первому реальному запуску

> Главный рабочий документ проекта на этом этапе (зафиксировано владельцем проекта 2026-07-27): вместо гадания «что дальше?» — движение по этому чек-листу до момента, когда GarmentOS можно использовать в реальной ежедневной работе. Основан на построчном аудите кодовой базы 2026-07-27 (не на документации — на том, что реально работает).
>
> **Целевой сценарий, по которому проверяется готовность**: владелец открывает Telegram → пишет заказ → подтверждает → получает спецификацию → она уходит в цех → получает статусы от цеха → принимает партию на склад → закрывает заказ — целиком через GarmentOS.
>
> После прохождения раздела 🟡 — **переход от проектирования к эксплуатации**: минимум неделю реальной работы, новые идеи — только по итогам реального использования, оформляются как отдельные архитектурные документы и итерации (`docs/ROADMAP.md`, Итерации 13+), не заранее.

## ✅ Готово

- Аутентификация/RBAC/мультитенантность на уровне API — все 11 доменных модулей.
- Аудит критичных операций (`packages/domain/audit`).
- Каталог/BOM/Contract Manufacturing/Warehouse/Sales/Marketplace Integration/Honest Sign/Finance/Notifications — доменный слой + API поверх всех 11 модулей.
- Telegram: привязка компании и цеха (инвайт-код + `/start`), полностью рабочая.
- Текст в Telegram → предпросмотр ("что понял / что нашёл / чего не хватает") → «Да» → черновик заказа → подтверждение → генерация PDF-спецификации → отправка цеху — весь путь работает, покрыт e2e-тестами.
- Document Template Engine: PDF по эталонному образцу, кириллица (Liberation Serif), русский формат чисел, сквозная нумерация спецификаций по договору цеха.
- Цех → простой текстовый статус-ответ ("готово"/"в работе") обновляет статус заказа.
- Полный monorepo pipeline (16 пакетов, build/lint/typecheck/test) зелёный на каждом шаге.

## 🟡 Осталось сделать до первого запуска

Реальные разрывы в целевом сценарии, найдены построчным аудитом кода 2026-07-27 (не гипотезы):

### Итерация 9 — завершить Telegram Owner Flow

1. **Компания не узнаёт о статусе от цеха.** Когда цех отвечает «готово», сообщение уходит только обратно цеху — ни в чат компании, ни в `notifications` ничего не попадает. Без этого шаг «получать статусы» из целевого сценария не работает никак, кроме прямого запроса к API по UUID заказа.
2. **Пример заказа из реальной переписки не распознаётся буквально.** Формулировка вида «Отшей модель Двойка. Петроль — 1000 шт.» — свободный текст, не строгий формат «Модель: ... Цена пошива — ...», который понимает `RuleBasedAIClassifier` без ключа. **Нужно решение владельца проекта**: подключить `ANTHROPIC_API_KEY` (реальное распознавание свободной речи) или закрепить строгий формат как рабочий стандарт на первое время.

### Итерация 10 — полный цикл производства

3. **Нет приёмки партии, привязанной к заказу.** Статус `received`/поле `receivedAt` существуют в схеме, но их не устанавливает ни один use case; `receiveStock` (склад) физически не связан с `production_order` — вызов склада и заказ пошива сегодня никак не пересекаются.
4. **Нет закрытия заказа** — такого состояния не существует в коде (не только не реализовано, а не спроектировано). Предлагается для MVP: использовать существующий статус `received` как терминальный, без разбора на партии/брак/компенсацию (это сознательно отложено — `docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`, ждёт вашего утверждения отдельно).
5. **Содержимое спецификации проверено на реальном примере (модель "Худи Петроль", показано 2026-07-27) — решить, что добавить до того, как шаблон встроится во все процессы**: сегодня в PDF нет артикула/SKU, состава ткани, расхода материалов по BOM, фурнитуры, требований к пошиву, требований к упаковке, QR-кода или идентификатора партии. Часть этих данных уже существует в системе (расход материалов — в BOM, `bom_items.quantity_per_unit`/`waste_percent`), но не выводится в спецификацию; часть (состав ткани, требования к пошиву, упаковка) не смоделирована вообще.

### Итерация 8 — резервное копирование

6. **Не начато** — ни одного скрипта/cron в `infra/`, только диаграмма в `docs/INFRASTRUCTURE.md`. Обязательно до подключения первой реальной компании (собственное правило Roadmap, зафиксированное ещё на Фазе 0).

### Сквозные системные принципы (зафиксированы 2026-07-27, реализуются вместе с Итерациями 9-12)

7. **Mobile-First** (`docs/PRINCIPLES.md`, принцип 20) — веб-интерфейс (Итерация 11) должен быть полностью функционален с телефона с первого экрана, не переделываться под мобильный постфактум.
8. **Локализация и валюта** (`docs/PRINCIPLES.md`, принцип 21) — интерфейс на русском, валюта учёта компании по умолчанию — KGS (изменено с RUB 2026-07-27, `companies.default_currency`), спецификации для цехов — всегда в RUB независимо от валюты учёта компании.

## 🔵 После запуска (Version 2)

Явно отложено до реального использования системы, не убрано из планов:

- **Баланс производственной партии** (`docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`) — полный жизненный цикл партии, брак с причинами и местом выявления, способы устранения (дошив/перешив/скидка/списание), обязательства цеха, KPI цехов. Архитектура готова, ждёт утверждения; реализация — Итерация 15, сознательно после MVP («не хочу добавлять новые крупные бизнес-модули», 2026-07-27).
- **Universal Inbox** (Итерация 13) — обобщение узкого текстового парсера Итерации 7 до полной AI-классификации любых форматов и каналов.
- **AI Production Assistant (полный)** (Итерация 14) — спецификация без готового BOM, согласование через Workflow Engine, e-signature.
- **Wildberries-коннектор** (Итерация 16).
- Возможность спросить в Telegram «какой статус у заказа» текстом — не нужно, если заработает пуш-уведомление (пункт 1 выше).
- Общие GET/list-эндпоинты по всем 11 модулям — нужны вместе с веб-интерфейсом (Итерация 11), не раньше.
- История переписки/фото по партии, KPI-дашборды цехов — вместе с Балансом производственной партии.
