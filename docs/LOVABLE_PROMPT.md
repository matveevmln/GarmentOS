# Промпт для Lovable / v0 — визуальный референс GarmentOS

> **Один промпт, один проход, минимум кредитов.** Всё, что съедает бюджет в Lovable, отключено явно: бэкенд, Supabase, авторизация, роутинг, сторонние библиотеки, уточняющие вопросы. Данные — реальные поля из `packages/db-schema` и `packages/shared-types`, чтобы генератор не изобрёл несуществующие сущности и не пришлось переделывать.

## Ответы на главные вопросы

**Картинки или код?** — Код. Lovable не генерирует изображения, он собирает работающую страницу. Это лучше картинки: макет заведомо реализуем в CSS, а скриншоты вы снимете сами из превью.

**Как снять скриншоты.** В превью Lovable откройте страницу, нажмите F12 → иконка «Toggle device toolbar» (Ctrl/Cmd+Shift+M) → выставьте ширину 1440, снимите; затем 768; затем 390. Либо просто меняйте ширину окна браузера.

**Что прислать мне.** Скриншоты в трёх ширинах + **текст дизайн-системы** (палитра с hex, шрифты, размеры) — промпт ниже требует напечатать его отдельно. С текстом перенесу цвета один в один, по картинке — только приблизительно.

## Экономия кредитов — что заложено в промпт

| Что | Зачем |
|---|---|
| Запрет на бэкенд, Supabase, авторизацию, БД | Главный пожиратель кредитов. Нам нужен только внешний вид |
| Одна страница с переключателем экранов вместо роутинга | Дешевле и достаточно для референса |
| Данные захардкожены в один файл констант | Никаких запросов, состояний загрузки, обработки ошибок |
| **Но UI-взаимодействия работают** — переключение экранов, фильтры, tabs, accordions | Иначе получится мёртвая картинка, на которой UX не проверить |
| Запрет ставить библиотеки (графики, анимации, иконочные паки) | Каждая зависимость — лишние токены |
| «Не задавай уточняющих вопросов, сделай всё за один проход» | Каждый диалоговый круг стоит кредитов |
| Сначала дизайн-система, потом экраны | Без этого экраны получаются разнородными, и правка каждого стоит отдельно |

## ⬇️ КОПИРОВАТЬ ОТСЮДА

```
Ты — сильный продуктовый дизайнер и фронтенд-разработчик. Сделай визуальный дизайн-макет GarmentOS за ОДИН проход, без уточняющих вопросов.

=== ЧТО ЭТО ===
GarmentOS — внутренняя операционная система владельца бренда одежды. Это НЕ интернет-магазин, НЕ CRM, НЕ лендинг. Это рабочий инструмент, в котором управляют производством одежды в подрядных цехах и деньгами по каждой партии. Им пользуются каждый день по многу часов.

=== ЖЁСТКИЕ ТЕХНИЧЕСКИЕ ОГРАНИЧЕНИЯ (важно, соблюдай строго) ===
- НЕ создавай бэкенд, базу данных, Supabase, авторизацию, регистрацию, формы входа.
- НЕ делай реальный роутинг. Сделай ОДНУ страницу с переключателем экранов (простое локальное состояние).
- НЕ устанавливай дополнительные библиотеки: никаких chart-библиотек, анимаций, иконочных паков, date-пикеров. Используй только то, что уже есть в проекте по умолчанию, и inline SVG для иконок.
- Все данные захардкодь как константы в одном файле. Никаких запросов, загрузок, обработки ошибок.
- НЕ задавай мне уточняющих вопросов. Прими решения сам и сделай всё сразу целиком.
- Бизнес-функциональность и backend не нужны.
- НО базовые UI-взаимодействия прототипа должны работать: переключение экранов, фильтры и чипы статусов, поиск (хотя бы визуальная фильтрация списка), tabs, accordions, раскрытие деталей, открытие боковой панели или bottom sheet — всё, что нужно, чтобы показать UX вживую.
- Не требуется сохранять данные, отправлять формы или выполнять реальные операции.

=== ЯЗЫК ===
Весь текст интерфейса — на русском. Названия ниже использовать дословно.

=== ПОРЯДОК РАБОТЫ (соблюдай именно этот) ===
ШАГ 1. Сначала спроектируй ЕДИНУЮ дизайн-систему и опиши её:
  - палитра (с точными hex-кодами): фон, поверхности, границы, основной акцент, успех, предупреждение, ошибка, три уровня текста;
  - типографика: шрифт, шкала размеров с названиями ролей (заголовок страницы, заголовок секции, основной текст, вторичный, подпись, крупное число);
  - шкала отступов (одна, без произвольных значений);
  - радиусы скругления и тени;
  - как выглядят статусы (цветовое кодирование).
ШАГ 2. Собери на основе системы переиспользуемые компоненты: боковое меню, верхняя панель, заголовок страницы, карточка, карточка-метрика, бейдж статуса, кнопки (основная/вторичная/иконка), таблица, строка списка для мобильного, шаги производства, timeline, строка документа, поле поиска, фильтры, пустое состояние, состояние загрузки, состояние ошибки.
ШАГ 3. И только потом собери из этих компонентов экраны.
Все экраны должны выглядеть как одна система, а не как семь разных дизайнов. Один и тот же элемент везде выглядит одинаково.

=== ВИЗУАЛЬНЫЙ BENCHMARK: PLMflow ===
Ориентир по уровню профессионального UX/UI — PLMflow (https://plmflow.com/), система класса apparel PLM.
Если к сообщению приложены скриншоты PLMflow — опирайся в первую очередь на них.

Что заимствовать — только принципы:
- профессиональная рабочая среда для швейной отрасли;
- высокая, но контролируемая плотность данных;
- понятная навигация между сущностями;
- устройство списков, таблиц и страниц деталей;
- карточки моделей, статусы, BOM и себестоимость, производственные заказы, работа с фабриками;
- визуальная иерархия и единая система компонентов.

Чего НЕ делать:
- не копировать буквально; не использовать логотип, название, тексты, изображения и уникальные элементы PLMflow;
- не добавлять функции только потому, что они есть в PLMflow;
- GarmentOS должен выглядеть самостоятельным продуктом, а не клоном.

PLMflow задаёт только планку качества и отраслевой контекст. Все разделы, данные, статусы и ограничения GarmentOS из этого задания имеют более высокий приоритет и перекрывают любые решения PLMflow.

Цель: GarmentOS должен выглядеть как современная профессиональная операционная система для швейного производства такого же класса, а не как обычная админка или шаблонный SaaS.

=== ПАЛИТРА И ТИПОГРАФИКА — РЕШАЕШЬ ТЫ ===
Конкретные цвета, тему (светлая/тёмная) и шрифты я НЕ задаю. Выбери сам в рамках планки качества выше и обоснуй выбор в двух предложениях.
Ориентиры по ощущению:
- Профессиональный рабочий инструмент, а не витрина. Здесь управляют производством и деньгами.
- Пользователь — владелец бренда одежды, не разработчик и не бухгалтер. Ему важно быстро понять: что происходит, где проблема, сколько денег.
- Плотность данных высокая, но экран не перегружен.
- Не должно выглядеть как ERP из 2010 года, Bootstrap-админка или набор случайных таблиц.
- Продукт про одежду и производство — можешь это учесть, но без буквальности.
Светлая тема, тёмная или обе — твой выбор.

=== АДАПТИВНОСТЬ: ОДНА КОДОВАЯ БАЗА, ТРИ РЕЖИМА ===
Не делай отдельный десктопный и отдельный мобильный макет. Один и тот же интерфейс перестраивается:
- 1440px — полноценное рабочее пространство, использующее всю ширину экрана. Не зажимай контент в узкую центральную колонку.
- 768px — промежуточный режим.
- 390px — должен ощущаться как хорошее мобильное приложение, а не сжатый сайт: крупные зоны нажатия (минимум 44px), ключевое действие под большим пальцем, вторичные детали спрятаны, никакого горизонтального скролла.
Как устроить навигацию в каждом режиме — реши сам.
```

## ⚠️ Обязательно: приложите скриншоты PLMflow к сообщению

В промпте есть ссылка на `plmflow.com`, но **на неё одну полагаться нельзя**: генераторы вроде Lovable, как правило, не открывают внешние сайты. Ссылка останется словами, и модель либо проигнорирует ориентир, либо додумает, как он выглядит.

Что делать: открыть `plmflow.com` самому, снять **3-5 скриншотов** (главная, список сущностей, страница детали, мобильная версия если есть) и **загрузить их в Lovable вместе с промптом**. Изображения работают надёжно, ссылки — нет.

Тот же приём годится для любого интерфейса, который вам нравится, — не только PLMflow.

## После генерации — что прислать мне

По убыванию ценности:

1. **Исходный код** — главное. В Lovable: кнопка **GitHub** (подключить репозиторий) или **Download / Export**. В v0: кнопка **Code** → скопировать. С кодом я переношу точь-в-точь: реальные значения цветов, отступов, структуру компонентов. Без него — только на глаз по картинке.
2. **Текст дизайн-системы** из ответа генератора (палитра с hex, шрифты, шкала размеров).
3. **Скриншоты** в 1440 / 768 / 390 (F12 → Ctrl/Cmd+Shift+M → задайте ширину). Нужны, чтобы я видел итоговую картину целиком и мог сравнить композицию.

Дальше я честно сравню с текущим прототипом (`apps/design-prototype/`), скажу, что там лучше и почему, и перенесу удачные решения.

## Полный маршрут работы

```
Промпт ниже
   ↓
Lovable/v0 проектирует UI: сначала дизайн-система, потом компоненты, потом экраны
   ↓
Desktop + Tablet + Mobile из ОДНОЙ системы
   ↓
Рабочий frontend-прототип (кликается, фильтры и accordions живые)
   ↓
Исходный код + текст системы + скриншоты — мне
   ↓
Я переношу визуальный язык в apps/web и подключаю к существующему API
```

Ключевое в последнем шаге: подключаю к **уже существующему** backend GarmentOS. Бизнес-логика, Snapshot партии, жизненный цикл заказа, генерация спецификаций, RBAC и аудит не трогаются — меняется только слой представления.

Промпт одинаково подходит для **Lovable** и **v0.dev**. У v0 практическое преимущество: он пишет на React + Tailwind + shadcn/ui — ровно наш стек, часть кода переносится напрямую.
