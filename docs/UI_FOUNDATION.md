# UI_FOUNDATION.md — инженерный фундамент интерфейса GarmentOS

> Готовится на утверждение владельца проекта, **до** реализации. После утверждения — официальный стандарт: все новые экраны `apps/web` строятся только на этом фундаменте, никаких альтернативных библиотек/паттернов без нового ADR (`CLAUDE.md`, раздел 6, пункт 3). Ничего из этого документа ещё не реализовано в коде — это план.

## 0. Принцип

Инженерное качество — из зрелых open-source библиотек (доступность, клавиатурная навигация, обработка edge case, тесты, годы продакшен-эксплуатации). Внешний вид — только фирменный, дословно по уже утверждённому прототипу (`docs/WEB_DESIGN_SYSTEM.md`). Библиотека даёт *реализацию* компонента (фокус-менеджмент модалки, доступность select'а, виртуализация таблицы) — не даёт ни одного пикселя итогового вида: цвета/радиусы/тени/иконки/типографика всегда наши токены, никогда библиотечная тема по умолчанию.

Проверка на каждом решении ниже: «если убрать логотип, узнает ли инженер, знакомый с shadcn/Tremor, откуда это взято?» Если да — переделать стилизацию, не менять библиотеку.

## 1. Обязательное архитектурное решение, которое нужно утвердить отдельно: Tailwind CSS

Список источников, который вы дали, технически требует Tailwind — и `shadcn/ui`, и `Origin UI`, и `Tremor` распространяются как **исходный код с Tailwind-классами**, который копируется в репозиторий (не как готовые npm-компоненты с собственным CSS) — без Tailwind этот код не заработает и не будет стилизуемым тем способом, каким его сопровождает и обновляет community.

Это **новая зависимость технологического стека** (`CLAUDE.md`, правило 6.4 — не добавлять без обновления `docs/TECH_STACK.md` и явного согласия владельца), которая идёт вместе с вашим запросом, но требует отдельного явного «да»:

- `apps/web` сейчас — обычный CSS с custom properties (`styles.css`, уже содержит все фирменные токены). Tailwind не заменяет эти токены — он читает их: цвета/радиусы/тени из `styles.css` (`:root`) пробрасываются в `tailwind.config`/`@theme` (Tailwind v4, CSS-first конфиг) как алиасы (`bg-accent`, `rounded-lg`, `shadow-card`), а не задаются заново по умолчанию Tailwind-палитрой.
- Обычный CSS (`.entity-form`, `.list-card` и т.д.) и Tailwind-утилиты будут сосуществовать первое время — компоненты из shadcn переписываются на наши токены через Tailwind-классы, существующие страницы не переписываются немедленно (нет двойной работы, `docs/PRINCIPLES.md` принцип 3).
- Vite-интеграция — официальный плагин `@tailwindcss/vite` (Tailwind v4, CSS-first, без отдельного `postcss.config`/`tailwind.config.js` в старом формате v3) — минимальная правка `vite.config.ts`.

**Если это «да» — считать решённым этим документом после утверждения, не поднимать отдельно.**

## 3. Иконки — осознанное отклонение от буквального запроса

Прямая замена на Lucide **не рекомендуется**. У GarmentOS уже есть утверждённый, дословно перенесённый из прототипа набор SVG-иконок (`apps/web/src/components/Icon.tsx`) — тот же stroke-width (1.75), те же пропорции, тот же визуальный характер, который владелец проекта уже одобрил. Замена на Lucide заново поставила бы под вопрос уже согласованный визуальный язык ради библиотеки, которая по вашему же принципу должна быть *не видна* пользователю.

**Решение**: фирменный набор остаётся основным источником. Lucide подключается только как **дополнительный источник для иконок, которых пока нет в фирменном наборе** (нужны для новых компонентов — например, `x`/close для модалок, `calendar` для дейтпикера, `command`/`⌘` для командной палитры, `bell` для центра уведомлений) — при добавлении такая иконка не берётся из Lucide как есть, а перерисовывается в той же геометрии (`viewBox 0 0 24 24`, тот же stroke-width) и добавляется в общий спрайт `Icon.tsx`, как уже сделано для `search`/`tag`/`file`. Lucide в этом случае — референс/источник контура, не runtime-зависимость на весь пакет ради 3-4 иконок.

## 4. TanStack Query — почему сейчас, а не раньше

Раньше в этом же цикле работ React Query был сознательно отклонён («не подключаем без доказанной необходимости на 2 пользователях», `docs/PRINCIPLES.md` принцип 3). С тех пор `apps/web` вырос до 8 экранов, из которых минимум 3 (`PurchaseOrdersPage`, `ProductionOrdersPage`, `ProductDetailPage`) независимо друг от друга запрашивают одни и те же справочники (материалы/склады/поставщики/продукты) без кэша — при переходе между экранами каждый раз заново. Порог для принципа 3 («реальная, не гипотетическая необходимость») пройден: это не про масштаб пользователей, а про то, что ручной `useCrudResource` уже дублирует логику загрузки/ошибок в каждом файле и не переиспользует данные между экранами.

`useCrudResource` не удаляется резко — переводится на `useQuery`/`useMutation` внутри той же сигнатуры (`items`/`isLoading`/`error`/`create`/`reload`), чтобы вызывающий код на экранах не переписывался ради самой миграции (тот же приём, что использовался для `ListCard` — замена реализации без переписывания страниц).

## 6. Структура пакета

**Отклонение от буквального запроса**: не выносить в отдельный pnpm-workspace пакет `packages/ui` сейчас. Структура подкаталогов — да, ровно как вы описали, но физически внутри `apps/web/src/design-system/` (`Button/`, `Input/`, `Select/`, `Card/`, `ListCard/`, `Timeline/`, `Charts/`, `Modal/`, `Navigation/`, `Feedback/`, `Typography/`, `Icons/`, `Tokens/`, `Hooks/`, `Theme/`, `Animations/`), а не в новом workspace-пакете. Причина — `docs/PRINCIPLES.md` принцип 3: `packages/*` в этом монорепозитории оправданы, когда есть **второй потребитель** (пример — `packages/shared-types` используется и `apps/api`, и `apps/web`). Сейчас единственный потребитель дизайн-системы — сам `apps/web`. Разделение на пакет добавляет постоянные издержки (отдельный `package.json`, сборка, версионирование) без реального выигрыша, пока не появится второй потребитель — например, будущий Telegram Mini App (упомянутый как идея на будущее) или отдельный маркетинговый/документационный сайт.

**Условие переноса**, зафиксированное здесь заранее, чтобы решение не принималось на ходу под давлением срока: как только в репозитории появится второй `apps/*`, которому нужны те же компоненты — `apps/web/src/design-system/` переносится в `packages/ui` одним рефакторингом (структура подкаталогов уже правильная, меняются только импорты).

## 7. Экраны используют только компоненты дизайн-системы

Принимается без изменений — как только компонент из раздела 5 существует, прямое использование `<button>`/`<select>`/голого `<div className="card">` на странице экрана становится ревью-замечанием (`docs/QUALITY_STANDARDS.md`, раздел 4 «Код-ревью»), а не альтернативным способом сделать то же самое.

## 8. Mobile First и производительность

Без изменений к уже принятому `docs/PRINCIPLES.md` принцип 20 — этот документ его не пересматривает, а обеспечивает техническими средствами: Radix-примитивы дают доступность/клавиатуру «из коробки» (пункт из вашего запроса про accessibility/keyboard), Tailwind — mobile-first по умолчанию (брейкпоинты — расширение вверх, не вниз, что как раз соответствует «сначала телефон, потом десктоп» в отличие от классического Bootstrap-подхода).

## 9. Что не делается

Не устанавливается ни одна библиотека из разделов 2-5 до вашего утверждения этого документа. Не создаётся `packages/ui`. Не переписываются существующие 8 экранов немедленно — перенос на дизайн-систему происходит по мере того, как каждый экран дорабатывается дальше (форма-эталон — первый), а не отдельным «рефакторинговым» PR, переписывающим всё разом.
