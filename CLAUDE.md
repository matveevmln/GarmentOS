# CLAUDE.md — главный документ проекта GarmentOS

> Этот файл — точка входа для любого разработчика (человека или AI-агента), заходящего в репозиторий. Он не дублирует остальные документы, а **указывает, куда идти** и фиксирует правила, обязательные для соблюдения при работе с кодовой базой.

## 0. Статус репозитория

**Фаза 0 — Фундамент закрыта (2026-07-24).** Архитектура согласована владельцем проекта, все открытые вопросы из `docs/ARCHITECTURE_SELF_REVIEW.md` закрыты явными решениями. **Текущая стадия: Фаза 1 — реализация MVP**, см. `docs/ROADMAP.md`.

Окончательные решения, зафиксированные на Фазе 0 (не пересматриваются без нового ADR):
- Инфраструктура cloud-agnostic, «Start Lean, Scale Smart» (`docs/INFRASTRUCTURE.md`).
- Мультитенантность: единая БД, изоляция по `company_id` (`docs/ARCHITECTURE.md` п.6).
- Первый маркетплейс: Wildberries, через `MarketplaceConnector` (`docs/ARCHITECTURE.md` п.5.1).
- Local-First: собственная БД — единственный источник истины (`docs/PRINCIPLES.md` принцип 14).
- AI-First: архитектура держит открытыми точки входа для будущих AI-агентов, не строит AI-функциональность сейчас (`docs/PRINCIPLES.md` принцип 15).

**Правило для любого агента/разработчика на Фазе 1:**
1. Разработка идёт маленькими итерациями строго по порядку из `docs/ROADMAP.md` («Порядок итераций Фазы 1») — сначала данные и домен (БД → доменная модель → API → RBAC → аудит → логирование → бэкапы), интерфейс (`apps/web`) — не раньше итерации 9.
2. Ни одна итерация не считается завершённой без прохождения ревью-гейта (`docs/QUALITY_STANDARDS.md`, раздел 11): план → реализация → тесты → документация → Architecture/Code/Security/Performance Review (+ UX/AI Review где применимо).
3. Перед началом первой итерации с кодом — свежая проверка архитектуры на критические риски (если появились новые после последних решений).
4. Если тебя просят «добавить фичу» вне текущей итерации по роадмапу — сначала уточни, не преждевременно ли это.

## 2. Что такое GarmentOS (кратко)

Операционная система для швейного/fashion-бизнеса: закупка материалов → спецификации (BOM) и техкарты → производство → склад (SKU по размеру/цвету) → продажи (маркетплейсы + опт + розница) → маркировка «Честный Знак» → финансы. Подробности — `PROJECT_VISION.md`.

## 3. Ключевые архитектурные решения (сводка)

Полный текст — `docs/ARCHITECTURE.md`. Здесь — то, что должен знать любой, кто пишет код:

- **Стиль**: модульный монолит с чёткими границами модулей (domain modules), готовый к выделению отдельных сервисов без переписывания домена.
- **API-first**: любой модуль сначала описывается контрактом (OpenAPI), потом реализуется.
- **Многотенантность закладывается с первого дня** на уровне схемы БД (`company_id` в доменных таблицах), даже если MVP разворачивается как single-tenant.
- **Интеграции с маркетплейсами** — через единый интерфейс адаптера (`MarketplaceConnector`), а не встраиванием специфики WB/Ozon в доменную логику.
- **Честный Знак — отдельный bounded context**, не размазан по другим модулям.
- **Инфраструктура cloud-agnostic** (принцип «Start Lean, Scale Smart»): Docker, PostgreSQL, Redis, S3-совместимое хранилище за адаптером — переносимо между self-hosted (включая Кыргызстан по стоимости), Yandex Cloud, VK Cloud, AWS, GCP, Azure без изменений в коде. Подробности — `docs/INFRASTRUCTURE.md`.
- Технологический стек — TypeScript везде (backend + frontend), PostgreSQL, Redis, монорепозиторий на pnpm + Turborepo. Обоснование — `docs/TECH_STACK.md`.

## 4. Терминологический глоссарий (используй именно эти термины в коде и документах)

Последовательность терминологии критична для читаемости кода в предметной области, где много синонимов.

| Русский термин | Английский эквивалент в коде | Пояснение |
|---|---|---|
| Модель (изделия) | `product` | Абстрактная модель одежды (например, «Худи Base») |
| Артикул / SKU | `sku` / `productVariant` | Конкретное сочетание модель × размер × цвет |
| Спецификация | `bom` (bill of materials) | Нормы расхода материалов на единицу модели |
| Техкарта | `techSpec` | Технологическая карта пошива (операции, нормы времени) |
| Партия (кроя/пошива) | `productionBatch` | Производственная партия определённого SKU/объёма |
| Остаток | `stock` / `stockItem` | Количество SKU на складе |
| Приёмка | `goodsReceipt` | Поступление товара/материала на склад |
| Отгрузка | `shipment` | Исход товара со склада |
| Честный Знак | `honestSign` / `chestnyZnak` | Система обязательной маркировки товаров в РФ (ГИС МТ) |
| Код маркировки | `markingCode` | Уникальный DataMatrix-код единицы товара |
| Маркетплейс | `marketplace` | Внешняя торговая площадка (WB, Ozon, ЯМ) |
| Личный кабинет / кабинет продавца | `marketplaceAccount` | Учётная запись компании на конкретном маркетплейсе |
| Компания / тенант | `company` / `tenant` | Юрлицо-владелец данных в системе (мультитенантность) |

Не изобретай синонимы (`item` вместо `sku`, `warehouse_balance` вместо `stock`) — сверяйся с этой таблицей и расширяй её при появлении новых понятий.

## 5. Конвенции разработки (когда появится код)

- **Язык кода**: TypeScript strict mode везде. Комментарии и коммиты — на русском или английском, но единообразно внутри модуля (предпочтительно английский для идентификаторов, русский — для бизнес-документации).
- **Коммиты**: [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`). Пример: `feat(warehouse): добавить инвентаризацию по SKU`.
- **Ветки**: `main` — защищённая, `feature/<module>-<short-desc>`, `fix/<short-desc>`. Никаких долгоживущих feature-веток дольше одного спринта (см. `docs/PRINCIPLES.md`, trunk-based подход).
- **PR**: не мержится без прохождения CI (lint, typecheck, test) и минимум одного ревью.
- Подробные стандарты — `docs/QUALITY_STANDARDS.md`.

## 6. Правила для AI-агентов, работающих в этом репозитории

1. Перед реализацией любой фичи — свериться с `docs/ARCHITECTURE.md` и `docs/DATABASE_SCHEMA.md`, не изобретать параллельную структуру.
2. Если задача противоречит `PROJECT_VISION.md` (например, просят фичу вне скоупа MVP) — явно сообщить об этом пользователю, а не молча реализовывать.
3. Значимые архитектурные решения, не описанные в текущих доках — оформлять как ADR в `docs/adr/NNNN-title.md`, не просто менять код.
4. Не добавлять новые языки/фреймворки/базы данных без обновления `docs/TECH_STACK.md` и явного согласия владельца проекта.
5. Изменения в терминологии — только через обновление глоссария в этом файле.
6. Данный файл (`CLAUDE.md`) обновляется при любом значимом изменении архитектуры — он должен оставаться точным входным документом, а не устаревшим артефактом.
