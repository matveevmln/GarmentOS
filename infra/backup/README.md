# Резервное копирование — Iteration 8 (docs/ROADMAP.md), P0 перед первой партией

Два независимых слоя защиты, не один — ни platform-бэкап, ни собственный
скрипт не должны быть единственной линией обороны (`docs/PRINCIPLES.md`,
принцип 13 — cloud-agnostic, не привязываться к одной managed-функции).

## Слой 1 — встроенный бэкап Railway Postgres (проверить руками)

Управляемый плагин Postgres на Railway обычно включает автоматические
снапшоты, но точная периодичность и глубина хранения зависят от плана — я
не могу это проверить сам (нет доступа к railway.app из песочницы, см.
`infra/RAILWAY_DEPLOY.md`). Сделать один раз при подключении Postgres:

1. Открыть сервис Postgres в Railway → вкладка **Backups** (или
   **Settings → Backups**, название зависит от текущего интерфейса Railway).
2. Убедиться, что автоматические бэкапы включены, и посмотреть, за сколько
   дней они хранятся.
3. Если на вашем плане автобэкапов нет или частота недостаточна (реже раза
   в сутки) — не полагаться только на них, слой 2 ниже обязателен.

## Слой 2 — собственный `pg_dump`, переносимый на любую площадку

`backup.sh`/`restore.sh` в этой же папке — обычный `pg_dump`/`pg_restore`
через `DATABASE_URL`, не завязан на Railway API. Тот же скрипт без
изменений будет работать после переезда на VPS (`docs/INFRASTRUCTURE.md`,
Стадия A).

```bash
# Бэкап (например, в Railway cron job раз в сутки, или в cron VPS позже):
DATABASE_URL="$RAILWAY_POSTGRES_URL" BACKUP_DIR=/data/backups ./infra/backup/backup.sh

# Восстановление в НЕ ту же переменную, что источник (см. комментарий в скрипте):
TARGET_DATABASE_URL="postgres://.../garmentos_restore_check" ./infra/backup/restore.sh /data/backups/garmentos_20260802T120000Z.dump
```

На Railway: добавить это как отдельный **Cron Job**-сервис в том же
проекте (Railway поддерживает cron-триггер для сервиса из того же
Dockerfile, что `api`, командой `bash infra/backup/backup.sh` вместо
`node dist/main.js`), с `BACKUP_DIR`, указывающим на подключённый Railway
Volume — иначе дамп пропадёт при следующем передеплое вместе с остальной
файловой системой контейнера (тот же риск, что описан для
`LocalFileStorageAdapter` в `docs/ARCHITECTURE_REVIEW.md`, раздел 9).
Оффсайт-копия (S3-совместимое хранилище) — следующий шаг, не блокирует
первую реальную партию: локальный Railway Volume + встроенный бэкап
слоя 1 достаточно для пилота на 2 пользователей.

## Восстановление проверено вживую (2026-08-02)

Перед тем как отмечать этот пункт закрытым, реально прогнан полный цикл на
локальной БД с демо-компанией: `backup.sh` → дамп 196 КБ → `restore.sh` в
чистую БД `garmentos_restore_check` → сверка количества строк в
`companies`/`workshops`/`production_orders`/`audit_log` (совпало точно,
161/4/1/7 в обеих базах) → индексы из миграции 0015 подтверждены
присутствующими в восстановленной БД → scratch-БД удалена. Сам механизм
дамп/восстановление корректен. Единственное, что не проверено мной лично, —
слой 1 (Railway-специфичный автобэкап), потому что для этого нужен
реальный аккаунт Railway.
