# Аварийное восстановление — Pilot v1

> Запрошено владельцем проекта явно (2026-08-04): до начала работы с реальными
> данными должно быть чётко написано, что делать в каждой из типовых
> аварийных ситуаций — не искать решение в момент, когда партия уже "горит".
> Этот документ не описывает новые механизмы — только то, как использовать
> уже существующие (`infra/backup/`, Snapshot, Immutable Original) в
> конкретной аварии. Если сценарий не описан здесь — сначала `backup.sh`
> дамп текущего состояния (даже сломанного, для разбора причины), потом
> действовать.

## 0. Общее правило перед любым восстановлением

Прежде чем что-либо чинить — снять дамп текущего (пусть даже сломанного)
состояния БД (`infra/backup/backup.sh`). Восстановление из старого бэкапа
необратимо теряет всё, что произошло после него — если есть шанс, что
проблему можно исправить точечно, не откатывая всю базу, сначала
попробовать точечное исправление (см. сценарии ниже), откат всей БД —
крайняя мера.

## 1. Сломалась миграция

**Симптом:** `pnpm --filter @garmentos/db-schema db:migrate` падает с ошибкой
или зависает.

1. Прочитать текст ошибки — Drizzle останавливается на первой неудачной
   миграции, `__drizzle_migrations` фиксирует последнюю успешно применённую.
   Приложение (`api`) не перезапускать/не деплоить дальше, пока схема не в
   согласованном состоянии — иначе новый код может обратиться к
   несуществующей колонке/таблице.
2. Если ошибка — в самой миграции (опечатка, конфликт типов) — это баг в
   коде, не в данных: исправить файл миграции (если она не была применена ни
   на одной живой базе, `packages/db-schema/drizzle/`), закоммитить,
   передеплоить, повторить `db:migrate`.
3. Если миграция частично применилась (например, упала на середине
   multi-statement файла — Postgres оборачивает каждую миграцию Drizzle в
   транзакцию, поэтому частичное применение внутри одного файла маловероятно,
   но между файлами возможно) — сверить фактическую схему
   (`\d+ <table>` в `psql`) с ожидаемой по файлам миграций, вручную
   доприменить недостающие `ALTER`/`CREATE` из следующей миграции по файлу,
   затем вручную вставить её id в `__drizzle_migrations`, чтобы Drizzle не
   попытался применить её повторно.
4. Если непонятно, что пошло не так — восстановиться из последнего бэкапа
   (раздел 3 `infra/backup/README.md`) в отдельную БД, применить миграцию
   там, только затем повторить на реальной.

## 2. Упал Railway (сервис `api`/`web` недоступен)

1. Railway → сервис → вкладка **Deployments** → посмотреть, упал ли билд
   (тогда причина видна в логах билда) или упал уже запущенный процесс
   (крашится при старте — смотреть **Logs**, обычно это отсутствующая
   переменная окружения или недоступная БД).
2. Самое частое на пилоте — забытая/просроченная переменная окружения после
   ручного изменения (`infra/RAILWAY_DEPLOY.md`, шаг 3-4). Проверить, что
   `DATABASE_URL` всё ещё ссылается на плагин Postgres (`${{Postgres.DATABASE_URL}}`),
   а не превратился в текст руками.
3. Если сама БД Postgres недоступна (не сервис `api`) — это отдельная
   авария, см. раздел 5 ниже.
4. Быстрый откат — Railway хранит историю деплоев: **Deployments → выбрать
   предыдущий успешный → Redeploy**. Это откатывает только код (образ), не
   БД — безопасно в любой момент, БД не трогается.
5. Если сама платформа Railway недоступна (не наш сервис, а инфраструктура
   провайдера) — cloud-agnostic принцип (`docs/INFRASTRUCTURE.md`) даёт путь
   отступления: снять `pg_dump` (раздел 3 ниже, если БД ещё доступна отдельно
   от упавшего API) и поднять `docker compose` локально/на VPS как временную
   меру — не блокирующий пилот сценарий, но восстанавливать только если
   простой Railway длится часами, не минутами.

## 3. Удалилась партия (`production_orders`)

Партия физически удаляется из БД только прямым SQL — ни один use case в
коде не делает `DELETE` на `production_orders` (только `UPDATE` статуса).
Значит случайное удаление — это ручная операция в Railway Shell/`psql` или
восстановление из более старого бэкапа поверх текущей БД.

1. Проверить `audit_log` — если удаление произошло через приложение, там не
   будет записи `production_order.*` (аудит фиксирует изменения, не
   удаления, потому что удалений в use case нет) — значит это подтверждает
   ручную БД-операцию, а не баг в коде.
2. Восстановить **только эту партию**, не всю БД: поднять последний бэкап
   (`restore.sh`) во временную БД, найти строку в `production_orders` (и
   связанные `production_order_variants`, `documents`/`document_links` по
   `entity_id`), скопировать `INSERT`-ом в реальную БД с теми же `id`
   (сохраняя PK, чтобы ссылки из документов/остатков не порвались).
3. Если партия уже была принята на склад (`received`) и её удаление также
   стёрло связанные `stock_movements` — восстанавливать в том же порядке,
   что и создавались (партия → движения склада), иначе `stockItems.quantityOnHand`
   разъедется с историей движений.
4. Если точечное восстановление невозможно (бэкап слишком старый, партии
   там ещё не было) — партию придётся создать заново в интерфейсе, но
   Snapshot (раздел 6 ниже) при этом будет содержать текущие, не
   исторические, цены — зафиксировать это как известное расхождение в
   `docs/PILOT_LOG.md`.

## 4. Удалился PDF (документ)

Два независимых случая:

**a. Удалена строка в `documents`, но файл физически на диске/S3 остался.**
Файл — просто мусор, ничего не сломано для пользователя (кроме потери
ссылки на скачивание из интерфейса). Восстановить строку из бэкапа так же,
как в разделе 3 (по `id`, чтобы `document_links` не порвались).

**b. Файл физически пропал (диск/Volume/S3), а строка в `documents` жива.**
`GET /documents/:id/file` вернёт ошибку при попытке отдать файл.
- Если документ — сгенерированная спецификация (`docType: specification`):
  файл можно **пересоздать** повторным вызовом
  `POST /production-orders/:id/generate-specification` — это создаст новую
  версию документа (следующий номер спецификации, `supersedesDocumentId`
  указывает на пропавшую), не восстановление старого файла один в один, но
  рабочий результат для пилота. Отметить в `docs/PILOT_LOG.md`, что версия N
  была пересоздана из-за потери файла — это законная причина новой версии,
  отдельная от смыслового пересмотра спецификации.
- Если документ — загруженный вручную оригинал (договор, инвойс от цеха,
  фото брака и т.п.), которого нет в системе, — **физически невосстановим**
  из БД: только повторный запрос оригинала у контрагента (цех/поставщик) или
  восстановление из бэкапа Volume/S3, если такой существует отдельно от
  бэкапа Postgres (сейчас не настроен — раздел `infra/backup/README.md`
  описывает только бэкап БД, не файлового хранилища; см.
  `docs/MASTER_BACKLOG.md` как известный пробел для post-pilot).

## 5. Сломалась БД (Postgres недоступен/повреждён)

1. Управляемый Postgres на Railway — сначала проверить статус самого плагина
   (Railway → сервис Postgres → **Metrics**/**Logs**) — часто это временная
   недоступность, не повреждение данных.
2. Если это реальное повреждение (не просто недоступность) — восстановление
   только из бэкапа: слой 1 (встроенный снапшот Railway, раздел
   `infra/backup/README.md`) или слой 2 (`restore.sh` из последнего
   `pg_dump`). Слой 2 проверен вживую 2026-08-02 — команда та же, что в
   `infra/backup/README.md`.
3. После восстановления — обязательно повторить smoke test
   (`infra/PRODUCTION_CHECKLIST.md`, раздел «После деплоя») на восстановленной
   базе, прежде чем сообщать, что всё в порядке.
4. Разница между текущим моментом и временем последнего бэкапа — это данные,
   которые теряются безвозвратно при откате всей БД. Зафиксировать в
   `docs/PILOT_LOG.md`, что именно было потеряно (какие партии/документы
   создавались в этом окне), чтобы восстановить их вручную через интерфейс,
   если они были важны.

## 6. Появился неверный Snapshot

Snapshot (`production_orders.cost_snapshot`) — намеренно неизменяем после
подтверждения заказа (`docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`,
раздел «Snapshot партии»; `docs/PRINCIPLES.md`, принцип 19, Immutable
Original). В коде **нет** use case "исправить Snapshot" — это осознанное
архитектурное решение, не пробел, и не заводить его сейчас в рамках
feature freeze Pilot v1 (`CLAUDE.md`, правило 10).

Если Snapshot оказался неверным (например, у цеха были не те реквизиты
договора на момент подтверждения, и это вскрылось уже после генерации
спецификации):

1. **Если заказ ещё не отправлен цеху / спецификация ещё не имеет силы для
   контрагента** — это единственный безопасный путь точечного исправления:
   прямой `UPDATE production_orders SET cost_snapshot = ... WHERE id = ...`
   в Railway Shell/`psql`, выполняет только владелец, **обязательно** после
   `backup.sh`-дампа непосредственно перед изменением. Это ручная операция,
   выполняемая в обход `AuditService` (прямой SQL, не через API) — сразу же
   после неё добавить `note` к заказу (или запись в `docs/PILOT_LOG.md`) с
   текстом "Snapshot скорректирован вручную <дата>, было/стало, кто и
   почему" — то же самое before/after, которое `audit_log` фиксировал бы
   для операции через API, зафиксированное человеком, а не системой.
2. **Если спецификация с неверными данными уже отправлена цеху** —
   Snapshot не трогать (он останется как исторический факт "что было
   подтверждено тогда"), новая корректная спецификация — обычная новая
   версия документа (генерация специи снова после исправления реквизитов
   цеха, `supersedesDocumentId` укажет на неверную) — тот же путь, что и для
   любого другого пересмотра спецификации, ничего специального.
3. Как этого избежать в будущем — единственная реальная профилактика:
   проверять карточку цеха (реквизиты/договор/условия оплаты) **до**
   подтверждения заказа, не после — Snapshot существует именно для того,
   чтобы после подтверждения такие ошибки было видно (сравнение "что было
   зафиксировано" против "что сейчас в карточке цеха"), не для того, чтобы
   их предотвращать на этом шаге.
