## После деплоя — smoke test (прогнать вручную один раз)

Все запросы — к `https://<домен api>.up.railway.app/v1`:

1. `GET /health` → `{"status":"ok",...}`.
2. `POST /auth/login` реальным пользователем → получен `accessToken`.
3. `GET /production-orders` → `200`, пустой список (свежая компания).
4. `POST /workshops` с `contractNumber` → `201`.
5. Создать модель + BOM + утвердить BOM → `POST /production-orders/from-quantity` → `201`.
6. `POST /production-orders/:id/confirm` → `costSnapshot` не `null` в ответе.
7. `POST /production-orders/:id/generate-specification` → `201`, документ создан.
8. `GET /documents/:id/file` → PDF реально открывается (не `file://`, не 404).
9. Открыть `apps/web` в браузере → зайти → карточка партии показывает то же самое, что вернул API.
10. Передеплоить сервис `api` (например, пустым коммитом) → повторить пункт 8 — PDF должен по-прежнему открываться (проверка Volume из п.13 выше).

## Стратегия миграций и обновлений (владелец проекта запросил явно, 2026-08-04)

**Как обновляется схема.** Drizzle — миграции идут по порядку, каждая — отдельный SQL-файл в `packages/db-schema/drizzle/`, применяются командой `pnpm db:migrate` (идемпотентно, уже применённые пропускаются — `__drizzle_migrations`). На Railway — вручную через Shell после каждого деплоя, меняющего схему (шаг 5 `RAILWAY_DEPLOY.md`); автоматизация (миграция как часть деплой-хука) — рассмотреть после пилота, не раньше (лишний риск уронить прод миграцией без ручного контроля на 2 пользователях).

**Как откатываются миграции.** Drizzle не генерирует автоматический down-скрипт — откат делается новой миграцией "вперёд" (например, миграция N+1 удаляет колонку, добавленную миграцией N), тот же принцип, что и в остальной практике проекта (Immutable Original — история не переписывается, только дополняется). Ручной откат `DROP COLUMN`/`ALTER TABLE` вручную в Railway Shell — только в экстренном случае, до восстановления из бэкапа (`infra/backup/`).

**Что происходит с существующими партиями при изменении схемы.** Это ровно то, для чего построен Snapshot (`docs/PRODUCTION_BATCH_LIFECYCLE_ARCHITECTURE.md`, §26) — `production_orders.cost_snapshot` заморожен в момент подтверждения и не пересчитывается никаким изменением схемы или данных после. Новые колонки на существующих таблицах добавляются как `nullable` (не ломают старые строки) — уже сложившийся паттерн во всех миграциях этого проекта, не новое правило.

**Как обновляется само приложение на Railway.** Push в отслеживаемую ветку → автоматический билд и деплой (п.15 выше). Zero-downtime не гарантирован на этом плане Railway — для пилота на 2 пользователей секунды простоя при деплое не критичны; если станет критично, обсуждать после пилота, не сейчас.
